# 容量履歴の保存設計

## 採用する構成

2026-10-14、最適化DuckDBのファイル方式を採用決定した。比較結果・判断理由・切り替え要件は
[採用決定](decisions/20261014-duckdb-storage.md) を参照する。保守性を優先する型付きモデル・LINQ・EF Coreの方針は維持する。
アプリと診断CLIをDuckDBへ切り替えた。アプリの共有履歴は `catalog-v4.duckdb` に保存し、旧SQLite・以前のDuckDBファイルは変更しない。未変更の観測とフォルダ一覧を共有する新形式については [共有履歴の実装](decisions/20261014-shared-history.md) を参照する。以下の世代単位のモデル説明は読み出しビューにも引き続き適用される。
EF Coreプロバイダー1.27.0と、その依存であるSkuirrels.DuckDB.NET.Data.Full 1.5.6を固定した。
UInt128は保存層の型アダプターでUHUGEINTとして保持する。UUID、任意のUTF-16名のBLOB、可視一覧用の派生テーブルを使う。
通常の照会・メタデータ更新・履歴整理はEF Core/LINQ、一括観測保存はEFモデルから列と変換を得たAppenderを使う。
世代の参照検査と一覧の一括作成は、測定で必要性を確認した集合SQLを `DuckReadModel` に隔離する。
新規DBのスキーマは `DuckMigrations` のチェックイン済みマイグレーションで作成し、アプリ識別と版を検証する。

以下のSQLiteの記述は初期設計および開発経緯を示す。履歴の現行方式は [history-design.md](history-design.md) を優先する。

SQLiteとEF CoreのSQLiteプロバイダーを使う。専用DBサーバーは不要で、保存層を
`Something.Storage` として取得・解析・集計・UIから分離する。
保守性を優先し、通常の検索・更新はLINQと型付きエンティティで記述する。
テーブル定義・参照関係・索引・制約はEF Coreのモデルに集約し、
スキーマ変更はバージョン管理したEF Coreマイグレーションで管理する。

大量データもまずこの構成で実装し、バッチ単位で変更追跡を解放する。
読み取りでは必要な列だけを取得し、変更追跡を無効にする。
手書きSQLによる最適化は、実測で問題が確認された箇所に限り、
理由と検証結果を記録して検討する。SQLite固有の接続設定は保存層内に閉じ込める。

保存基盤と、一時DBを使う読み取り専用スキャンの上位5フォルダ表示を実装した。
診断CLIは履歴を保存しない。WinUIアプリは共有履歴DBへ自動保存し、過去結果の閲覧と24時間後の日次整理を行う。
過去24時間・7日・365日のフォルダ変動・増加／減少ランキングの照会APIも実装した。
現在の保存構成・保持・期間比較・開発中の旧データの扱いは [history-design.md](history-design.md) を参照する。
以下には初期設計と段階ごとの実装・測定記録も含む。履歴の現行方針は同文書を優先する。
合成MFTを読み取り専用スキャナーから型付き観測へ変換し、保存・集計・世代公開する流れを検証した。
容量帰属と比較の具体的な規則は [statistics-design.md](statistics-design.md) に定義する。
フォルダ表示・ランキング用には可視名ごとの無名DATA容量を保存する。
別にハードリンクの全DATAを共通祖先へ一度だけ帰属した指標も保存し、容量保存則の検証に使う。

`AddFolderEntryAccounting`マイグレーションで、folder_sampleへ名前別の直下・配下容量、名前件数、
未解決名前件数を追加した。旧世代の追加列はNULLのまま残し、未計算を0へ置き換えない。
旧世代の名前別ランキングは再走査が必要。明示的なSingleCountAllDataランキングは旧世代も読み取れる。
履歴比較では同じ集計方式の指標同士だけを比較し、旧世代と新世代を混在させない。

`ReadLargestFolders`は既定で名前別の配下容量を順位付けする。
`FolderRankingFilter`で絶対深さ（ルート0・直下1）または最下位ディレクトリへ絞り込める。
フィルターは集計後のフォルダグラフへ適用し、容量にはサブディレクトリも含む。
RootとNTFS管理フォルダは順位付けしない。最下位判定は有効な子フォルダを持たないこと。
範囲の未観測や不正な階層がある世代では、末端表示も楽観的な観測として扱う。

DBには取得済みのメタデータと集計を保存する。ファイルの内容やraw MFTダンプは保存しない。
WinUIの保持履歴は各スキャンのDB全体を複製するため、過去のファイル詳細とフォルダ集計の両方を保持する。
単一DB内の世代公開APIと、履歴のDBファイルを選ぶカタログは別の役割。ファイル単位の差分表示は未実装。

## 保存先と書き込みの境界

- 標準保存先はユーザーのLocalApplicationData配下のSomething専用ディレクトリ。
  開発中もリポジトリ内に実データを生成しない。
- ボリューム取得は読み取り専用。DB書き込みは通常のファイルAPIでアプリ専用領域に限る。
  DBの作成・更新のためにボリュームの書き込みハンドルを開かない。
- DB、WAL、共有メモリ、一時ファイル、バックアップは同じアプリ専用領域で管理する。
  スキャン結果のパスをDB保存先や削除先として使用しない。
- DB自身も対象ドライブの使用量に含まれる。アプリ専用領域を識別できた場合は
  Somethingの履歴として表示し、通常の肥大化ランキングから除外できるようにする。
  ドライブ全体の使用量からは差し引かない。
- ファイル名とパスは私的な情報。Git、通常のログ、例外メッセージへ出力しない。
  DBの暗号化は初期版では提供せず、ユーザープロファイルのアクセス制御に従う。

## 保存モデル

以下は論理モデル。SQLの列と制約は保存層の実装時に確定する。

| モデル | 主な情報 | 保持範囲 |
|---|---|---|
| Volume | 内部ID、ボリューム識別情報、NTFSシリアル、クラスタサイズ | 継続 |
| ObservationEpoch | ボリューム、連続性を確認できる観測区間、区切った理由 | 継続 |
| Scan | 開始・終了UTC、対象範囲、処理状態、観測方式、未解決件数、各ルールのバージョン | 履歴 |
| FileObservation | スキャン、ファイル参照、種別、取得状態、観測時刻 | 最新世代 |
| FileNameObservation | ファイル、親参照、名前、名前空間、リンク識別情報 | 最新世代 |
| StreamObservation | ファイル、ストリーム名、論理サイズ、割り当て容量、解決状態 | 最新世代 |
| FolderSample | スキャン、フォルダ参照、当時の親・名前、直下・共有・自身DATA・配下容量、件数、集計品質 | 履歴 |
| FolderCategorySample | フォルダ集計、データ種別、容量、件数 | 履歴 |
| VolumeSample | 一意DATA合計、管理DATA、所属不明DATA、独立取得したドライブ使用量、区分別の品質 | 履歴 |
| ScanIssue | スキャン、対象参照、未解決理由、試行回数、エラーコード | 履歴 |
| PublishedGeneration | 対象ボリューム・範囲、公開済みの最新スキャンID | 現在 |

### 識別情報

- ドライブ文字とパスは表示情報。永続的なキーにしない。
- ファイル参照は48ビットのレコード番号と16ビットのシーケンス番号を別々のINTEGERに保存する。
  符号なし64ビット参照をSQLiteの符号付きINTEGERへ直接キャストしない。
- ボリュームシリアルは固定長8バイトのBLOBとして保存する。シリアルだけを一意性の根拠にせず、
  取得層が報告するボリューム識別情報と連続性も照合する。複製ボリュームを無条件に統合しない。
- シーケンス番号も有限である。再フォーマット、参照の再利用、観測の連続性が確認できない場合は
  ObservationEpochを分け、長期間の同一ファイル・フォルダとの断定を避ける。
  USN追跡の実装後はJournal ID・USN範囲・欠落も連続性の判定に使う。
- 名前の比較にSQLiteのNOCASEを使ってNTFSの同一性を推定しない。
  元の名前・名前空間を保持し、照合規則は統計層で明示する。
- 最新世代のリンク名はすべて保存する。DOSエイリアスを別ファイルとして数えない。
  名前付きストリームも保持し、容量算入のルールは集計ポリシーに記録する。

## 容量と集計品質

論理サイズと割り当て容量を別々に扱う。未知の値はNULLまたは未解決状態で表し、
0へ変換しない。正常に取得できた0バイトとは区別する。
合算はchecked演算で行い、オーバーフローを0や負の容量として保存しない。
集計容量はUInt128の固定長16バイトbig-endian BLOBで保存し、C#側で合算する。
SQLiteの符号付きINTEGERやSUMへ切り詰めない。ストリーム単位のlong容量とは保存形式を分ける。

フォルダ集計には確認済みの容量、解決済みファイル数、未解決件数を保存する。
親が未解決で所属を特定できないファイルはスキャン全体の問題として記録し、
影響するフォルダを特定できないことも品質情報へ残す。
確認済み容量はライブ観測で得た部分合計であり、ある瞬間の使用量の厳密な下限とは主張しない。

初期版のフォルダ容量は、同一ファイルのDATAを一つの帰属先でだけ数える加算可能な指標とする。
ハードリンクの親が一つなら直下容量、複数なら最も近い共通祖先の共有容量へ帰属する。
親の配下容量は直下・共有・自身DATAと子の配下容量の和。全体で二重計上しない。
各リンクの名前・共有ファイル参照を保存するが、独立したリンクファイル容量を作らない。
リンクから参照される共有容量は参考値として主合計と分ける。確認できないリンク集合や
所属の容量は所属不明DATAへ保持し、分かっている親だけから帰属を推測しない。

DATA合計はNTFS管理領域等を含むドライブ全体の使用済み容量とは別指標。
取得層が報告するドライブ使用量も別に保存し、差分を自動的にファイルへ配分しない。

データ種別は主に拡張子で分類し、分類不能・曖昧なものを「その他・不明」へ残す。
複数リンク名で分類が衝突するファイルは「その他・不明」とし、同一集計内で二重に分類しない。
名前付きストリームは所属ファイルの分類へ算入する。
動画などのデータ種別とログ・キャッシュなどの用途タグを別軸にする。
用途の割合表示を追加する場合も、二重加算を避ける排他的な優先規則を定義する。
ファイル内容の解析は行わず、分類結果を内容の証明とは扱わない。
分類・容量算入・リンク処理のルールにはそれぞれバージョンを付ける。

## スキャンの公開と中断

処理状態と集計品質は独立に保存する。

- 処理状態: Running / Completed / Cancelled / Failed / Interrupted。
- 観測方式: OptimisticLive / PointInTimeSnapshot。現時点のライブ取得は前者のみ。
- 集計品質: 対象範囲の列挙状況、未解決の参照・ストリーム・親、変化が続いた対象など。
  Completedでも欠測はあり得る。

新しいスキャンは独立した世代として作成する。現在の実行経路は完了まで観測をメモリへ保持し、
メモリ上で集計・容量保存則を検証してから、全詳細・集計・PublishedGenerationを1トランザクションで保存する。
取得中はDBへ書き込まず、保存失敗時は新世代全体をロールバックする。
SQLiteの書き込みロックは保存の間だけ保持するが、大規模な世代では長くなる。
旧ステージ方式もAPIとして維持する。この方式は上限付きバッチで保存し、最後に公開を切り替える。
UIはPublishedGenerationが指す同一世代の詳細と集計を読む。
欠測を含む完了結果は品質を明示して公開できるが、信頼できる比較の基準としては別途判定する。

中断・失敗時は前回の公開世代を維持する。起動時に残ったRunningはInterruptedへ変更する。
中断世代のファイル詳細は履歴として公開せず、後でアプリ自身のDB内から片付ける。
この処理でスキャン対象のファイルを削除しない。

## 履歴比較

- 同じボリューム・観測区間・対象範囲・集計ルールの結果を比較する。
  条件が異なる場合は無条件に増加量を出さず、比較できない理由を返す。
- フォルダは参照で追跡し、当時の親・名前も履歴に残す。移動・改名と新規フォルダを区別する。
  親の容量増加にはフォルダの移入も含まれるため、純粋な内容の増加と断定しない。
- 不完全な観測同士の差を確定的な増減として表示しない。
  Missing / NotInUse / Replacedだけから過去のファイルの削除を推定しない。
- 7日・30日前の履歴がない場合は欠測扱い。近い日時を使う場合は実際の比較期間を表示する。
  増加速度は実際の経過時間から計算する。基準容量0の増加率は未定義として扱う。
- フォルダ履歴には直下と配下の容量を残す。親子ランキングの増加量を足し合わせない。
- 共通祖先の共有容量とフォルダ自身のDATAも残す。共有リンク変更による帰属移動を
  内容の増加と断定せず、共有容量の観測差として別に表示する。
- 履歴から後日分類を再計算するための全ファイル詳細は残らない。
  分類ルール変更をまたぐ種別別比較は区切る。

履歴の保持期間・日次への間引き・DBサイズ上限は、実測して実装前に決める。
初期保存層には明示的な保持設定と削除対象の選択を用意し、無制限の保持を前提にしない。
公開中の最新詳細と必要な比較基準を消さない。自動清掃はアプリのDB内部に限定する。

## SQLiteの運用

- ローカルDBでWALを使い、書き込み担当を1つにする。UIには別の読み取り接続を使う。
- 書き込みは明示的なトランザクションでバッチ単位にまとめる。大量の新規行はEFモデルから
  生成したprepared INSERT、状態変更と既存行の更新はEF CoreのSaveChangesで処理する。
  複数回の更新・削除と公開世代の切り替えは同じトランザクションで整合させる。
  一括登録の件数・時間・メモリは計測して調整する。
- Microsoft.Data.Sqliteの非同期APIは同期実行される。DB処理はUIスレッドから離し、
  バッチ境界でキャンセルを確認する。進行中の同期呼び出しの即時中断は約束しない。
- 各接続で外部キーを有効にする。容量・件数・状態・参照番号にCHECK制約を設ける。
  主な索引はスキャンと参照、親参照、フォルダと日時、フォルダ集計と種別に付ける。
- 読み取りのトランザクションを長時間維持しない。WALサイズとチェックポイントを監視する。
- スキーマ変更はEF Coreマイグレーションで管理する。新しすぎるスキーマを
  古いアプリで開いた場合は更新せず、対応していないことを返す。
- バックアップはSQLiteのバックアップAPIを使う。稼働中のDB本体だけをコピーしない。
  破損時にDBを勝手に削除して再作成せず、元の履歴を保持して復旧方法を提示する。

## 保存層の検証

### 現在の実装範囲

`Something.Storage` はEF Core 10.0.12の型付きモデルとLINQを使う。
初期マイグレーション・モデルスナップショット・NuGet lockファイルをリポジトリに保持する。
BufferedScanは記録に必要なStagedObservationをすべて保持し、生MFTやDATA runは保持しない。
列挙完了後にCompleteを呼び、PublishBufferedScanで一括保存する。
Complete前の保存・完了後の追加・重複レコードを拒否する。保存には表ごとに同じprepared INSERTを再利用する。
ステージ方式のStageBatchは1回最大1,000観測の別経路として維持する。
どちらも成功・失敗時に変更追跡を解放する。
読み取りはAsNoTrackingとレコード番号によるページングで行い、ページの番号範囲に対して
名前・ストリームを別々のLINQクエリで取得する。Includeのページング副問い合わせを繰り返さない。
階層構築はDBでディレクトリを絞り、通常ファイルやストリームを読み込まない。
集計はコンパクトな観測を再列挙し、全ファイルのrunやraw MFTバッファを保持しない。

最新世代の参照、フォルダ集計、当時のフォルダ名・親参照、名前付きストリームを保存する。
メモリ方式では全詳細・容量の要約・完了状態・公開ポインターを同じトランザクションで保存する。
旧ステージ方式は集計保存と公開を分け、最後のトランザクションで要約・完了状態・ポインターを更新する。
古い詳細の整理は1回最大1,000件で、公開中・実行中の世代を拒否し、
過去のフォルダ名と集計を保持する。自動整理・保持期間の適用はまだ接続していない。

SQLite固有の設定は`SqliteDatabaseBootstrap`、識別ヘッダーは初期マイグレーション内に置く。
識別ヘッダーはスキーマ作成と同じトランザクションで設定する。
大量の新規観測・名前・ストリーム・フォルダ集計の登録は`ModelInsert<T>`へ限定する。
INSERTの列名と値変換はEFモデルから取得し、表別のSQLや列一覧を重複管理しない。
準備済み文の実行だけをSQLitePCLRawで行う。既存のSqliteConnectionとEFのトランザクションを共有し、
1から始まるパラメーター番号へ直接バインドする。ADO.NETの行ごとのパラメーター名検索・reader生成を省く。
対応するprovider型は整数・bool・enum・TEXT GUID・文字列・byte配列・NULLに限定し、
対応外のモデルや値は例外にする。名前のUTF-16バイト配列とUInt128の16バイト容量はEFの既存変換を使う。
GUIDはMicrosoft.Data.Sqliteと同じ大文字D形式で保持する。
同じインスタンスの不変文字列だけバインドを再利用し、NULL・数値・blobは毎行更新する。
sqlite3_reset後に残る値が次の行へ混入しないことと、GUID切り替え・空blob・特殊なUTF-16名をテストする。
statementのsafe handleを処理終了時に解放し、SQLiteへ渡す文字列・blobはライブラリ側でコピーする。
アプリ側にunsafeコードや別の接続・トランザクションは追加しない。
値をSQLへ文字列連結しない。検索・既存行更新・削除・状態管理・マイグレーションは引き続きEF Coreを使う。
件数上限・CHECK/FK/一意制約・バッチのロールバック・公開ポインターの原子性は維持し、
履歴DBはWAL・synchronous=FULLを維持する。診断専用の設定は後述のプロファイルに分離する。
SQL失敗はDbUpdateExceptionへ包み、既存のエラー契約を保つ。
別アプリのDB・未知のスキーマやマイグレーション履歴は、削除・再作成せず拒否する。
途中で残ったRunningを自動変更しない。稼働中の別プロセスを誤って中断扱いにしないため、
起動時の排他制御とInterruptedへの復旧は今後実装する。

現在のScanStoreは単一の担当スレッドから呼び出す同期API。SQLiteのDB処理はUIスレッドから離す。
キャンセルはバッチ内の観測処理と保存・コミットの間で検査するが、進行中の同期SQLの即時中断は保証しない。
ScanDescriptorのボリューム識別・Epochと、列挙完了後だけCompleteScanを呼ぶ責任は上位の実行層にある。
ReadLargestFoldersは保存済み集計とフォルダ名履歴から階層を再構築し、ルート・NTFS管理領域を除いて
配下の既知の割り当てDATA容量で順位を付ける。親と子がともに上位になることがあり、順位の容量は加算しない。
集計を公開する前に、全入力の既知DATA容量と、ルート配下・管理ファイル・所属不明の既知容量の
合計を論理・割り当て両方で照合する。所属不明でも容量既知のファイルは捨てず、
Unattributed.KnownDataへ一度だけ計上する。CLIはこの既知量も表示する。
観測した名前は表示用であり、パスを開いたりリパース先を追跡したりするためには使わない。
`--top5`は列挙とメモリ上の集計が完了した後でTemporaryScanDatabaseを作成し、永続履歴とは独立する。
既知・未知の参照、DOS名、名前付きストリームを含む全観測を保存し、履歴比較のための情報を削減しない。
実行開始時刻・終了時刻、対象範囲・ボリューム識別・集計方針も従来どおり保存する。
識別キーは取得済みシリアルと呼び出し固有の範囲に限定し、ボリューム間・過去世代との同一性は主張しない。
DBはOSの一時ディレクトリ内の専用フォルダに作成し、正常終了・例外・キャンセル時に明示的なDB関連ファイルだけを削除する。
再帰削除やスキャン対象パスの削除は行わない。プロセス強制終了時の残った一時DBの回収は未実装。
ファイル一覧のフォルダ別照会、履歴比較、バックアップ、自動復旧と実機の保存性能測定は今後の作業。

テンポラリディレクトリ内のDBで検証し、管理者権限や実ボリュームを必要としない。
パーサーのカバレッジ指標とは分け、次の動作をテストする。

- 空DBからの作成、旧スキーマからの更新、未対応の新スキーマの拒否。
- 複数の名前・DOSエイリアス・ストリーム、最大参照番号・シーケンス番号の往復。
- 未解決容量と正常な0バイトの区別、合算オーバーフローの拒否。
- バッチ保存の失敗・キャンセル・再起動でも前の公開世代が維持されること。
- 世代公開と集計の整合性、外部キー制約、保持処理で最新世代を壊さないこと。
- 読み取りと書き込みの競合、ロックの待機上限、ディスク容量不足のエラー伝達。
- 移動・改名・参照再利用・欠測・ルール変更・基準容量0の比較。
- SQLiteバックアップからの復元と、取得対象への書き込みが不要であること。

### SQLiteのメモリ処理と診断専用設定（2026-10-13）

SqliteDatabaseBootstrapで履歴DB、診断用の調整ファイルDB、メモリDB、省メモリのファイルDBの設定を分ける。
診断CLIは後述の空きメモリ判定で方式を自動選択する。
比較用の`--memory-db`は完全なメモリDBと最後の書き出しを強制し、`--file-db`は省メモリのファイルDBを強制する。
どちらも保存する観測・名前・ストリーム・フォルダ履歴・世代公開は同じEFモデルを使う。

| 設定 | 履歴DB | 診断ファイルDB | 診断メモリDB |
| --- | --- | --- | --- |
| 主DB | ファイル | 所有する一時ファイル | 接続専用`:memory:` |
| journal_mode | WAL | DELETE（rollback journal） | MEMORY（rollbackを保持） |
| synchronous | FULL | FULL | FULL |
| page_size | 既存値・SQLite既定値 | 新規作成前に16 KiB | 新規作成前に16 KiB |
| temp_store | 既定値 | MEMORY | MEMORY |
| cache_spill | 既定値 | OFF | 既定値（主DBはメモリ内） |
| locking_mode | NORMAL | EXCLUSIVE | NORMAL |
| foreign_keys / CHECK / 一意制約 | 有効 | 有効 | 有効 |

診断ファイルDBのcache_spill=OFFは、トランザクション中のdirtyページの途中書き出しを抑える。
新しい大量データの書き出しは主にコミット時に行う。初期スキーマ作成などの書き込みもあり、
ファイル出力が完全に0になる方式ではない。WALでは同じ大量ページをWALと主DBへ書くため、
単独接続の使い捨て診断DBではrollback journalを使う。EXCLUSIVEもこの専用接続だけに限定する。
履歴DBにはこの排他設定やcache_spill=OFFを適用しない。

診断メモリDBはEFマイグレーション・INSERT・集計・世代公開を接続内で完結する。
読み取り専用ボリュームの取得完了後、C#の観測バッファからSQLiteへ保存する流れは維持する。
SQLiteへの保存中も主DBファイルは作らず、ExportSnapshotで初めて所有する一時ファイルを予約し、
Microsoft.Data.SqliteのBackupDatabaseでDB全体をコピーする。
書き出し先はCreateNewで確保し、既存ファイルを上書きしない。完成したファイルをFlush(true)した後だけ成功を返す。
未完了・未コミット世代の書き出しは拒否する。書き出し開始前と終了後にキャンセルを検査し、
失敗・キャンセル時は今回作成した一時ファイルを消す。BackupDatabase自体は同期処理で、途中の即時中断は保証しない。
ファイルはTemporaryScanDatabaseのDisposeで削除する。現在の診断CLIでは恒久履歴を保持しない。
将来の履歴保存では、完成したスキャンを履歴DBへ取り込む必要があり、履歴DB全体をこのスナップショットで置き換えない。

新規16 KiBページの100万件合成比較（全件・全名前・全ストリームと容量の読み戻しは回帰テストでも確認）：

| 構成 | SQLite保存・公開 | 最後のファイル書き出し | 保存関連合計 | ピークworking set |
| --- | ---: | ---: | ---: | ---: |
| 前回のファイルDB（WAL・既定設定） | 12.493秒 | 保存に含む | 12.493秒 | 750,379,008バイト |
| 診断ファイルDBの調整版 | 9.140秒 | 保存に含む | 9.140秒 | 1,525,895,168バイト |
| 診断メモリDB＋最後のsnapshot | 8.559秒 | 0.640秒 | 9.199秒 | 1,604,202,496バイト |

この試行では調整版の保存関連時間は約27%短縮した。メモリDBの書き出したファイルは724,697,088バイト。
設定変更前の4 KiBメモリDBは保存8.671秒＋書き出し1.264秒だった。
単回比較・OSキャッシュの影響を含むため、ページサイズだけの改善幅や実ボリュームの速度は確定しない。
ピークRAMは約2倍になった。C#の観測バッファに加え、SQLiteのページをメモリ保持するため、
巨大なスキャンでのメモリ予算・退避は今後の課題。RAMが増える設定を履歴DBへ一律に適用しない。
temp_storeは一時的なsort/indexのファイル出力を抑える設定で、主DBそのもののメモリ化とは異なる。
既に比較して効果のなかった単純な64 MiBキャッシュ拡大は採用しない。
mmap_sizeやthreadsはこのメモリDB・逐次INSERTの高速化に結びつく測定がなく、
設定値を並べるためだけには追加しない。PRAGMA optimizeはクエリ計画用であり、今回のINSERT改善には追加しない。

### 空きメモリに応じた自動選択

`--top5`の既定値はAutomatic。スキャン・BufferedScan.Complete後、既存のC#バッファと集計を
すでに確保した状態でWindowsのGlobalMemoryStatusExを呼ぶ。搭載RAMだけでは判定せず、
その時点の空き物理RAM、現在のプロセスでコミット可能な量、空き仮想アドレス空間を使う。
取得失敗や明らかに不正な値は、省メモリのファイルDBを選ぶ。

DBサイズ見積もりはファイルの内容サイズを使わず、全観測・名前・ストリームの件数とUTF-16長、
ディレクトリの集計・名前履歴から求める。初期64 KiB、観測256バイト、名前384バイト＋UTF-16長、
ストリーム320バイト＋UTF-16長、ディレクトリ集計512バイト、ディレクトリ名履歴256バイト＋UTF-16長。
この合計に50%の索引・ページ余白を加え、16 KiBへ切り上げる。実際のDBサイズの保証ではない保守的な推定値。
必要な追加余裕は見積DBサイズの2倍＋予備容量で、予備は搭載RAMの20%を1〜4 GiBに制限する。
空きRAM・コミット可能量・仮想空間のすべてがこの必要量以上の場合だけ、自動でメモリDBを選ぶ。
通常のCLIには`--memory-db`を付ける必要がない。

メモリが足りない場合のファイルDBは16 KiBページ・DELETE journal・EXCLUSIVE・FULL・制約有効を保ち、
空き量に応じた可変のcache_size、cache_spill=ON、temp_store=FILEを使う。
途中でdirtyページを書き出せるようにし、全DBページをRAMに抱えるcache_spill=OFFを使わない。
固定64 MiBではなく、メモリDBに足りない場合でも残った余裕をキャッシュに使う。
利用可能量は空きRAM・コミット可能量・仮想空間の最小値とし、予備容量を除いてから4で割る。
キャッシュ目安はその値と推定DBサイズの小さい方を64 MiB〜2 GiBに制限し、16 KiB単位へ切り下げる。
空き量を取得できない場合は64 MiBにする。極端に余裕がない場合にも最小値64 MiBは設定する。
搭載16 GiB、各空き量の最小値6 GiB、推定DB4 GiBの場合、メモリDBには不足するが、
キャッシュは約717 MiBを使える。DB全体を保持するための余裕と、部分キャッシュに使える余裕を分ける。
キャッシュはページに応じて確保され、設定した全量を最初から予約しない。
SQLiteへ渡す値は負のKiBに変換する。設定値の範囲・整列を接続前に検証し、予算やその反映をテストする。
キャッシュ設定はSQLite全体やC#バッファのハード上限ではない。
調整ファイルDBのcache_spill=OFFプロファイルは合成比較用に残すが、自動判定でRAMが足りない場合には使わない。

選択直後にDatabase-selectionを1行表示し、方式・理由・DB見積もり・必要追加量・予備量・空き量・file-cache-bytesを記録する。
`--memory-db`と`--file-db`は比較用の強制指定で、併用・重複は入力エラーにする。
方式を変えても保存する観測情報・容量・集計方式・確定状態は変えない。
スナップショット書き出しはメモリDBを選んだときに実施する。

この選択は開始時の見積もりであり、メモリの予約や実行中のメモリ不足を防ぐ保証ではない。
キャッシュ予算もこの時点で決め、実行中に継続して増減させる制御はまだ行わない。
ほかのプロセスが後からメモリを消費した場合の、保存途中での動的切り替え・OOM後の自動再試行は未実装。
低メモリ時もC#の全観測バッファは維持する。取得段階の固定予算やファイルへの退避は別の設計課題。
純粋な選択テストで各不足条件・境界・取得不能・計算上限・強制指定を検証し、
実Windowsのメモリ照会、省メモリのファイルDBでの保存・容量復元と有効PRAGMAも検証する。

## DuckDBとの性能比較と採用決定

2026-10-14、性能比較と一覧用構造をそろえたSQLiteとの追試を経て、ユーザーが最適化DuckDBのファイル方式を採用決定した。
ルート一覧の約10msを許容し、保存時間・DB容量・変動ランキングの優位性を重視する。
比較の条件・測定結果は [storage-comparison.md](storage-comparison.md)、結論・本番化の要件は [採用決定](decisions/20261014-duckdb-storage.md) を参照する。
アプリはDuckDB＋EF Coreへ切り替え済み。以下は比較開始時の検証方針の記録。

評価対象はスキャン完了後の大量保存と、将来の履歴比較・肥大化分析。
MFT取得／NTFS解析はDBと独立しており、フォルダ集計も現在はC#のメモリ上で行うため、
DBを置き換えるだけでこれらの処理が速くなるとは想定しない。
DuckDBは大量分析向けであり、ツリー展開やフォルダ一覧の小さな照会が速くなるかは別途測定する。

検証時は同一の合成観測データ（目安100万ファイル以上）を使い、最適化済みの現行SQLite保存と
DuckDBのAppenderによる一括保存を比較する。以下を確認してから採用を判断する。

- 保存・コミット・閲覧用索引準備・ファイル書き出しを含めた、結果が閲覧可能になるまでの時間。
- ツリー展開、サイズ順一覧の初回／追加取得、件数取得、ランキング、将来の履歴差分の応答時間。
- ピークメモリ、DBサイズ、一時ファイルへの書き込み量。メモリDB／ファイルDBと別ドライブ同時実行も区別する。
- 行数・容量の保存則・シーケンス番号・ハードリンク名・DOS別名・名前付きストリーム・未解決情報の一致。
- キャンセル／失敗時の公開単位と、前回結果を維持できること。
- EF Core 10向け第三者プロバイダーのLINQ変換、型マッピング、マイグレーション、保守状況。
  現在のUInt128容量表現とSQLite固有の挿入・接続設定・バックアップ処理の移植範囲も確認する。

単純なINSERTループだけの比較や、履歴・名前・不確実性の記録内容を減らした比較で採否を決めない。
比較後、DuckDBのファイル方式を選択した。プロバイダー互換性・同一プロセス内の並行保存・履歴整理を本番のモデルと回帰テストで検証した。実機の再スキャンと多世代運用の性能は別途確認する。
