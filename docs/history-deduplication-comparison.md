# 履歴の重複保存方式の比較

2026-10-14。合成DBでの検討結果。当初の試作に加え、現在は共有方式をアプリ本体にも組み込んだ。[実装の違いと保存形式](decisions/20261014-shared-history.md)、[当初の構造案](history-deduplication-proposal.md)。

## 比較CLI

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --history-dedup --count 100000 --generations 5 --output artifacts/history-dedup-100k-mixed.json
dotnet run --project tools/Something.StorageCompare -c Release -- --history-dedup --shape wide --count 100000 --generations 6 --output artifacts/history-dedup-100k-wide.json
dotnet run --project tools/Something.StorageCompare -c Release -- --history-dedup --count 1500000 --generations 3 --budget-mib 4096 --output artifacts/history-dedup-1500k-mixed.json
dotnet run --project tools/Something.StorageCompare -c Release -- --history-dedup --count 1000 --generations 20 --output artifacts/history-dedup-1k-20.json
dotnet run --project tools/Something.StorageCompare -c Release -- --history-dedup --count 1000 --generations 365 --output artifacts/history-dedup-1k-365.json
```

`--mode` は `full`、`reference`、`folders`、`blocks`、`all`（既定）。`--count` はルートを除く観測数、`--generations` は2〜365、`--budget-mib` は1024〜8192。通常はフォルダ10%・残りがファイルの構造。`wide` は一つのフォルダに約90%のファイルを置く。フォルダ32の照会が巨大フォルダの照会になる。

6世代の変化パターンは、初回、未変更、約1%変更、約10%変更、初回の状態へ戻る、単件変更。長期試験ではこの周期を繰り返す。変更にはサイズ、改名、親変更、参照のシーケンス変更、未解決、未観測も含む。ハードリンク、DOS別名、ADS、未解決ファイル、UTF-16の特殊コード単位を保存する。ファイル内容や実ボリュームは読み取らない。

## 同じ条件と検証

- `full` は本番のScanStore.PublishBufferedScanと同じ全件保存・一覧生成を使う。各候補の原データは本番の型付きエンティティ、モデル、制約、UTF-16/UInt128変換、Appenderを再利用する。スキャン時間の診断行はどの方式にも保存せず、構造の差に限定する。
- 各方式は独立したプロセスで順番に実行。同じDuckDB 1.5.6、ファイルDB、WAL有効、threads=4、preserve_insertion_order=false、同じメモリ上限。世代ごとにCHECKPOINTして本体サイズを測る。OSキャッシュは消去しない。
- 保存時間には変更検出・原データ追加・参照作成・一覧生成・コミットを含める。合成データ生成と集計は除外。CHECKPOINT時間は別の値。
- 保存後に接続を閉じ、C#の比較キャッシュを解放し、新しい接続で現在・過去の一覧を測る。照会ごとに初回と15回のウォーム測定を行う。初回はその照会の最初であり、OSキャッシュや先に実行した照会の影響まで除いた完全なコールド測定ではない。ウォームp95は15点の最大値で近似する。
- 全世代の観測・名前・全ストリーム・全フォルダ集計・管理/所属不明集計・世代メタデータ、および全可視一覧行を正規化したSHA-256で照合する。測定ページの件数・ソート・ルートツリー・容量ランキング・差分ランキングも照合する。最初の世代を削除後に、残る全世代の原データ・一覧を再照合する。
- ピークRAMはプロセス全期間なので、生成・保存・全件照合の負荷も含む。プロセスI/Oの書き込みバイト数は物理SSDのNAND書き込み量ではない。

このCLIは実験用のDBを `artifacts/history-compare/<実行ID>/` に作り、所有ディレクトリの範囲とIDを確認して削除する。実履歴を開かない。候補のDB識別子も本番と異なるため、アプリの履歴として誤って開くことを拒否する。

| ファイル参照 | 53.5 MiB | 2.264秒 | 23.540ms | 10.001ms |

フォルダ一覧共有は最終本体が約64%減少。未変更の2世代目は現行1.943秒・本体増分約47.2MiBに対し、共有一覧0.126秒・約5.5MiB。小さいデータでの最低ページ割当・索引・チェックポイントの影響もあるため、これを一定のバイト/ファイルとして外挿しない。

## 150万件・通常フォルダ・3世代

初回、未変更、約1%変更の3世代。DuckDBメモリ上限は全方式4GiB。一覧時間は接続を開き直した後のウォーム中央値で、ルートには約15万フォルダがある。

| 方式 | 本体 | 保存合計 | 未変更の保存 | ルート先頭 | 小フォルダ |
| --- | ---: | ---: | ---: | ---: | ---: |
| 現行全件 | 1597.8 MiB | 60.625秒 | 19.913秒 | 10.780ms | 1.405ms |
| ファイル参照 | 473.0 MiB | 25.010秒 | 1.923秒 | 194.386ms | 59.798ms |
| フォルダ一覧共有 | 621.0 MiB | 28.937秒 | 1.236秒 | 63.833ms | 10.298ms |
| ブロック共有 | 623.8 MiB | 28.656秒 | 1.106秒 | 69.627ms | 35.255ms |

フォルダ一覧共有は本体が約61%減少。未変更の世代による本体増分は現行約548.5MiBに対し約26.8MiB。初回保存は現行19.889秒に対し25.348秒で、共有構造を作る費用がある。

ルート先頭のp95は現行11.094ms、ファイル参照222.874ms、フォルダ一覧共有77.905ms、ブロック共有75.043ms。原データだけ共有して全ファイルの対応表から毎回一覧を組み立てる方式は、通常の表示に不利。フォルダ一覧共有も現行と同じ速度ではなく、特に大量の子フォルダの集計値を結合する照会には改善が必要。

プロセスピークRAMは順に4586.7、3387.0、3754.0、3846.9MiB。DuckDBの上限はプロセス全体の上限ではない。プロセス書き込み量は順に1711.5、489.2、631.6、634.1MiBだが、検証や世代削除も含む参考値であり、SSDの実書き込み量とは異なる。

## 小規模の長期履歴

1000件＋ルートで6世代の変更パターンを繰り返した。20世代・365世代とも全保存事実・一覧・測定照会・先頭世代削除後の残存履歴が全方式で一致した。365世代は365日間の実測ではなく、合成スキャン365回を保持した試験。

| 方式 | 20世代の本体 | 365世代の本体 | 365世代の保存合計 |
| --- | ---: | ---: | ---: |
| 現行全件 | 24.8 MiB | 149.5 MiB | 42.514秒 |
| ファイル参照 | 14.8 MiB | 20.0 MiB | 9.447秒 |
| フォルダ一覧共有 | 18.0 MiB | 32.8 MiB | 12.130秒 |
| ブロック共有 | 19.3 MiB | 33.8 MiB | 12.232秒 |

小規模ではチェックポイント・索引・最低ページ割当の割合が大きいため、大規模な365世代の容量や時間へ比例計算しない。実際の保持整理スケジュール、共有状態のGC、365日間の期間選択APIの検証は別途必要。

## 現時点の判断

次の実装候補は**原データとフォルダ一覧を共有し、大きな一覧だけブロック分割する方式**。全ファイルの「前回と同じ」参照行を世代ごとに作る方式より、表示に必要な直下の一覧を直接参照する構造を優先する。

採用前に、ファイル行とフォルダ行の結合の分離、一覧IDを直接指定した照会、必要なら最新世代・閲覧中フォルダだけの再生成可能な表示キャッシュを比較する。小フォルダまでブロック化しない。一覧応答、初回保存、メモリ予算、共有データの回収を確認してからアプリの保存方式を変更する。

合成DBの全方式で全世代の保存事実・一覧・測定照会・最初の世代を削除した後の残存世代が一致した。比較実験は実履歴DBを変更しない。本体への組み込みは別の新形式DBで開始する。

## 試作の限界と採用前の作業

候補はC#で前回の観測状態と、変更があった状態の過去版を保持して比較する。ファイルごとに元の値を照合し、ハッシュ一致だけで同一と判定しない。保存時のキャッシュはメモリ予算に収める必要があり、本番ではDBからの一括比較との対比も必要。状態が初回へ戻る場合は原データを再利用するが、一覧・ブロックの過去版の再検索はこの試作では行わない。

原データの状態は短い整数IDではなく、世代単位のUUIDグループ＋MFT番号で識別する。未変更の状態は元グループを直接参照する。世代を消しても共有状態は独立して残る。構造の有効性を比べる試作であり、最終的な整数IDモデルの測定値とは異なる。

保持整理の検証は世代の参照を除いた後の復元まで。共有データの到達性によるGC、失敗後の比較キャッシュの巻き戻し、複数ドライブの同時公開、公開ポインターとリースを含めた本番の実装は残る。試作は失敗時に終了するため、試作クラスをそのままアプリへ差し込まない。

単発測定から速度を保証しない。複数回の測定、大規模な長期世代、深い階層、取得異常を含む管理・拡張レコード、メモリ予算下の保存、実際のEF/LINQ一覧API・期間比較APIを確認してから採用する。今回の合成データは浅い階層の通常ファイル・フォルダと未解決観測で、実ディスクのあらゆる構造を検証したものではない。WALや取得内容、履歴の精度は容量削減のために省略しない。
