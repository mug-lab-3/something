# SQLite / DuckDBの比較

## 採用結論（2026-10-14）

比較とSQLite側にも同じ一覧用構造を追加した追試を経て、ユーザーは「最適化DuckDB・ファイル」を採用すると決定した。
SQLite案の一覧の方が速いが、DuckDB案の約10msを許容できる。保存時間・DB容量・容量および変動ランキングの性能を重視する。
オンメモリ書き出し方式は標準にしない。保守性を優先する型付きモデル・LINQ・EF Coreの方針は維持する。
[決定理由・比較表・本番化の要件](decisions/20261014-duckdb-storage.md) に詳細を記録した。
アプリと診断CLIをDuckDBのファイル方式へ切り替えた。下記は比較時点の実装・依存・測定の記録であり、本番移植後の性能を保証する数字ではない。

`Something.StorageCompare` は合成観測だけを使う開発用CLI。アプリの既存履歴や実ボリュームを開かない。DuckDB依存はこのツールだけに閉じ、アプリ本体はSQLite＋EF Coreを維持する。パッケージはDuckDB.NET.Data.Full 1.5.5に固定し、NuGetロックファイルを使用する。Visual StudioやDBサーバーは不要。実行時にはWindowsのMicrosoft Visual C++ Redistributable x64が必要（[DuckDB公式の前提条件](https://duckdb.org/docs/current/installation)）。このPCでは実行できており、新たなインストールは行っていない。未導入のPCでは `winget install --id Microsoft.VCRedist.2015+.x64 --exact` で導入する。ベンチマーク自体の実行に管理者権限は不要。

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --count 1200000 --repeats 3 --budget-mib 1024 --memory-budget-mib 2048 --output artifacts/storage-comparison.json
```

`--count` はルート以外の観測数で、10%がディレクトリ。120万件では約108万ファイルと12万ディレクトリを1世代として2世代を作る。まず `--count 1000 --repeats 1` でも確認できる。進行段階を5秒ごとに標準エラーへ出し、結果は最後にまとめる。Ctrl+Cで中断できる。

## 測定条件

- 同じ決定的な合成データを使い、各エンジンを別の子プロセスで計測する。反復ごとにSQLite→DuckDBとDuckDB→SQLiteの順序を交互にする。OSのファイルキャッシュは消去しない。
- 一意な所有一時ディレクトリにDBを作り、終了時にそのディレクトリだけを削除する。JSONの結果は指定した出力先に残す。各子プロセス終了時に部分結果も保存し、全照合成功時だけCompleted=trueになる。生成した履歴やDBはリポジトリへコミットしない。
- SQLiteは現行の `PublishHistoryBuffer`、EFの型変換と最適化済みModelInsert、WAL＋synchronous=FULL。固定したキャッシュ予算を適用する。
- 5方式を測る。`sqlite-browser` は同じ一覧用派生テーブルをSQLiteに追加した対照。`sqlite` は現行、`duckdb` はSQLite互換表現の初期比較、`duckdb-native` はDuckDB向けの構造、`duckdb-memory` はその構造で1世代ずつオンメモリに保存する方式。
- DuckDB向けの構造ではGUIDをUUID、容量をUHUGEINTにする。UTF-16の任意コード単位を保持する名前はBLOBを維持する。全観測・名前・ストリーム・集計を保持する。
- 一覧用の派生テーブル `browser` を親フォルダ順に物理配置し、ParentIndexのART索引を追加する。一覧は4テーブルの結合をやめてこの表から取得する。作成・配置・索引の時間と容量も測定に含める。期間差分と上位20件はUHUGEINTを使ってDB内で計算・抽出する。
- 主キー・一意制約・チェック制約は維持する。ネイティブ方式では外部キーの行単位の検査・索引を、世代のコミット前の一括anti-join検査に置き換える。これは不変の世代を一括で公開する設計が前提で、独立した行更新を許す汎用DBの互換実装ではない。参照関係を省略した高速化として扱わない。
- Appender、threads=4、preserve_insertion_order=falseを使う。予算はファイル方式が1 GiB、メモリ方式が2 GiB。同じ種類の設定でもエンジンごとの対象は異なり、プロセス全体の上限ではない。
- メモリ方式は `ATTACH ':memory:' (COMPRESS)` を使い、スキャン1世代ごとに確定保存する。初回は `COPY FROM DATABASE` で新しいファイルを作り、次回は空のメモリDBで1世代を作成して既存DBへトランザクションで一括追加する。過去の全履歴をメモリへ読み直さず、既存DBの置き換えもしない。書き出し・追加・チェックポイントまで計測する。照会と全列照合は最終のファイルDBに対して行う。
- データ生成とメモリ上のC#集計は保存時間から除外する。スキーマ・索引作成、2世代の保存・コミット、SQLiteのWALチェックポイント／DuckDBのCHECKPOINTを測る。`ready` はこれらの合計で、DBファイルへの反映までを含む。最終DBサイズはチェックポイント後に取得する。
- 同じ結果となるパラメーター付き照会で、小さなフォルダ、ルートのツリー・一覧初回／追加ページ、件数、容量上位20件、2世代の容量差分上位20件を照会する。結果を最後まで読み取って、初回と15回のウォーム計測を返す。15点のp95は最大値になるため、厳密な裾の分布の推定ではない。
- 差分はシーケンス番号を照合し、両世代とも解決済みのフォルダだけを対象にする。互換表現ではBLOBをC#のBigIntegerに変換し、ネイティブ方式ではDB内でUHUGEINTの差と順位を計算する。ここではDB照会・結果の読み取り・順位付けを測り、既存のパス再構築やWinUI描画は含めない。
- 全テーブル・全列を、世代のランダムScanIdだけ正規化してSHA-256で照合する。可視名、ハードリンク別名、DOS名、名前付きストリーム、シーケンス番号、未解決状態、直下／配下容量、履歴メタデータを省略しない。照合は保存・照会の時間から除外する。
- ピークワーキングセットは子プロセスごとに取得する。データ生成と照合のメモリも含む。Windowsのプロセス全体のWriteTransferCountもJSONに出すが、物理ディスクの書き込み量ではなく、標準出力等も含むI/O量である。

## 評価範囲と制限

これは保存エンジンの試作比較で、DuckDBへの置き換え実装ではない。DuckDB側は削除のCASCADEとSQLiteの部分索引を実装していない。ネイティブ方式の参照検査は不変世代の公開時に行う。その差を隠して同等の運用保証があると判断しない。DuckDBでコミット直前のキャンセル、SQLiteで最終メタデータの制約違反を起こす検証も用意し、未完成世代と最新ポインターを残さないことを確認する。大量保存の速度が良くても、履歴間引きの削除、強制終了・故障時の運用、同時スキャン、EF Core 10のLINQ・マイグレーション互換は別途検証する必要がある。

比較用SQLはこのCLI内だけに置く。アプリのLINQを手書きSQLへ置き換えてはいない。複数世代のフル観測の保存と、SQLiteの既存バルク処理という実際の負荷を比較対象にしており、`SaveChanges`の1件ずつの呼び出しとの比較ではない。

256 MiBでの120万件試験ではDuckDBが保存中にメモリ不足となったため、互換表現の同規模比較は両側とも1024 MiBで測定する。複数世代を1つのメモリDBにまとめる試作も1 GiBで失敗したため、メモリ方式は1世代ずつ作り2 GiBで検証する。予算値は同じでも、SQLiteのページキャッシュ予算とDuckDBのmemory_limitは同じ対象を制限しているわけではない。プロセス全体の上限ではないのでピーク実測値で判断する。圧縮の効きや索引の負荷は、この規則的で短い合成名・サイズのデータに依存する。実際の長いパス、深い階層、名前の偏り、長期の多世代DBで同じ結果になるとは保証しない。

ネイティブ方式の改善にはエンジンの変更だけでなく派生テーブルの追加が含まれる。SQLiteにも同じ用途の派生テーブルを加えた比較は未実施で、エンジン自体の優劣をこの数字だけで断定しない。最適化した試作であり、全ワークロードで最適な構造と保証するものではない。

## 2026-10-14の初回測定結果（一覧構造をそろえる前）

Windows x64、16論理プロセッサのPCで実施。各方式を独立プロセスで3回、1世代120万観測（約108万ファイル＋12万フォルダ）を2世代保存した。初期のSQLite互換表現の3回測定を対照として再利用し、その後ネイティブ構造と世代ごとのメモリ書き出しを測った。OSキャッシュ・PCの他の負荷は制御していない。代表値は3回の中央値で、照会は各回15回のウォーム中央値の中央値。WinUIやパス再構築は含まない。

| 項目 | 現行SQLite | DuckDB互換表現 | DuckDB向け構造・ファイル | DuckDB向け構造・メモリ→ファイル |
|---|---:|---:|---:|---:|
| 設定した予算 | 1 GiB | 1 GiB | 1 GiB | 2 GiB |
| 2世代の保存完了まで | 35.16秒 | 56.52秒 | 34.36秒 | 53.34秒 |
| うちチェックポイント／書き出し | 0.073秒 | 0.0005秒 | 0.001秒 | 22.58秒 |
| ルート一覧の初回ページ（温） | 492.86 ms | 86.51 ms | 12.35 ms | 12.80 ms |
| 小さいフォルダの一覧（温） | 0.030 ms | 4.38 ms | 1.35 ms | 1.53 ms |
| 期間差分上位20件（温） | 183.68 ms | 37.86 ms | 13.04 ms | 13.36 ms |
| 最終DBサイズ | 2097.8 MiB | 983.3 MiB | 699.5 MiB | 703.5 MiB |
| プロセスのピークワーキングセット | 2872.4 MiB | 2646.6 MiB | 2677.3 MiB | 3634.8 MiB |

全方式の全保存列のSHA-256と全照会結果が一致した。小規模の検証ではUUID、UHUGEINTの最大値、非対称サロゲートとNULを含むUTF-16名の保持、キャンセル／失敗時の世代と最新ポインターのロールバックも確認する。

ファイル方式の保存速度差は約2%で、この試験から有意な保存高速化とは判断しない。ネイティブ構造では大きい一覧が約40倍、差分が約14倍速く、ファイルサイズは約3分の1になった。小さなフォルダ照会は現行SQLiteの方が速い。メモリ方式は予算が大きくても書き出しの追加コストで遅くなったため、この条件では採用する理由がない。

ネイティブ方式の利点には親順の派生テーブルとDB内差分計算が含まれ、エンジンを交換するだけの効果ではない。同じ一覧用構造をSQLiteにも設けた対照は後述。採用前にはより深く不規則な名前・多世代データ、実アプリの応答、履歴削除、第三者EF Coreプロバイダーでの保守性を検証する。初回比較時点ではアプリのDBは置き換えていなかった。

実測JSONはローカルの `artifacts/storage-compare-final.json` にあり、生成データなのでコミット対象に含めない。

境界検証でDuckDB.NET 1.5.5の標準／Mapped AppenderがBigIntegerを符号付きHUGEINTとして扱い、UInt128の上位半分を直接追加できないことを確認した。比較用アダプターはその範囲だけ、同じ未公開トランザクション内でパラメーター付き文字列→UHUGEINT変換によって補正し、RETURNINGで値の一致を検証する。範囲外をゼロとして公開しない。最大UInt128を実際のフォルダ保存経路で書いて読み戻す検証は成功した。フル規模の測定データにこの例外範囲は含まれず、補正経路の追加後は小規模の全方式照合を再確認した。第三者ドライバーの型対応も採用前に確認する必要がある。

## 同じ一覧用構造を設けたSQLiteとの追試

再現コマンド:

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --engine compare-browser --count 1200000 --repeats 3 --budget-mib 1024 --output artifacts/storage-browser-1200000.json
```

現行SQLite、一覧用構造を追加したSQLite、最適化DuckDBファイルを新たに各3回測定する。全方式の設定予算を1 GiBとし、反復ごとに順序を反転する。SQLite側の派生テーブルにはDuckDBと同じ17列と同じ可視名・解決状態の条件を用いる。名前付きストリームやDOS名などを含む元の観測テーブルは削らない。一覧・ツリー・件数は両方式とも派生テーブルから同じ結果列・条件・並び順で取得する。

SQLiteには用途に合わせた複合B-tree索引を作成する: `(ScanId, ParentIndex, ParentSequence, IsDirectory DESC, EntrySubtreeAllocated DESC, StreamAllocated DESC, RecordIndex, Ordinal)`。別途 `(ScanId, RecordIndex, Ordinal)` を一意索引とする。DuckDBは既存候補の親順配置とParentIndexのART索引を維持する。索引を同じ文字列にそろえるのではなく、各エンジンに適した構造で同じ機能を満たす。作成・索引更新・最終チェックポイントをすべて保存時間とDB容量に含める。

SQLiteの派生テーブル追加は元データと同じ公開トランザクションで行う。追加中の失敗や最終メタデータの制約違反では派生行と新世代がともにロールバックし、既存の最新ポインターを保つ。通常のアプリ保存にはこの試験用処理を渡さず、本番スキーマは変更しない。

全観測テーブルの全列SHA-256と全照会結果に加え、測定対象のページ以外も含めた可視一覧全行のSHA-256を照合する。現行SQLiteは元テーブルの結合結果を比較基準とする。これらの検証時間は性能値に含めない。

今回そろえたのは一覧用構造。容量のSQLite BLOB表現とDuckDB UHUGEINT表現、期間差分をC#で計算するかDB内で計算するか、外部キーの検査方式は前回と同じで異なる。期間差分の差を一覧用構造の効果やエンジン単独の効果とは解釈しない。保持日数が多いDB、深い階層、実際のUI描画はこの合成試験の対象外。

候補実装は変更前に `artifacts/benchmarks/duckdb-candidate-20261014-132344.zip` へソース一式を退避した。SHA-256: `65EE6B13D41A56E2B6A27B32450E5CEDB7C837FD5B75F6CD2714DFA23B214E44`。NuGetロックファイルと固定SDK・ツール設定も含む。生成したDBやSDK・ビルド成果物は含めない。ZIPはローカル退避用でGit対象外。コミットや本番DBの置き換えは行っていない。
### 追試結果

120万件＋ルートを2世代、各方式3回、設定予算1 GiB。値は3回の中央値。照会は各回15回のウォーム計測の中央値を使う。初回・p95・各反復の値はJSONに残す。

| 項目 | 現行SQLite | 一覧用構造ありSQLite | 最適化DuckDB・ファイル |
|---|---:|---:|---:|
| 2世代の保存完了まで | 35.34秒 | 47.70秒 | 28.78秒 |
| ルートのツリー初回ページ（温） | 408.50 ms | 0.82 ms | 10.62 ms |
| ルート一覧の初回ページ（温） | 495.52 ms | 0.81 ms | 9.71 ms |
| ルート一覧の追加ページ（温） | 491.28 ms | 0.82 ms | 9.96 ms |
| ルートの件数（温） | 392.06 ms | 4.32 ms | 0.55 ms |
| 小さいフォルダの一覧（温） | 0.030 ms | 0.030 ms | 1.17 ms |
| 容量上位20件（温） | 32.83 ms | 34.63 ms | 3.35 ms |
| 増加量上位20件（温） | 182.24 ms | 179.51 ms | 11.28 ms |
| 最終DBサイズ | 2097.8 MiB | 2665.8 MiB | 699.3 MiB |
| プロセスのピークワーキングセット | 2872.7 MiB | 2873.7 MiB | 2675.4 MiB |

- 一覧構造をそろえると、SQLite案のルート一覧はDuckDB案より約12倍速い。前回の「大きい一覧ではDuckDBが速い」という差は、主に派生テーブル導入前のSQLiteとの比較によるものだった。この追試でDuckDBへの交換が一覧応答を改善する根拠は得られなかった。
- SQLite案は現行に対し一覧を約610倍高速化する一方、保存時間は約35%、DBサイズは約27%増える。派生行と複合索引を追加するコストを含む。
- DuckDB案はSQLite案より保存完了までが約40%短く、DB容量は約74%小さい。増加量上位20件の処理は約16倍速い。ただし容量表現・DB内計算・参照制約の検査方式も異なるので、エンジン単独の差ではない。
- 候補実装は引き続き保持する。ユーザーは一覧の絶対時間を許容し、保存時間、長期履歴の容量、変動ランキングを重視してDuckDBのファイル方式を採用決定した。本番化では互換性と既存機能の回帰検証を行う。

全9回で全保存列と一覧全行のSHA-256が一致し、7種類の照会結果も一致した。全保存列: `26DC06D76AB3DCD998A63467E036C72DB0E6844C33E0E9F509BEF36EEE1FB548`。一覧全行: `F4A7F246A21C8F227A971543EE23B86936CD99A1A5A8244B675C41977C48146C`。今回の3方式のフル規模追試はUInt128上位範囲の補正経路を追加した後の実装で行った。ただし合成観測そのものの容量はその範囲に達しない。起動時の境界プローブで最大値を別途検証する。

実測JSON: `artifacts/storage-browser-1200000.json`（Completed=true）。全5方式の小規模照合も `artifacts/storage-browser-all-smoke.json` で成功。失敗・キャンセルした派生テーブル作成が元データと一緒に戻る単体テストを追加し、テスト717件成功・公開コーパス7件未実行。CSharpierチェックとビルドも成功。

ピークメモリには合成データ生成と全行の検証も含む。CPUやOSキャッシュ・他プロセスの負荷は隔離していない。今回のデータは単一ボリューム・2世代で、候補CLIには複数ボリュームの最新世代更新や日次履歴整理などの本番機能をまだ移植していない。実際の深い階層、多世代履歴、保持期限後の削除、並行スキャン、UI描画、EF Core経由での保守性は採用前の確認項目。

## 本番移植後の状態（2026-10-14）

アプリ・診断CLIをDuckDBへ切り替えた。EF Coreプロバイダー1.27.0はSkuirrels.DuckDB.NET.Data.Full 1.5.6を使用する。公式DuckDB.NET 1.5.5と同じ名前のアセンブリが競合するため、現在の比較CLIも同じ1.5.6に統一した。初回・追試の数字は1.5.5で測った過去の結果であり、新バージョンの性能値として扱わない。元の候補ZIPはその時点の依存とソースを保持している。

移植後は通常の照会をLINQで記述し、観測の一括保存と参照検査・一覧作成だけを保存層に隔離したAppender／集合SQLで行う。全フォルダの変動レポートは従来のC#によるパス再構築・符号付き差分・未知状態の照合を維持する。比較CLIのDB内TOP20計算は本番の全件レポートAPIへそのまま移植していないため、その約16倍という測定値を現在のAPIの高速化率とは主張しない。

合成100万件のバッファ保存では、生成0.668秒、集計0.792秒、保存・公開10.742秒、容量一致を確認した。単回の動作確認で、並行して回帰テストも動いていた。これをエンジンの厳密な比較値には使わない。実ボリュームの再スキャン結果は未確認。
