# 履歴DBの削除と最適化

## 画面からの操作

DB管理タブには独立した「DBを最適化」ボタンを設ける。これは全ドライブ共通の履歴DBを対象とし、履歴を削除せず、未参照の削除済み世代を整理してから残存データを詰め直す。

「履歴を削除」は確認ダイアログを開く。対象件数と最古・最新の完了日時を表示し、「削除後にDBを最適化する」を選択できる。初期状態はオフで、削除ボタンをEnterキーの既定動作にはしない。最適化を選ばなければ削除後に通常の `CHECKPOINT` を一度だけ実行する。最適化を選んだ場合は削除後に全体の詰め直しへ進む。削除が成功し、後続の最適化が失敗した場合は、削除済みであることを明示した警告にする。

スキャン中や起動時の読込中は、最適化を開始しない。削除の確認中・処理中、最適化中はドライブとタブの切り替え・新しいスキャンの開始を抑止する。既に動いているスキャンを勝手に中断しない。

## DuckDBの仕様と採用した処理

`VACUUM` はDuckDBの削除領域回収には使わない。`CHECKPOINT` は削除が多い行グループを一部まとめ直すが、すべての空き領域を回収するものではない。全体の詰め直しは公式の `COPY FROM DATABASE` を用いる。

出典: [Reclaiming Space](https://duckdb.org/docs/current/operations_manual/footprint_of_duckdb/reclaiming_space)、[CHECKPOINT](https://duckdb.org/docs/current/sql/statements/checkpoint)、[COPY FROM DATABASE](https://duckdb.org/docs/current/sql/statements/copy#copy-from-database--to)。実装は `Something.Storage/HistoryCompaction.cs` に隔離している。通常の履歴照会はEF Core/LINQを維持する。

1. アプリ内の最新・過去・比較元の履歴セッションを解放する。同じDBのゲートを保持し、共有エンジンに別の管理対象接続が残っていれば実行を拒否する。別Archiveの読み取りも対象となる。
2. 参照が解放された削除済み世代を回収し、元DBをチェックポイントして接続を閉じる。ここでは日次保持ルールで新たな履歴を間引かない。
3. DBファイルサイズの1.25倍＋64 MiB以上の空きディスクを事前に確認する。これは一時DBの余裕を含む事前チェックで、実際の書込中のディスク不足も失敗として扱う。元DBは置き換えない。
4. 同じ履歴ディレクトリ内の専用作業ディレクトリへ新しいDBをコピーする。元は読み取り専用でアタッチし、共有状態IDや参照関係を変更せずDB全体をコピーする。自動バックグラウンド実行はしない。
5. すべての永続テーブルについて、双方向の `EXCEPT ALL` で重複も含めて内容が一致することを検証する。コピー先をチェックポイントして閉じ、アプリのDB識別・マイグレーション・共有関係を開き直して検証し、ファイルをディスクへフラッシュする。
6. コピー先が小さくならなければ元DBを維持する。小さくなる場合だけ、同一ファイルシステム内で `File.Replace` によりバックアップを伴う原子的な置換を行う。再接続・再検証後にバックアップを削除する。切替直前まではキャンセル可能で、置換から検証・バックアップ処理の短い区間はキャンセルしない。
7. アプリの接続を開き直し、可能なら表示していた過去の記録・比較条件・フォルダを復元する。前後のDBバイト数と削減量を表示する。

コピーはメモリDBを制御用の接続として使うが、コピー先はファイルである。アプリは操作時点の物理・コミット・仮想メモリの空きの最小値から75%を予算とし、ネイティブ表現の上限内に16 KiB単位で丸める。固定1 GiBなどの上限は置かない。メモリ不足をディスクへのスピルで補う設定にはしない。不足時は失敗し、元DBを維持する。クエリはキャンセルトークンからネイティブCancelを呼ぶ。

## 中断時の保護

バックアップ名は `catalog-v4.duckdb.compaction-backup`。これは原子的な置換から新DBの再検証完了までの間だけ存在する。次のアーカイブ操作でバックアップが見つかった場合、未完了の置換として元DBへ戻してから開く。バックアップがある間に新しい書き込みを認めないため、元へ戻しても後続の保存を失わない。

バックアップと現在のDBにWALが併存するなど、通常の手順で想定していない状態は強行して消さず、復旧待ちのエラーとして保持する。プロセスが作業コピー中に異常終了した場合、元DBはそのままで、`.compaction-<GUID>` に未完の候補が残ることがある。この候補は公開しない。通常の失敗・キャンセルでは、その操作自身の作業ファイルだけを削除する。

## 検証と制限

合成DBで空き穴を作り、ファイルが小さくなることと、残る履歴・他ドライブ・共有状態・UTF-16名・ストリームを保持することを検証する。独立したArchiveの読み取り中の拒否、コピー後のキャンセル、置き換え中断を模したバックアップからの復旧をテストする。UIではダイアログのキャンセル、既定オフ、最適化付き削除、通常削除、単独最適化と表示復帰を合成データだけで確認する。ユーザーの実DBを自動で最適化する検証は行わない。

他の履歴が共有状態を参照している限り、その状態は削除しない。削除件数に比例した削減量は約束しない。全体コピーと照合には処理時間・メモリ・SSDへの書き込みが必要なので、全体最適化は利用者が明示的に選んだときだけ行う。DuckDBを複数アプリプロセスから同時に使う運用、媒体故障に対する復旧保証、OS電源断の網羅的な実機検証は対象外。
