# 履歴の重複保存を減らす構造案

当初の検討案。本体への組み込み結果は [共有履歴の実装](decisions/20261014-shared-history.md)、測定結果は [比較結果](history-deduplication-comparison.md) を参照。

## 現状と方針

現行の `BufferedPublication` は、各世代に観測・名前・ストリーム・フォルダ集計・フォルダ名を保存する。さらに `DuckReadModel.CompleteWrite` が世代ごとの `browser` を全件生成する。未変更の名前・サイズも世代数に応じて繰り返し保存される。今回の「2回で約2倍」の正確な内訳は未測定であり、DB本体とWAL、索引、使用済み・再利用可能ブロックを分けて比較する必要がある。

推奨候補は、ファイルの観測状態とフォルダの一覧を不変の共有データにし、各スキャンはそれらを直接参照する方式。参照先は前回のスキャンではなく、保存済みの状態・一覧のIDとする。古いスキャンを削除しても、残るスキャンが使う共有データは残せる。未変更ファイルごとに「前回と同じ」という新しい行を作る必要も減らす。

## 比較する候補

| 方式 | 未変更時の追加量 | 一覧取得 | 課題 |
| --- | --- | --- | --- |
| 現行の全件保存 | 全ファイルの情報と一覧行 | 世代の一覧表を直接取得 | 履歴数に比例して大きくなる |
| ファイル状態共有＋世代ごとの全ファイル参照 | 全ファイル数に比例する小さいID行 | 参照表と状態の結合 | 実装は比較的単純だが毎回百万件単位の参照が増える |
| ファイル状態共有＋フォルダ一覧共有（第一候補） | フォルダ数に比例する小さい参照表＋変更箇所 | 指定世代・フォルダから共有一覧を直接取得 | 結合増加と大きいフォルダへの対処を測定する必要がある |
| 前回との差分だけ保存 | 変更箇所中心 | 基準世代から差分を適用 | 初回表示・履歴整理・未取得時の扱いが複雑になる |

前回との差分を何十世代もたどる方式は、一覧をすぐ出す要件との相性が悪い。まず直接参照できる候補を比較する。

## 第一候補の保存単位

| 保存対象 | 内容と参照 |
| --- | --- |
| ObservationVersion | 現在保存している観測状態・MFT参照とシーケンス・種別・解決状態・全名前/DOS別名・全DATAストリームを、等しい状態について一度だけ保持 |
| ListingVersion / ListingEntry | ある親フォルダの直下の可視名集合。各行はObservationVersionIdと名前Ordinal等を参照。未変更なら一覧全体を共有 |
| FolderSampleVersion | 配下容量・直接容量・件数・未解決件数・未観測数など、集計値が等しい場合に共有 |
| ScanFolder | 各世代のフォルダ参照・観測状態ID・一覧ID・集計値ID。各世代を独立して開くための小さい対応表 |
| ScanAuxiliaryObservation | 通常の一覧から参照できない観測の対応表。管理レコード、拡張レコード、名前のない未解決観測、所属不明等を落とさない |
| Scan / Volume / Timing | 世代の取得範囲・公開状態・不確実性・管理/所属不明集計・ステップ時間。引き続き世代単位 |

例：第1回のProjectsが一覧ID=100を使い、第2回に直下の観測状態・名前集合が同じなら同じ100を使う。ファイルが変更されたら新しい状態IDと新しい一覧IDを作る。第2回の結果から第1回の結果を読み戻す操作は不要。

サブフォルダの配下容量は一覧に埋め込まず、選択中の世代のScanFolderから取得する。これにより深いファイルが大きくなった際、すべての祖先の一覧まで複製することを避ける。祖先の集計値は新しいFolderSampleVersionになる。

空フォルダ、階層が不明なフォルダ、名前の親が未取得の観測も復元可能にする。ScanAuxiliaryObservationは「所属不明容量」だけではなく、共有一覧経由で復元できない保存済み観測すべてを対象にする。一覧と補助観測を合わせて、現行の保存内容が欠落せず、レコード単位で重複なく復元できることを検証する。

## 一覧速度を守る方法

照会はScanFolderから一覧IDを得て、その直下だけを読む。ファイルの表示用サイズ・状態はObservationVersionに保持し、名前・種類・サイズが過去の差分適用なしで得られるようにする。サブフォルダの容量は選択世代の集計値を結合する。通常の照会はEF Core・LINQ・型付きモデルを維持し、変更検出・一括保存のSQLは測定で必要な箇所に限定する。

一つのフォルダに十万ファイルがある場合、一件の変更で一覧全体を複製すると不利になる。比較では一覧全体を共有する簡単な案に加え、MFTレコード番号の固定範囲等で分けた一覧ブロックを共有する案も測る。表示順の行番号だけで分割すると途中の追加で後続ブロックがずれるため、保存時の分割キーはサイズ順・名前順と独立させる。UIの並べ替え・連続スクロールはこれまでどおり照会側で行う。

全世代の幅広いbrowser行を別途残すと重複削減の効果を失う。共有一覧がbrowserの役割を担う。結合が遅い場合は最新世代または閲覧中のフォルダに限定した、再生成可能なキャッシュを比較する。キャッシュを全履歴に恒久保存しない。

内部参照は短い整数IDを候補とする。DuckDBでは行の並び順が圧縮・ゾーンマップによる絞り込みに影響する。索引は増やせば必ず速くなるものではなく、既に起きたメモリ不足を再発させ得る。現行と同じ予算で、索引と並べ替えを含めて測る。[DuckDBの索引とメモリ](https://duckdb.org/docs/current/guides/performance/indexing)

## 同一状態の判定と安全性

- 「変化なし」は保存対象のメタデータが等しいという意味であり、ファイル内容のバイト一致を主張しない。ファイル内容は読み取らない。
- VolumeKey、MFT番号、シーケンスを保持する。サイズだけ、MFT番号だけ、更新時刻だけで再利用を判定しない。参照の再利用やシーケンスの周回を越えた同一ファイルの保証は追加しない。
- 親参照のシーケンス、名前、名前Ordinal、名前空間、属性、リンク集合の完全性、観測ヘッダー数、名前付きストリーム、取得/解決状態も比較する。フォルダ集計はポリシーバージョンと全保存項目を含める。
- ハッシュは検索候補の絞り込みに使い、等しい状態を共有する前に元の値を照合する。ハッシュ衝突で別状態を混ぜない。UTF-16の名前を正規化・置換して比較しない。
- 未取得や未解決の観測を「前回と同じ容量」として埋めない。同じ未解決状態を共有しても、その世代の不確実性は保持する。今回参照されなかったファイルを実ファイルの削除と断定しない。
- 共有データは変更しない。新状態・新一覧・世代参照・最新ポインターを一つのトランザクションで公開し、失敗時は旧世代を維持する。複数ドライブのVolumeKey、メモリ予約、限定再試行も維持する。
- 履歴整理は世代の参照を先に除き、残る世代や閲覧リースから到達可能な共有データを保護する。参照されなくなった状態・一覧・集計だけをまとめて回収する。元スキャンを削除しただけで共有行をカスケード削除しない。

## 容量と性能の確認計画

全スキャンが同一でも、世代ヘッダー・時間・フォルダ等の参照表は増える。2回目の増加をゼロとする案ではなく、名前・サイズ・一覧の大量の複製を避ける案。変更の割合や名前の長さによるため、削減率はまだ断定しない。

150万観測規模で現行、全ファイル参照、共有フォルダ一覧、一覧ブロック共有を比較する。未変更、1%変更、10%変更を含め、短期20世代と日次365世代の小規模ケースも測る。対象は通常フォルダ、空フォルダ、十万件の巨大フォルダ、深い階層、長い名前、ハードリンク、ADS、参照再利用、未解決観測、変更後に元の状態へ戻るケース。

測定はDB本体＋WALの増分、チェックポイント後の本体サイズ、保存・変更検出・一覧生成時間、初回/ウォームの一覧・件数・次ページ・ソート・ツリー展開・過去世代の表示、期間差分・ランキング、ピークRAM、書き込み量を対象とする。候補は中央値だけでなくp95と絶対時間も比較する。全可視行・生の保存事実・容量集計・未解決状態の一致と、保持整理後の残存世代の一致を先に確認する。

比較時のWAL・耐久性・メモリ予算は現行にそろえる。重複削減による効果と、WAL無効化や追加RAMによる効果を混ぜない。DuckDBのDELETEでは本体が直ちに縮むとは限らないため、内部で再利用可能になった領域も区別する。[領域回収の仕様](https://duckdb.org/docs/current/operations_manual/footprint_of_duckdb/reclaiming_space)

未リリースのため、採用時には新しいスキーマで開始し、旧DBの移行・上書き・削除を行わない。まず合成DBで容量と一覧応答を比較し、その結果で保存粒度を決める。
