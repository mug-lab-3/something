# 履歴ストレージ

## 保存先と型

全ドライブ・全スキャンを一つの DuckDB ファイルへ保存します。既定は `%LOCALAPPDATA%\Something\History\catalog-v6.duckdb`、共有形式識別子は 6 です。形式 5 以前の DB は開かず、自動変換もしません。設定から保存フォルダを変更できます。単独スキャン診断用の DuckDB 形式は 3 で、共有履歴とは区別します。

通常の照会は EF Core・LINQ・型付きエンティティを使用します。保存層には UInt128 / UHUGEINT と、任意の UTF-16 コード単位を保持する名前 BLOB のアダプターがあります。GUID は UUID で保存します。ファイル名を不正な Unicode として欠落させたり、置換文字へ変換したりしません。

## エンジンの選定

履歴の通常保存に DuckDB のファイル方式を使うのは、大規模なスキャンの保存容量・保存時間・集計と履歴比較の性能を優先したためです。同じ一覧構造を持つ SQLite を対照にした合成 120 万件・二世代の比較では、保存時間と DB サイズの両方で DuckDB が大きく下回りました。一方、ルート一覧の点照会は SQLite の方が速く、DuckDB をすべての照会で最速とは評価していません。比較条件と数値は[性能計測](benchmarks.md)にあります。採用時の候補構造は現在の共有状態モデルと同一ではないため、その数値を現在の性能保証には使いません。

型付きモデル、EF Core、LINQ を基本とし、エンジン選定を全処理を手書き SQL にする理由にはしません。Appender や集合 SQL は、測定したボトルネックに限って保存層の中で使います。

次の要件は、性能改善のためでも緩めません。

- 原観測・名前・DOS 別名・ストリーム・未解決状態を省かない。
- UInt128 全域、任意 UTF-16 名、符号付き増減を保持する。
- 差分はハッシュ一致だけで同一と判定せず、保存対象の全列を比較する。
- 世代の公開を原子的にし、参照を検証してから公開する。
- 物理 FK・カスケードに依存せず、依存行と共有状態を明示的に回収する。
- 一覧構造を持ち、連続スクロール・件数・ソート・過去世代の照会を維持する。
- ドライブごとの並行取得と共有 DB の予算・保存調停を分離する。
- 未対応の旧 DB を自動移行・上書き・削除しない。

## スキーマ

スキーマはチェックインした EF Core マイグレーションで構築します。既存 DB の形式・適用履歴を検査し、未知の形式を自動変換しません。古い SQLite / DuckDB ファイルを自動移行・上書き・削除しません。SQLite 実装は比較・回帰テスト用です。

## 共有状態の構造

| テーブル群 | 内容 |
| --- | --- |
| `state_observation` | ファイル参照、取得状態、容量解決状態、種別、属性、観測リンク数 |
| `state_file_name` / `state_stream` | DOS 別名を含む全名前・親参照と全 DATA ストリーム |
| `state_folder_sample` | 名前別・重複排除のフォルダ集計、未解決件数 |
| `generation_observation` | 世代に含まれる全観測と、その観測状態の版への参照 |
| `scan_folder_ref` | 世代のフォルダから観測状態・集計状態への直接参照 |
| `shared_entry` / `scan_listing_ref` | 不変の直下一覧と世代ごとの参照 |
| `scan` / `volume_sample` / `history_snapshot` | 世代の識別、品質、管理容量、完了日時等 |
| `scan_timing` / `scan_step_timing` | 合計と各ステップの実測時間 |

共有表の内部キーは整数です。世代は `scan.Number`（DB 内で単調増加）、状態の版はその状態を最初に保存した世代の番号、一覧は `世代番号 << 32 | 連番` です。`scan.Id`（UUID）は履歴・リース・アプリが使う外部の識別子として残し、読み取り用のビューは `scan` と結合して UUID を返します。版は状態グループの番号で、元スキャンの寿命を意味しません。世代から状態へ直接参照し、前回の差分を何世代も再帰的にたどりません。空フォルダも記録します。

上の表のうち件数に比例する表（状態・所属・参照・一覧）は、物理 PK・一意インデックスを持ちません。DuckDB の ART インデックスはメモリに常駐し、ディスクへ退避できないためです。一意性と参照は公開時に構築・検証します。新しい一覧の番号は昇順に振り、一覧のエントリを番号順に連続して書くことで、インデックスなしでも行グループの最小値・最大値による読み飛ばしを効かせます。整数の版・番号は値の範囲が小さいため、ビットパッキングで強く圧縮されます。

一覧が 4096 件を超える場合は MFT 番号の 1024 レコード範囲で分割します。表示ソート順と独立した分割により、巨大フォルダ内の変更で一覧全体を複製する量を抑えます。配下容量は世代の集計状態から結合し、深い変更のたびに祖先の一覧を複製しません。

## 変更検出と公開

同じボリューム・シリアル・範囲・集計ポリシーの直前の公開世代と、保存対象の全列を比較します。完成したスキャンバッファは .NET のメモリにあるため、前世代の観測・名前・ストリームを DB から一度だけ流し読みし、MFT 番号で引いたバッファの値と照合します。世代全体を TEMP テーブルへ複製せず、作業用に保持するのは観測ごとの小さな配列（版・一致状態・名前数・ストリーム数）だけです。ハッシュ一致だけで同一と判定しません。名前・属性・親シーケンス・ストリーム・取得状態の変化も保持します。

変化した観測だけを新しい状態として書き、変化のない観測は前世代の状態を参照します。一覧は、前世代の各エントリが同じキー・同じ観測状態の版で揃い、件数も一致する場合だけ再利用します。版の一致は ID の一致で判定します。

「変更なし」は取得したメタデータ状態が同じという意味で、ファイル内容のバイト一致ではありません。未取得・未解決の値を前回の既知値で補いません。全過去状態を毎回検索する方式でもありません。

新しい状態、一覧、参照、集計、履歴と最新ポインターを同じトランザクションで公開します。公開前に論理参照の存在・一意性・容量の保存則を検証します。検証は世代ごとの件数照合で行い、全履歴をハッシュ集合にしません。同じファイル内でストリーム名が重複する観測、前世代で同じ観測が重複する所属は、推測で補わずに公開を拒否します。物理外部キーやカスケードには依存せず、世代削除は依存行を明示的に処理します。他の世代が参照する共有状態は削除しません。削除候補は削除する世代が参照していた状態・集計・一覧だけで、全履歴を走査して孤立行を探す処理はしません。

キャンセルや保存確定前の失敗ではロールバックします。Appender の解放時に発生した後続例外で、保存本体の原因例外を上書きしません。WAL は有効のまま維持します。

## 一覧と閲覧保護

一覧取得は指定世代・親の一覧 ID を解決してから、その共有一覧を LINQ で照会します。件数・ソート・ページ単位の取得を提供し、UI は連続スクロールで追加読み込みします。画面へ全行を一度に構築する方式ではありません。

閲覧中の世代は `leases/<scan-id>.lock` のリースで保護します。保持整理や手動削除は世代を退役させ、参照解放後に回収します。アプリ内の公開・閲覧・整理は調停しますが、DuckDB を複数の独立アプリプロセスから同時編集する運用は対象外です。

## メモリ予算

保存・照会の成否を、実行する PC の空きメモリに依存させません。最低予算 1 GiB で、ボリュームの件数に関係なく完了することを要件とし、予算は速度にだけ影響させます。開発機の RAM に合わせて予算を引き上げ、メモリ不足を避ける方式は採りません。このため、大きな表にはメモリ常駐を前提とするインデックスを置かず、差分比較・検証・回収で世代全体の行をハッシュ集合として同時に保持しません。

通常の履歴保存はファイル DB です。オンメモリ DB の最後の書き出しを標準にはしません。メモリ DB を選ぶ診断用の処理とは区別します。

バッファ完成後の空き物理・コミット・仮想メモリの最小値から、他スキャンの予約と OS 用余裕を引きます。余裕は物理 RAM の 20% を 1〜4 GiB に収めた値です。残量の半分を DuckDB の `memory_limit` に割り当て、残りを管理外の割り当て等に残します。下限・情報取得不能時の起動予算は 1 GiB、値は 16 KiB 単位です。固定の 2 / 8 GiB の天井は置かず、ネイティブ表現上の上限を使います。

予約はスキャンバッファと DB 上限の約 2 倍を計上します。既存エンジンの上限を小さい別ドライブの接続から下げません。`memory_limit` はプロセス全体の上限でも事前確保でもなく、空き RAM が少ない環境での完了保証ではありません。

共有履歴は `threads=4`、`preserve_insertion_order=true`、`temp_directory=''` を設定します。挿入順を保持する設定でだけ、DuckDB は確定前の追記を完成した行グループ単位で DB ファイルへ書き出し、トランザクション中のメモリに溜めません（300 万行の追記で常駐 54 MiB、無効時 453 MiB）。通常は TEMP の自動ディスク退避を無効にし、追加の一時書き込みより RAM の増額を優先します。永続 DB・WAL の書き込みまで抑止する設定ではありません。

DuckDB の OOM では、失敗トランザクションの破棄後に空きメモリと競合予約を再確認し、予算を増やせる場合に最大 3 回再試行します。予算を増やせない、または増額を使い切った場合は、最後に一度だけ DB 隣接の `<DB>.spill` ディレクトリへのディスク退避を有効にして再試行します。退避はそのエンジンを閉じるまで有効で、最後の接続を閉じるときにディレクトリを削除します。異常終了で残った退避ディレクトリは、次にエンジンを開くときに削除します。どの再試行も完成済みバッファを使い、再スキャンしません。

確定中の OOM は、DB を読み直し、試行した世代が完了状態で存在すれば公開済みとしてその世代を返します。存在しなければ未公開と判断し、上と同じ規則で再試行します。一般の .NET OOM、制約違反、キャンセルは自動再試行しません。予算増額とディスク退避は想定外の場合の保険です。200 万件・予算 1 GiB の計測では、再試行・退避なしで保存が完了しました（[性能計測](benchmarks.md)）。

## 書き込み量

ディスクへの書き込みは、SSD の寿命を縮めないよう最小限にします。

- 1 世代で書き込むのは、変更された状態と所属・参照の行だけにする。
- 世代全体の一時複製、中間表の作り直し、退避ディレクトリへの書き出しを、通常の保存経路に入れない。
- DB 全体を書き直す最適化は、明示操作のときだけ実行し、自動では実行しない。
- 書き込み量はプロセスの書き込みバイト数で計測し、変更前後を比較する（[性能計測](benchmarks.md)）。

## 時間計測

各区間は単調増加時計で計測し、100 ns 単位の ticks へ保存します。再試行も別区間として残し、区間合計と全体時間の一致を検査します。履歴付き処理は 14 ステップです。

公開と保持整理の時間も測るため、計測結果の最終保存は観測公開後の別トランザクションです。最終書き込み前の終了では、公開世代に計測行がない場合があります。欠測を 0 秒と解釈しません。ボリュームを開く処理、UI 描画・一覧クエリ、計測結果自身の最終書き込みは合計に含みません。
