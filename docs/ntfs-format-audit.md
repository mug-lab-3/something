# NTFS解析規則の根拠と未確定事項

2026-10-12時点の設計監査。現在の実装全体がNTFS仕様に適合済み、という宣言ではない。
ライブ検査で正常に解析できた件数や合成テストの成功だけでは、形式の解釈の正しさを証明しない。
以下はコードの判断根拠を区別したもので、実機の個別ファイルの情報やdumpは保存しない。

## 根拠の区分

- **公開仕様**: Microsoftが説明しているフィールドやAPIの契約。
- **実装知見**: ntfs-3g等の実装者が公開する構造・読み取り処理。Microsoftの仕様保証とは区別する。
- **実機観測**: 今回のWindows返却データで確認した挙動。全ボリューム・全形式へ一般化しない。
- **実装方針**: 資源上限や保守的な拒否条件。本来のNTFS形式制約とは区別する。

## 現在の主要な判断

| 判断 | 根拠 | 現状／必要な見直し |
|---|---|---|
| raw FILEの512バイト刻みの全末尾を検証し、検証後に復元する | 公開仕様: MULTI_SECTOR_HEADER | 維持。raw検証失敗を別入力モードで救済しない |
| USAが第1stride末尾より前に収まることを検証する | 公開仕様: MULTI_SECTOR_HEADER | 維持。配列要素数とbyte長を区別する |
| 属性長を8バイト単位とし、レコードの使用領域内で検査する | 公開仕様: ATTRIBUTE_RECORD_HEADER、境界検証方針 | 維持 |
| LowestVcn / HighestVcnがextentの範囲を示す | 公開仕様: ATTRIBUTE_RECORD_HEADER | 維持。VCN不連続を省略値で補わない |
| 非常駐サイズの正本はLowestVcn 0のextentにある | 公開仕様: AllocatedLength / FileSize / ValidDataLength、実装知見 | 維持。継続extentのサイズ欄を合計しない |
| mapping pairsを属性ごとに初期化して解読する | 公開仕様: ATTRIBUTE_RECORD_HEADERの解読手順、実装知見 | 維持。signed LCN差分、hole表現、終端、範囲を検証する |
| FSCTLで返された番号を起点に降順列挙する | 公開仕様: FSCTL_GET_NTFS_FILE_RECORD | 維持。空き範囲を歴史的削除と推定しない |
| Windows返却をrawディスク画像と同じUSA保存値基準で検査しない | 公開仕様の書き込み／復元手順からの推論と実機観測 | WindowsDecodedの取得契約として分離。APIの全条件での挙動保証やディスク整合性の証明とは扱わない |
| DATA extent間の設定省略を容量解析に限定して扱う | ntfs-3gのSparse更新、OSS読取構成、実機観測と推論 | Sparse差、および先頭の圧縮形式が1のときの継続の圧縮ビット省略を許容。逆方向・別形式・暗号化・未知ビットの差はUnsupported |
| 圧縮単位をoffset 34の1 byteとして読み、予約5 byteを別に保持する | NTFS3 v6.12、ntfs-3g 2022.10.3の構造定義 | U16読み取りを撤去。予約byteが非ゼロでも圧縮単位へ混ぜず、入力を変更しない |
| ストリームの圧縮単位は先頭extentだけから取得する | NTFS3 v6.12 attr_is_frame_compressedの明示的な有効範囲、ntfs-3g属性初期化 | 4→0の個別例外と継続値の一致要求を撤去。継続値は元の属性として保持する |
| 全物理runのクラスタ数を合計し、先頭の容量欄と照合する | 実装知見、容量検証方針 | 一致は必要な検証だが、flagsや容量欄の解釈が正しいことの独立証明ではない |
| DATAの物理runが観測した総クラスタ数の範囲内に収まることを検証する | ボリュームジオメトリ、境界検証方針 | ライブ診断・走査で総クラスタ数を結合器へ渡す。holeの論理VCNには物理境界を適用しない |
| 最大レコード長64 KiB、リスト1 MiB、ファイル128レコード等 | 実装方針: 資源上限 | NTFS仕様上の上限ではない。超過は容量不明として明示する |

## 監査で見つかった追加の確認点

1. Microsoftの公開構造ではoffset 34以降はReserved。幅と有効範囲は下記の固定版OSSを
   根拠に修正した。Microsoftの公開仕様から圧縮形式全体が確定したとは扱わない。
2. flagsのうちSparseビットは先頭extentだけで状態変更される実装知見を確認した。
   先頭で形式1が示される圧縮設定の継続での省略にも、容量解析の対応を追加した。
   対応条件以外の差はUnsupportedで構造不正と区別する。
   VCN不連続・容量不一致は引き続きInvalidAssembly。
   どちらの失敗でも容量を返さず、変更の可能性を再取得で検査してから分類する。
3. 合計が一致しても、個々のDATAの物理LCNが実ボリュームの範囲内にある証明にはならない。
   DATA結合器に任意のtotalClustersを追加し、取得層からライブ診断・走査の全経路で渡す。
   物理runの先頭LCNとクラスタ数を減算で検査し、終端が総クラスタ数と一致する場合は許可する。
   範囲外は再取得で変更を検査してからInvalidAssemblyとし、部分容量を返さない。
   総クラスタ数を省略した単体レコード解析では実ボリューム境界を検証したと主張しない。
   ジオメトリはボリュームを開いた時点の観測であり、走査中のサイズ変更を追跡する仕組みではない。
4. 容量の実機照合は現状、通常ファイル1件と圧縮ビット省略のある複数extentファイル1件の論理サイズと割り当て容量。その他の拡張・圧縮・Sparseの割り当て容量を
   Windows APIや独立した公開コーパスの期待値で照合する必要がある。
   --fileにWindowsのFileStandardInfo（通常）／FileCompressionInfo（圧縮・Sparse）を
   使った容量照合を追加した。通常ファイルにも圧縮情報の値を割り当て容量として使った
   初期実装は修正済み。APIのフィールド名やMS-FSAの定義だけでWin32返却を一般化しない。
   同一ハンドルで前後の容量も検査し、API失敗や変化は一致へ変換しない。
   自身の一時ファイルでAPI取得を検証し、圧縮ビット省略のある実ファイル1件ではMFTとの両容量一致も確認した。Sparseのライブ容量照合は未確認。

## 容量の独立照合テスト

テスト専用にDiscUtils.Ntfs 0.16.13（MIT）を追加した。製品側のNTFS実装への依存にはしない。
バージョンと依存関係はNuGet lockで固定し、通常のsetupで復元する。追加の開発ツールは不要。

NISTの7ケースはMFTとディスク画像のSHA-256を検証してから、画像を読み取り専用で開く。
DiscUtilsのディレクトリ検索で得たシーケンス番号込みの参照を結合結果と照合し、
DATAの論理サイズと、独立解析器が返す物理クラスタ範囲の合計を比較する。
サイズ取得にFILE_NAMEのキャッシュを使わず、名前付きDATAも比較する。
ハードリンクは参照とストリーム名の組で重複を除く。
再帰列挙は使わず、ディレクトリ参照による重複除去・件数上限・キャンセル付きで探索する。

| NISTケース | 比較DATAストリーム | うち圧縮 | うちSparse |
|---|---:|---:|---:|
| 01 | 9 | 0 | 0 |
| 02 | 10 | 0 | 0 |
| 03 | 12 | 0 | 0 |
| 04 | 19 | 0 | 0 |
| 11-mft | 13 | 0 | 0 |
| 11-compress | 13 | 6 | 0 |
| 17 | 52 | 0 | 0 |
| 合計 | 128 | 6 | 0 |

比較件数は選定した画像とAPI列挙から得たローカルの回帰期待値であり、NIST発表の期待値ではない。
全レコードの解析・結合検証に加えて、独立列挙から到達できたファイルの容量を照合する。
この独立列挙の比較が全管理レコード・全ディレクトリDATAまで網羅するという主張はしない。

これらの画像にはSparse DATAがなかったため、別の2テストではDiscUtilsでメモリ内に
64 MiBのNTFS画像を作り、8 MiBのSparseファイルを格納する。
全領域がholeの場合は物理割り当て0、先頭と末尾の各1クラスタにデータがある場合は
2クラスタ分となることを、生成側の物理クラスタ取得とSomethingのraw MFT解析で照合する。
テストのFormat・SetAttributes・データ書き込みは、そのテスト専用MemoryStreamだけが対象。
実ディスクのフォーマット・属性変更・マウント・ボリュームアクセスは行わない。

DiscUtilsを使う独立画像照合と画像生成はWindows限定。純粋な解析・結合テストは引き続き
実ボリュームや管理者権限を必要としない。NIST画像は既存のオプトイン取得手順を使う。
独立実装との一致は追加の根拠であり、Windowsで作られた全形式への対応や
圧縮・Sparseのライブ容量照合の代わりにはならない。

## 次の実装の進め方

NTFS解析・容量検証はまだ完了していない。走査の処理完了と、全ファイル形式への対応完了を区別する。
フォルダ集計へ進む前に、初期版の対応範囲と次の残件を明示する。

| 残件 | 現状 | 完了／扱い確定の条件 |
|---|---|---|
| DATA extent間のflags差 | Sparse差と先頭圧縮形式1の継続省略に対応。圧縮省略1件はWindowsと両容量一致 | 変更後の全件走査で残件を確認する。逆方向・別形式・暗号化等の差を根拠なく通さない |
| 非resident ATTRIBUTE_LISTのmappingが拡張レコードへ続く形式 | 取得未対応 | 参照追跡とリスト取得の循環・欠損・変更・資源上限を設計し、検証する。未対応のままなら明示的に初期版対象外とする |
| $BadClusの専用容量集計 | 通常DATAとして補完せずUnsupported | 管理領域としての算入／除外方針を根拠とともに定義し、一般ファイル容量とは分離する |
| 大量の拡張レコード | 明示上限256で個別ファイル1件が解決。全件走査にはLimitExceededが残る | 残る必要件数と理由を診断し、有限の上限と超過時の未解決方針を確定する |
| 圧縮・Sparse等のライブ容量 | 公開画像・メモリ画像の独立照合済み。圧縮の実ファイル1件はWindows APIと両容量一致 | Sparse等の未確認条件を独立照合する。合成テストや1件の一致から全形式の対応を推定しない |

未解決39件という件数だけで全件の理由や容量を確定しない。未解決を0バイトへ変換しない。
当面はflags差の解釈の監査を優先し、統計層の新規実装は保留する。

現物で出たエラーを通すためのflags例外追加や上限引き上げを先に行わない。
元のextentメタデータを保持したまま、ストリーム全体の設定・extentごとのmapping・
容量検証に必要な情報を分けて、フィールドごとの有効範囲を定義する。
未確定の組み合わせは容量不明のまま扱う。

テストは「今回通したい値」だけから生成しない。
公開仕様の境界値、独立した解析器／公開データとの照合、検査用一時ファイルとWindows APIの
独立照合を組み合わせ、どこまでが確認済みかを各規則に対応づける。
本番ボリュームへの書き込み・修復・強制flushは行わない。

## 2026-10-12の実装照合

参照版はLinux v6.12とntfs-3g 2022.10.3。可変のmasterではなく以下のタグ付き資料を基準とする。

| 対象 | 参照箇所 | 確認した事実と採用範囲 |
|---|---|---|
| フィールド幅 | NTFS3 ntfs.h: ATTR_NONRESIDENT、ntfs-3g layout.h: ATTR_RECORD | 両者ともoffset 34は1 byte、35..39は予約5 byte。パーサーは別々の所有する値として保持 |
| 圧縮単位の有効範囲 | NTFS3 attrib.c: attr_is_frame_compressed（1434..1457）、attr_load_runs_vcn（1229..1267） | 圧縮単位はprimary segmentだけが有効。継続のmappingはVCNとmapping pairsから取得。結合後のStorageには先頭値を設定 |
| 初期化 | ntfs-3g attrib.c: ntfs_attr_open、ntfs_attr_init | 最初の属性からサイズと圧縮設定を初期化。圧縮形式の対応制限は実装固有であり、すべてをパーサーの構造制約へ転用しない |
| Sparseビットの更新 | ntfs-3g attrib.c: ntfs_attr_update_meta（5543..5645） | 継続extentでは状態更新を行わず、先頭でSparseを設定／解除し容量欄を更新する。全extentのSparse一致は要求できない |

Sparse差への対応は、この更新処理から導いた容量解析上の判断であり、Microsoftの形式保証ではない。
先頭extentのflagsとサイズ欄をストリームの設定として使い、継続のSparseビットから
サイズ欄を選び直したり、flagsをORして先頭を書き換えたりしない。
元のflagsは各属性に保持する。Sparse以外の扱いは下記の圧縮ビット差監査を参照。
全extentのVCN・参照・物理境界・容量とrun合計の照合、および取得後の変更検査は維持する。
先頭が非Sparse、継続がSparseでも、run合計が先頭の割り当て容量と合わなければInvalidAssembly。
差を許容することと、容量の不整合を補正することは別であり、欠落分を0として補完しない。
合成テストはSparse差の両方向、名前付きDATA、元データ保持、他ビットの差の拒否、
容量不一致・VCN欠損・物理境界・再検証中の変更を含む。NIST画像にはこの差の独立期待例がなく、
公開画像の既存照合が成功しても、この組み合わせの独立照合済みとは扱わない。

容量解析は圧縮単位を使ったshiftや解凍を行わない。パーサーはbyteの全範囲を保持し、
値を保持できることを、その圧縮形式の解凍対応や構造全体の妥当性保証とは扱わない。
結合器は全extentの物理run合計・論理容量・VCN連続性を検証する。
Storageと元の各NonResidentAttributeを分離し、継続値を先頭値で上書きしない。

テストは予約領域非ゼロ、byte境界、継続値の省略／相違、VCN欠落、容量不整合、
フラグ差の未対応分類、分類前の変更検出を含む。
既存のSHA-256固定NIST公開データ7ケースも再検証する。
このコーパス検証はWindowsの実ボリュームでの割り当て容量照合を代替しない。

## 圧縮ビット差の追加監査

2026-10-12、Linux NTFS3 v6.12のattr_is_frame_compressed、attr_load_runs_vcnと、
ntfs-3g 2022.10.3のntfs_attr_open、ntfs_attr_map_whole_runlistを再確認した。
前者は先頭extentの圧縮状態を参照し、継続のmapping pairsは別経路で取得する。
後者は先頭でストリーム設定を初期化し、VCN順にmapping pairsを結合する。
これらの読み取り経路には、全extentのflagsを同値とする検査は見当たらない。
ただし、検査がないことと、すべてのflags差が有効な形式であることを同一視しない。

NTFS3のattr_set_compress（2468..2530）は先頭の圧縮設定を変更するが、
非residentで論理サイズが非ゼロのファイルを拒否する。この関数だけを根拠に、
非空の複数extentに見られたCompressed→0の差が状態更新で生じるとは説明できない。
ntfs-3gの圧縮ストリーム初期化でも、空ストリームに限定した状態更新と形式チェックがある。
Sparseの場合に確認した先頭だけでのビット更新と、同じ根拠として扱わない。

この段階では圧縮ビット差をUnsupportedとして保持し、Windows API照合を追加した。
その実機診断で、先頭Compressed・継続0のファイルをWindowsが圧縮ありと報告し、
論理サイズ4,517,414バイト・割り当て容量1,245,184バイトを返した。
これはファイル全体の圧縮状態の観測であり、NTFS解析容量との一致や全形式の正当性の証明ではない。

OSSの先頭設定と継続mappingを分ける読み取り構成と、この観測を組み合わせた推論として、
容量解析に限り、先頭の圧縮形式（flags下位8ビット）が1の場合に継続の圧縮ビット省略を許容する。
Sparse差の許容と併用できるが、暗号化・別の圧縮形式・未知ビットの差は引き続き拒否する。
先頭が非圧縮で継続だけが圧縮の場合も未対応。特定の番号・容量・VCNで例外を分岐しない。
先頭のStorageと容量欄を使い、全runの物理容量との一致・VCN・参照・ボリューム境界・変更検査を維持する。
圧縮データの解凍やフレームの正当性検査を追加したわけではない。
省略された設定を元の属性へ書き戻さず、未解決・不整合は部分容量へ変換しない。
合成テストと既存の独立公開画像照合を実行するが、公開画像にこの差の独立期待例はない。
2026-10-12、対応後に同じ実ファイルを参照から開いて再照合した。
NTFSとWindowsの双方で論理サイズ4,517,414バイト、割り当て容量1,245,184バイトとなり、
logical-match・allocated-match・matchはすべてTrueだった。
この1件で圧縮ビット省略のある複数extentの容量一致を確認した。変更後の全件走査、
Sparseのライブ照合、他の圧縮条件の検証は残る。時点スナップショットの保証ではない。
一次資料の処理を転記せず、観測・確認した事実・そこからの推論を分けて記録する。

## OSS実装の参照方針

Microsoftの公開説明で不足する部分はLinuxのNTFS実装（NTFS3）とntfs-3gを比較する。
これらの実装の挙動をMicrosoftの保証する仕様とは扱わない。

- 参照する版／commit、ファイル、対象フィールド、有効範囲、確認できた事実と推論を記録する。
- コードやコメント、テストを転記せず、C#への逐語的な移植も行わない。
- 形式上の事実を自分の言葉で記述し、その記述と独立した期待値から実装・テストを作る。
- GPLライブラリを製品へ組み込む場合は、この調査方針とは別にライセンス条件を確認する。
- ソースを読んだ担当が実装するため、厳密なクリーンルーム開発を行ったとは主張しない。

参照したという理由だけで製品全体へGPLが適用されるとは扱わないが、
著作権で保護される表現の流用と、形式上の事実の確認は区別する。
これは調査手順の方針であり、個別のコードについて法的な適合性を保証するものではない。
