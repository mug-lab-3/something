# スキャン履歴とフォルダ変動

保存エンジンは2026-10-14にDuckDBのファイル方式へ変更する方針を決定した。
[採用理由と切り替え要件](decisions/20261014-duckdb-storage.md) を参照。
アプリ・診断CLIのDuckDBへの切り替えを実装した。保持ルール・期間比較・世代公開の意味は維持する。
旧SQLite・初期DuckDB履歴の自動移行・削除は行わず、ステップ計測を含む新形式は別ファイル `catalog-v2.duckdb` を使う。

2026-10-14。スキャンごとのDBをやめ、全ドライブ・全世代を1つのDuckDBファイルへ保存する。過去24時間・7日・365日の変動一覧と増加／減少／変動量ランキングを照会できる基盤を実装した。変動表示のUIは次の作業。

## 保存構成

- 保存先は `%LOCALAPPDATA%\Something\History\catalog-v2.duckdb`。全観測・一覧用データ・履歴を含む共有DB。DuckDBのトランザクションとWALを使用する。旧 `catalog.sqlite3` と `catalog.duckdb` は保持し、自動移行・削除しない。
- VolumeKeyはボリュームGUIDとNTFSシリアル番号。ドライブ文字だけで同一ディスクと判断しない。
- ScanIdごとに観測、MFT参照とシーケンス番号、可視名とDOS別名、名前付きストリーム、フォルダ集計、未解決状態を保持する。保持履歴の情報を削減しない。
- ライブスキャンはメモリ上で取得・集計した後、共有DBへ一度のトランザクションで保存する。メタデータと最新世代ポインターも同時に確定し、途中の結果を公開しない。共有DB全体をメモリDBの内容で置き換えない。
- 共有DBには、同時スキャンの予算から選んだ1〜2 GiBをDuckDBのmemory_limitとして適用する。共有エンジンの設定なので、読込接続は予算を再設定しない。アプリ・診断CLIの既定はファイル方式。CLIの明示的なメモリDBは診断用途として残す。
- 読み取り専用のScanStoreで、保存済みの世代をツリー・一覧・ランキングへ表示する。ネイティブ接続は同じ書き込みエンジンを共有するが、公開APIの書き込みを拒否する。通常の `--demo` は履歴を保存しない。明示的な `--demo-history <専用ディレクトリ>` は合成データのみを保存する。

## 開発中の旧データ

未リリースのため旧形式のデータ移行は実装しない。旧 `snapshots\<scan-id>.sqlite3` を読み込む処理、共有DBへの取り込み、移行後の削除、移行状態の管理は持たない。

今回のSQLiteからの切り替えは、同じHistoryディレクトリ内に別名のDuckDBを作る。旧 `catalog.sqlite3` とsnapshotファイルは保持し、読込・自動移行・自動削除をしない。既存記録の引き継ぎは保証しない。今後のDuckDBスキーマが未知・非対応の場合は自動変換せずエラーにする。その場合はアプリを閉じ、旧Historyディレクトリを別名に退避して空のディレクトリで再スキャンする。

EF Coreのチェックイン済みマイグレーションは、新しいDBのスキーマ構築のために維持する。過去スキャンのデータ変換とは別の処理。

## 保持ルール

1. 現在時刻から7日（168時間）未満の完了記録はすべて保持する。
2. それ以前は、ボリュームごと・記録時のローカル日付ごとの最後の1回を保持する。
3. 同日の最終記録がまだ7日未満なら、それより古い同日の記録は残さない。
4. 7日ちょうどは整理対象。同じ終了UTCはスキャンIDで決定的に選ぶ。
5. 新しいスキャンの保存成功後に整理する。起動時の整理、バックグラウンド監視、定期実行は行わない。次の保存まで既存履歴を保持する。

日付とUTCオフセットは記録時に固定する。タイムゾーン変更で振り分け直さない。最大保持日数は設定していないため365日前の記録も日次で保持できるが、記録開始より前の履歴は生成できない。

整理対象を先に非公開にし、世代の一覧行・名前・ストリーム・集計・観測・メタデータを同じトランザクションで明示的に削除する。DuckDBの物理外部キー・カスケードには依存しない。閲覧中の世代は `leases\<scan-id>.lock` の共有読み取りハンドルで保護する。別のアプリインスタンスにも有効で、閉じた後に削除を再試行する。長期間の読み取りトランザクションで閲覧世代を保護しない。同じプロセス内の別Archiveでも公開・整理を調停する。DuckDBファイルを複数のアプリプロセスで同時に開く運用は対象外。ファイルの縮小・長期運用時の容量は別途検証する。

## 期間比較API

`FolderHistoryService.ReadChangesAsync` はワーカースレッドで `ScanHistoryArchive.ReadFolderChanges` を実行する。期間は `Last24Hours`、`Last7Days`、`Last365Days`。基準時刻は省略時に現在UTC。

- 現在側は基準時刻以前の最新完了記録、比較元は期間開始時刻以前の最新の保持記録を選ぶ。未来の記録は使わない。
- 要求した期間開始時刻と実際の両端のScanId・日時を返す。日次間引きやスキャン間隔で要求期間より長くなる場合がある。例えば24時間前の記録が残っていなければ、それより前の記録を使う。古い記録を正確な24時間前と表示しない。
- 現在側がない、比較元がない、期間内に現在側の記録がない場合は、専用の状態を返す。ゼロの変動として表示しない。
- フォルダは同じVolumeKey内のMFT番号＋シーケンス番号で照合する。改名・移動に備えて両時点の相対パスを返す。シーケンスが違えば別の観測で、同一フォルダとして差を計算しない。
- サイズはUIと同じ「無名DATAを可視名ごとに計上した配下の割り当て容量」。ハードリンクは名前ごとに数える。ルートとNTFS管理フォルダは除外する。親子の値は重複するのでランキングを合計しない。
- 両端が確定している場合に `AllocatedDelta = After - Before` を計算する。符号付きBigIntegerで全UInt128範囲を保持する。
- 片方だけのフォルダは `NotObservedBefore/After` とし、新規・削除と断定しない。未解決容量、未観測ディレクトリ、所属不明容量がある場合も差を確定せず `UncertainCapacity` とする。古い集計方式を現在の方式に混ぜない。
- `Folders` は比較対象一覧、`ChangedFolders` は確定した非ゼロの変動一覧、`UncertainFolders` は比較不能一覧。`Rank(Growth/Shrinkage/Magnitude, count)` は確定した増加／減少／絶対変動量順のランキング。

これは期間両端の差であり、期間内の全変動の累積・一時的なピークではない。スキャンは楽観的観測で、時点スナップショットではない。USN連続性は未検証のためシーケンス番号の周回をまたぐ同一性を保証しない。

## スキャンの進捗表示

各ステップの処理時間は `scan_timing`（ScanIdごとの計画バージョン・全ステップ数・合計ticks）と `scan_step_timing`（ScanId・時系列Ordinalごとのステップ番号・処理種別・再試行番号・経過ticks）へ保存する。1 tickは100ns。再試行は別区間として記録し、単調増加する時計で区切った各区間の合計が全体時間と一致することを保存前に検証する。メモリ待機はステップ0、取得はステップ1。DB待ち・保存先準備はファイル保存区間、公開結果の読み込みは最後の確定・整理区間に含める。UI通知がなくても計測する。

コミットと履歴整理も測定するため、観測・一覧データの保存後に計測結果を少量の行として別トランザクションで一括保存する。合計時間も履歴のElapsedTicksへ反映する。計測結果そのものの最終書き込み、スキャン前のボリュームを開く処理、UIの表示・一覧クエリは計測に含めない。プロセスが計測の最終保存前に停止した場合は、観測は公開済みでも計測行は存在しない。行がないことを0秒の計測とは扱わない。

保存済みの計測は履歴を開いた際に読み戻し、カードの `スキャン済み (53.4秒)` に合計時間を表示する。世代の整理・削除時は計測行も明示的に削除する。未リリースで互換性不要という方針に従い、旧DBの変換処理は持たず、format version 2の新しいファイルで開始する。

カードとステータスに、スキャン開始からの通しステップ番号と全ステップ数も表示する。履歴付きは14ステップ（取得1、集計5、保存7、履歴整理1）、履歴を残さないデモは最後の整理を除く13ステップ。例えば `8/14 · フォルダ容量を保存中 65%`。待機中は準備中と表示する。ステップ番号は所要時間による重み付けではないため、`8/14` を全体の57%完了と換算しない。各ステップの割合が取れないDB処理にも番号・処理名・回転表示は出す。

集計・保存の進捗率は、処理段階ごとの件数比として表示する。フォルダ抽出とファイル集計は観測レコード数、サブフォルダ集計と容量保存は対象フォルダ数、ファイル保存とフォルダ名収集の走査は観測レコード数を分母にする。保存件数はトランザクション内で処理した件数であり、コミット済み件数ではない。段階が変われば割合もリセットされ、全体の所要時間の割合や残り時間の推定ではない。

階層構築・データ反映・参照整合性検証・一覧用データ生成・コミット・履歴整理は件数比を取得できないため、処理名と回転表示を出す。全体の完了は保存確定後に通知する。進捗通知は同期のワーカー側コールバックで、通常250ms間隔、段階の開始・終了は即時通知する。進捗のための追加DB照会・中間コミット・ファイル出力は行わない。

## 検証と残る作業

合成データで旧形式の拒否と既存ファイルの保持、保存トランザクションのロールバック、別インスタンスの閲覧保護、保持境界、各期間の選択、未来・欠測・参照再利用・改名・未解決容量・ランキングを確認する。ネイティブのデモUIで履歴切り替えと再読み込みも確認する。

変動UI、実ドライブの複数世代での性能測定、バックアップ、保存容量の管理は今後の作業。DuckDBの評価は保留課題のまま。大量の詳細履歴を日次で残すため、保存量はファイル数と保持日数に比例する。
