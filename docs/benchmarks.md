# 性能計測

## 測る範囲を分ける

取得だけの時間、バッファを含む時間、集計、永続化と公開、照会、UI 描画を分けて比較します。DB の列や未解決状態を省いた方式と、同じ事実を保存する方式の数値をそのまま比べません。キャッシュ、反復数、行数、世代数、変更率、メモリ予算も結果と一緒に記録します。

ライブ走査は[診断 CLI](diagnostics.md)の `--scan`、保存とフォルダ集計は `--top5` で確認できます。ライブ出力は対象ボリュームの情報を含むため、公開性能資料には合成データの測定を使います。

## ストレージ比較 CLI

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --engine compare-browser --count 1200000 --repeats 3 --budget-mib 1024 --output artifacts/storage-comparison.json
```

`compare-browser` は SQLite、一覧構造を追加した SQLite、DuckDB の最適化ファイル方式を別プロセスで比較します。各方式で保存事実・可視一覧・照会結果の一致を確認します。候補の全比較には `--engine all`、個別には `sqlite` / `sqlite-browser` / `duckdb` / `duckdb-native` / `duckdb-memory` を指定します。

このツールは比較用に固定した構造も含みます。現在のアプリ全体や共有履歴の性能を直接測るものではありません。結果 JSON と生成 DB は `artifacts` 等の追跡対象外に置きます。

## 採用時の比較記録

2026-10-14 の合成 120 万件 + ルート・二世代、予算 1 GiB、各方式三回の中央値です。照会は各実行で十五回のウォーム計測を行いました。個別 PC のパス・ファイル内容は用いていません。

| 項目 | SQLite | 一覧構造あり SQLite | 最適化 DuckDB・ファイル |
| --- | ---: | ---: | ---: |
| 二世代の保存完了 | 35.34 秒 | 47.70 秒 | 28.78 秒 |
| ルート一覧の初回ページ | 495.52 ms | 0.81 ms | 9.71 ms |
| ルートの件数 | 392.06 ms | 4.32 ms | 0.55 ms |
| 小フォルダの一覧 | 0.030 ms | 0.030 ms | 1.17 ms |
| 容量上位 20 件 | 32.83 ms | 34.63 ms | 3.35 ms |
| 増加量上位 20 件 | 182.24 ms | 179.51 ms | 11.28 ms |
| 最終 DB サイズ | 2097.8 MiB | 2665.8 MiB | 699.3 MiB |

全九回で保存列・可視一覧の SHA-256 と七種類の照会結果を照合しました。一覧構造をそろえた SQLite の点照会は DuckDB より速く、DuckDB は保存・容量・集計で有利でした。この差にはスキーマ・型・挿入経路の効果を含み、エンジンだけの効果とは主張しません。現在の版や異なる PC の速度を保証する数値ではありません。

同日の別反復では、オンメモリ方式の二世代保存と書き出しは 2 GiB 予算で 53.34 秒、ファイル方式は 34.36 秒でした。このため通常の履歴はファイル方式を採用しています。上表と別の反復なので、両者を使った改善率は計算しません。

## 共有履歴の評価

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --history-dedup --count 100000 --generations 3 --mode production --output artifacts/history-sharing.json
```

本体の共有履歴経路について、初回・未変更・変更ありの保存を比較します。`--mode all` は全件方式と比較用の共有候補も実行します。保存事実・一覧・照会・先頭世代削除後の残存履歴の一致を確認し、保存容量の削減だけで正しさを判断しません。

採用時の 10 万件・三世代・約 1% 変更の予備測定では、共有形式の最終 DB は 63.5 MiB、全件形式は 123.0 MiB でした。共有形式の初回 / 未変更保存は 2.222 / 0.686 秒、全件形式は 2.178 / 2.128 秒です。入力生成・集計を除いた単回の保存測定であり、長期運用や大規模履歴の保証ではありません。

## アプリ経路の計測

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --app-paths --count 2000000 --generations 30 --repeats 3 --budget-mib 1024 --output artifacts/app-paths.json
```

`--app-paths` は本体の `ScanHistoryArchive` / `ScanStore` を通して、次の処理を計測します。

- 世代ごとの保存（段階別時間を含む）
- 履歴一覧、世代を開く処理、ルート一覧
- フォルダ分析、全件読み込み、表示フィルター投影、期間比較

既定の `deep` 形状は、1 フォルダに 8 フォルダを入れ子にして、表示パスに深さを持たせます。各照会の結果チェックサムを出力するので、高速化の前後で同じ値になることを確認します。時計を固定しているため、保持整理で世代は退役しません。プロセスのピーク使用量も出力します。

[高速化方針](decisions/20261019-storage-performance.md)の標準条件は、200 万件・30 世代・DuckDB 予算 1 GiB です。予算はアプリの最低値で、開発機の空きメモリに合わせて引き上げません。

### 変更前の状態（2026-10-19）

予算 1 GiB では、変更前の共有履歴は 200 万件・50 万件・100 万件の初回保存がいずれもメモリ不足で失敗しました。30 万件は 3 世代とも成功しました。原因は TEMP 表への Appender 投入と、ディスクへの一時退避が無効なことです。参考として、予算 4 GiB でも 200 万件の 2 世代目の差分比較が失敗しました。予算 16 GiB での 200 万件の初回保存は 33.2 秒（確定 12.0 秒、関係検証 11.3 秒、投入 4.7 秒）でしたが、この予算は標準条件ではありません。

### R1・R2

標準条件は変更前のコードで完了しないため、予算 1 GiB で動く 30 万件・6 世代・五回反復のウォーム中央値で比較しました。

| 項目 | 変更前 | R1・R2 後 |
| --- | ---: | ---: |
| 期間比較 | 557.4 ms | 383.1 ms |
| フォルダ分析（全件） | 333.4 ms | 332.8 ms |
| 表示フィルター投影 | 1113.4 ms | 892.4 ms |
| 全件読み込み | 517.4 ms | 558.1 ms |

期間比較は、集計の二重読み込みを除いた分だけ短縮しました。合成データの階層は深さ 5 程度で、パス構築の改善（R2）はこの規模では誤差の範囲です。表示フィルター投影と全件読み込みはコードを変えておらず、差は反復間のばらつきです。照会結果のチェックサムは変更前と一致しました。

### 形式 5（所属表・PK なし・流し読み照合）

2026-10-19 に標準条件（200 万件・`deep`・30 世代・予算 1 GiB・照会三回）で計測しました。30 世代すべてが再試行・ディスク退避なしで完了しました。

| 項目 | 変更前（予算 16 GiB、参考） | 形式 5（予算 1 GiB） |
| --- | ---: | ---: |
| 初回保存 | 33.2 秒 | 11.9 秒 |
| 2 世代目以降の保存 | 9.0〜15.2 秒（3 世代まで） | 4.8〜8.1 秒（30 世代、履歴量で増えない） |
| 確定直前の DuckDB 使用量（初回） | 3.3 GiB | 0.3 GiB |
| 初回の書き込み量 | 705 MiB | 98 MiB |
| 変更なし / 約 1% / 約 10% 変更の書き込み量 | 39 / 193 MiB / — | 4〜19 / 35〜53 / 57〜67 MiB |
| DB サイズ（3 世代 / 30 世代） | 916 MiB / — | 119 MiB / 840 MiB |

変更前は予算 1 GiB で 50 万件以上を保存できないため、比較用の値は予算 16 GiB での参考値です。初回保存の確定前メモリ削減の主因は、PK の廃止と、`preserve_insertion_order=true` による確定前の行グループ書き出しです。3 世代での照会結果のチェックサムは、変更前とすべて一致しました。

照会は 30 世代時点で、ルート一覧 153 ms、フォルダ分析 1.4 秒、全件読み込み 3.3 秒、表示フィルター投影 5.7 秒、期間比較 3.1 秒（いずれもウォーム中央値）でした。照会経路の高速化は次の段階で扱います。プロセスのピーク使用量は 5.1 GiB で、走査バッファと照会結果の .NET 側展開が主です（M5）。

### 読み込み経路（形式 5）

照会だけを繰り返し測るため、`--database <dir>` で履歴ディレクトリを残し、既存の履歴があれば保存を省略します。`--profile true` は、同じ SQL を生の読み取りで計測した時間と `EXPLAIN ANALYZE` の結果（`<DB>.plans.txt`）を出力します。

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --app-paths --count 2000000 --generations 30 --budget-mib 1024 --database artifacts/bench-db-2m30
dotnet run --project tools/Something.StorageCompare -c Release -- --app-paths --repeats 5 --budget-mib 1024 --database artifacts/bench-db-2m30 --profile true
```

2026-10-20 に、同じ 200 万件・30 世代の DB に対して五回反復のウォーム中央値で比較しました（括弧内は初回）。

| 項目 | 変更前 | 変更後 |
| --- | ---: | ---: |
| ルート一覧の初回ページ | 154 ms（216） | 105 ms（175） |
| フォルダ分析 | 1290 ms（2267） | 1040 ms（1748） |
| 表示用フォルダ属性 | 1081 ms（1172） | 186 ms（214） |
| 全件読み込み | 3415 ms（3550） | 1677 ms（1880） |
| 表示フィルター投影 | 6165 ms（6076） | 3281 ms（3221） |
| 期間比較 | 2866 ms（3075） | 2078 ms（2204） |

照会結果のチェックサムは変更前とすべて一致しました。同じ PC でも反復間で 10〜20% のばらつきがあります。

計測で分かった内訳と対策は次のとおりです。

- 全件読み込みは、DuckDB 内の SQL 実行が約 1.5 秒、EF のエンティティ変換が約 1.6 秒でした。DuckDB では型付きの列を直接読む方式にしました。
- 表示用フォルダ属性は、EF の `Include` による結合をやめ、ディレクトリと名前の二つの順序付き読み取りを突き合わせる方式にしました。
- フォルダ集計とフォルダ構造の辞書を `ImmutableDictionary` から `FrozenDictionary` に変えました。20 万件で構築が 150 ms → 16 ms、参照が約 3.5 倍速くなります。
- フォルダ一覧は、全世代の集計状態表を走査せず、一覧中のフォルダが参照する版だけを読みます。履歴が増えても読む範囲が増えません。
- DuckDB.NET の読み取りは 1 値あたり約 30 ns かかります。200 万件の全件読み込みは約 5,000 万値を読むため、残りの時間の大半はこの読み取り数で決まります。

### 形式 6（整数キー）

2026-10-20 に、形式 5 と同じ標準条件（200 万件・`deep`・30 世代・予算 1 GiB）で計測しました。30 世代すべてが再試行・ディスク退避なしで完了し、照会結果のチェックサムは形式 5 と一致しました。

| 項目 | 形式 5 | 形式 6 |
| --- | ---: | ---: |
| DB サイズ（30 世代） | 840 MiB | 498 MiB |
| 初回保存 | 11.9 秒 | 10.8 秒 |
| 2 世代目以降の保存 | 4.8〜8.1 秒 | 4.3〜7.3 秒 |
| 変更がほぼない世代（同一・1 ファイル変更）の書き込み量 | 17〜20 MiB | 6〜9 MiB |
| 約 1% 変更の世代の書き込み量 | 35〜62 MiB | 30〜47 MiB |
| 約 10% 変更の世代の書き込み量 | 60〜67 MiB | 44〜52 MiB |

照会（五回反復のウォーム中央値、形式 5 は読み込み経路の改善後の値）は次のとおりです。

| 項目 | 形式 5 | 形式 6 |
| --- | ---: | ---: |
| ルート一覧の初回ページ | 105 ms | 106 ms |
| フォルダ分析 | 1040 ms | 1058 ms |
| 表示用フォルダ属性 | 186 ms | 149 ms |
| 全件読み込み | 1677 ms | 1469 ms |
| 表示フィルター投影 | 3281 ms | 2754 ms |
| 期間比較 | 2078 ms | 1870 ms |

整数キーの主な効果は容量と書き込み量です。照会時間は、.NET 側で値を読み取るコストが大半を占めるため、改善は 0〜16% にとどまりました。

### .NET 側のメモリ

`--managed-memory true` は、走査バッファ作成中のヒープ最大値（5 ms 間隔の標本）、作成後に GC してから残る量、保存中のヒープ最大値を世代ごとに出力します。

2026-10-20 に 200 万件の初回世代で計測しました。走査バッファは 1 観測あたり 506 バイト（約 965 MiB）を保持し、保存中は比較用の配列や書き込み用エンティティで約 370 MiB 上乗せされます。重複検出をレコード範囲のビット列に替え、観測リストを MFT のレコード数（上限 400 万件）で確保した結果、作成中の最大値は 1,279 MiB → 1,226 MiB、保持量と保存時間は変わりませんでした。残りの大半は観測ごとのオブジェクト構造で、削減には走査バッファの表現の変更が必要です。

## 結果を評価する基準

- 処理件数と保存内容が一致し、参照再利用や未解決状態も保持されていること。
- 初回とウォーム、未変更と変更あり、通常フォルダと巨大フォルダを分けること。
- 累積割り当て、保持メモリ、ピーク working set、DuckDB の上限を混同しないこと。
- 失敗・キャンセル・OOM を成功結果から除外するだけでなく、失敗条件として記録すること。
- 保存・照会の高速化と引き換えに、履歴比較や保持整理の正しさを失っていないこと。

性能上の判断と保守性の境界は[保存エンジンの選定](decisions/20261014-duckdb-storage.md)を参照してください。
