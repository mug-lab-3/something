# 性能計測

## 測る範囲を分ける

取得だけの時間、バッファの作成を含む時間、集計、保存と公開、照会、UI の描画は、分けて比較します。DB の列や未解決の状態を省いた方式と、同じ情報をすべて保存する方式の数値を、そのまま比べることはしません。キャッシュの有無、反復回数、行数、世代数、変更率、メモリ予算も、結果と一緒に記録します。

実際のボリュームの走査は[診断 CLI](diagnostics.md) の `--scan` で、保存とフォルダーの集計は `--top5` で確認できます。実際のボリュームの出力には、そのボリュームの情報が含まれるため、公開する性能の資料には合成データでの測定結果を使います。

## ストレージ比較 CLI

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --engine compare-browser --count 1200000 --repeats 3 --budget-mib 1024 --output artifacts/storage-comparison.json
```

`compare-browser` は、SQLite、一覧構造を追加した SQLite、DuckDB の最適化したファイル方式を、別々のプロセスで比較します。各方式で、保存した内容・表示される一覧・照会結果が一致することを確認します。候補の全比較には `--engine all`、個別には `sqlite` / `sqlite-browser` / `duckdb` / `duckdb-native` / `duckdb-memory` を指定します。

このツールには、比較のために固定した構造も含まれます。現在のアプリ全体や共有履歴の性能を直接測るものではありません。結果の JSON と生成した DB は、`artifacts` など Git で管理しない場所に置きます。

## 採用時の比較記録

2026-10-14 に、合成 120 万件とルート・2 世代、予算 1 GiB で、各方式 3 回実行した中央値です。照会は、各実行で 15 回のウォーム計測を行いました。特定の PC のパスやファイルの内容は使っていません。

| 項目 | SQLite | 一覧構造あり SQLite | 最適化 DuckDB・ファイル |
| --- | ---: | ---: | ---: |
| 2 世代の保存完了 | 35.34 秒 | 47.70 秒 | 28.78 秒 |
| ルート一覧の初回ページ | 495.52 ms | 0.81 ms | 9.71 ms |
| ルートの件数 | 392.06 ms | 4.32 ms | 0.55 ms |
| 小フォルダーの一覧 | 0.030 ms | 0.030 ms | 1.17 ms |
| 容量上位 20 件 | 32.83 ms | 34.63 ms | 3.35 ms |
| 増加量上位 20 件 | 182.24 ms | 179.51 ms | 11.28 ms |
| 最終 DB サイズ | 2097.8 MiB | 2665.8 MiB | 699.3 MiB |

全 9 回の実行で、保存した列と表示される一覧の SHA-256、7 種類の照会結果を照合しました。一覧構造をそろえた SQLite は点照会で DuckDB より速く、DuckDB は保存時間・容量・集計で有利でした。この差にはスキーマ・型・挿入方法の違いも含まれており、エンジンだけの差とは言えません。現在のバージョンや別の PC での速度を保証する数値ではありません。

同じ日の別の計測では、オンメモリ方式の 2 世代の保存と書き出しが予算 2 GiB で 53.34 秒、ファイル方式が 34.36 秒でした。このため、通常の履歴にはファイル方式を採用しています。上の表とは別の計測なので、両者から改善率は計算しません。

## 共有履歴の評価

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --history-dedup --count 100000 --generations 3 --mode production --output artifacts/history-sharing.json
```

アプリ本体の共有履歴について、初回・変更なし・変更ありの保存を比較します。`--mode all` を指定すると、全件を保存する方式と、比較用の共有方式の候補も実行します。保存した内容・一覧・照会結果・最初の世代を削除したあとに残る履歴が一致することを確認し、容量が減ったことだけで正しさを判断しません。

採用時に 10 万件・3 世代・約 1% 変更で予備的に測ったところ、最終的な DB は共有形式が 63.5 MiB、全件形式が 123.0 MiB でした。初回と変更なしの保存は、共有形式が 2.222 秒と 0.686 秒、全件形式が 2.178 秒と 2.128 秒です。入力の生成と集計を除いた 1 回だけの保存の測定であり、長期の運用や大規模な履歴での性能を保証するものではありません。

## アプリ経路の計測

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --app-paths --count 2000000 --generations 30 --repeats 3 --budget-mib 1024 --output artifacts/app-paths.json
```

`--app-paths` は、アプリ本体の `ScanHistoryArchive` / `ScanStore` を通して、次の処理を計測します。

- 世代ごとの保存（段階別時間を含む）
- 履歴一覧、世代を開く処理、ルート一覧
- フォルダー分析、全件読み込み、表示フィルター投影、期間比較

既定の `deep` 形状では、1 つのフォルダーに 8 つのフォルダーを入れ子にして、パスに深さを持たせます。各照会の結果のチェックサムを出力するので、高速化の前後で同じ値になることを確認します。時計を固定しているため、保持の整理で世代が退役することはありません。プロセスのピークのメモリ使用量も出力します。

高速化の計測の標準条件は、200 万件・30 世代・DuckDB の予算 1 GiB です。この予算はアプリの最低値で、開発機の空きメモリに合わせて引き上げることはしません。

### 変更前の状態（2026-10-19）

予算 1 GiB では、変更前の共有履歴は、200 万件・50 万件・100 万件のいずれも初回の保存がメモリ不足で失敗しました。30 万件は 3 世代とも成功しました。原因は、TEMP 表へ Appender で投入していたことと、ディスクへの一時退避が無効だったことです。参考として、予算 4 GiB でも 200 万件の 2 世代目の差分比較が失敗しました。予算 16 GiB での 200 万件の初回保存は 33.2 秒（確定 12.0 秒、関係検証 11.3 秒、投入 4.7 秒）でしたが、この予算は標準条件ではありません。

### 照会の改善（集計の二重読み込みとパスの構築）

標準条件では変更前のコードが完了しないため、予算 1 GiB で動く 30 万件・6 世代で、5 回反復したウォーム中央値を比較しました。

| 項目 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 期間比較 | 557.4 ms | 383.1 ms |
| フォルダー分析（全件） | 333.4 ms | 332.8 ms |
| 表示フィルター投影 | 1113.4 ms | 892.4 ms |
| 全件読み込み | 517.4 ms | 558.1 ms |

期間比較は、集計の二重読み込みをなくした分だけ短くなりました。合成データの階層は深さ 5 程度のため、パスの構築の改善はこの規模では誤差の範囲です。表示フィルター投影と全件読み込みはコードを変えておらず、差は反復ごとのばらつきです。照会結果のチェックサムは変更前と一致しました。

### 形式 5（所属表・PK なし・流し読み照合）

2026-10-19 に、標準条件（200 万件・`deep`・30 世代・予算 1 GiB・照会 3 回）で計測しました。30 世代すべてが、再試行もディスク退避もなしで完了しました。

| 項目 | 変更前（予算 16 GiB、参考） | 形式 5（予算 1 GiB） |
| --- | ---: | ---: |
| 初回保存 | 33.2 秒 | 11.9 秒 |
| 2 世代目以降の保存 | 9.0〜15.2 秒（3 世代まで） | 4.8〜8.1 秒（30 世代、履歴量で増えない） |
| 確定直前の DuckDB 使用量（初回） | 3.3 GiB | 0.3 GiB |
| 初回の書き込み量 | 705 MiB | 98 MiB |
| 変更なし / 約 1% / 約 10% 変更の書き込み量 | 39 / 193 MiB / — | 4〜19 / 35〜53 / 57〜67 MiB |
| DB サイズ（3 世代 / 30 世代） | 916 MiB / — | 119 MiB / 840 MiB |

変更前は予算 1 GiB で 50 万件以上を保存できないため、比較用の値は予算 16 GiB での参考値です。初回の保存で確定前のメモリが減った主な理由は、PK をなくしたことと、`preserve_insertion_order=true` によって確定前に行グループを書き出すようになったことです。3 世代での照会結果のチェックサムは、変更前とすべて一致しました。

30 世代の時点の照会は、ルート一覧 153 ms、フォルダー分析 1.4 秒、全件読み込み 3.3 秒、表示フィルター投影 5.7 秒、期間比較 3.1 秒（いずれもウォーム中央値）でした。照会の高速化は、次の「読み込み経路」で扱っています。プロセスのピークのメモリ使用量は 5.1 GiB で、その大半は走査バッファと、照会結果を .NET 側に展開したものです。

### 読み込み経路（形式 5）

照会だけを繰り返し測れるように、`--database <dir>` で履歴のディレクトリを残し、既存の履歴があれば保存を省きます。`--profile true` を指定すると、同じ SQL を直接読み取って計測した時間と、`EXPLAIN ANALYZE` の結果（`<DB>.plans.txt`）を出力します。

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --app-paths --count 2000000 --generations 30 --budget-mib 1024 --database artifacts/bench-db-2m30
dotnet run --project tools/Something.StorageCompare -c Release -- --app-paths --repeats 5 --budget-mib 1024 --database artifacts/bench-db-2m30 --profile true
```

2026-10-20 に、同じ 200 万件・30 世代の DB で、5 回反復したウォーム中央値を比較しました（括弧内は初回）。

| 項目 | 変更前 | 変更後 |
| --- | ---: | ---: |
| ルート一覧の初回ページ | 154 ms（216） | 105 ms（175） |
| フォルダー分析 | 1290 ms（2267） | 1040 ms（1748） |
| 表示用フォルダー属性 | 1081 ms（1172） | 186 ms（214） |
| 全件読み込み | 3415 ms（3550） | 1677 ms（1880） |
| 表示フィルター投影 | 6165 ms（6076） | 3281 ms（3221） |
| 期間比較 | 2866 ms（3075） | 2078 ms（2204） |

照会結果のチェックサムは、変更前とすべて一致しました。同じ PC でも、反復ごとに 10〜20% のばらつきがあります。

計測で分かった内訳と対策は次のとおりです。

- 全件読み込みは、DuckDB 内の SQL 実行が約 1.5 秒、EF のエンティティ変換が約 1.6 秒でした。DuckDB では型付きの列を直接読む方式にしました。
- 表示用フォルダー属性は、EF の `Include` による結合をやめ、ディレクトリと名前を 2 つの順序付きの読み取りで突き合わせる方式にしました。
- フォルダー集計とフォルダー構造の辞書を `ImmutableDictionary` から `FrozenDictionary` に変えました。20 万件で構築が 150 ms → 16 ms、参照が約 3.5 倍速くなります。
- フォルダー一覧は、全世代の集計状態表を走査せず、一覧中のフォルダーが参照する版だけを読みます。履歴が増えても読む範囲が増えません。
- DuckDB.NET の読み取りは 1 値あたり約 30 ns かかります。200 万件の全件読み込みは約 5,000 万値を読むため、残りの時間の大半はこの読み取り数で決まります。

### 形式 6（整数キー）

2026-10-20 に、形式 5 と同じ標準条件（200 万件・`deep`・30 世代・予算 1 GiB）で計測しました。30 世代すべてが再試行もディスク退避もなしで完了し、照会結果のチェックサムは形式 5 と一致しました。

| 項目 | 形式 5 | 形式 6 |
| --- | ---: | ---: |
| DB サイズ（30 世代） | 840 MiB | 498 MiB |
| 初回保存 | 11.9 秒 | 10.8 秒 |
| 2 世代目以降の保存 | 4.8〜8.1 秒 | 4.3〜7.3 秒 |
| 変更がほぼない世代（同一・1 ファイル変更）の書き込み量 | 17〜20 MiB | 6〜9 MiB |
| 約 1% 変更の世代の書き込み量 | 35〜62 MiB | 30〜47 MiB |
| 約 10% 変更の世代の書き込み量 | 60〜67 MiB | 44〜52 MiB |

照会の時間（5 回反復したウォーム中央値。形式 5 は読み込み経路を改善したあとの値）は次のとおりです。

| 項目 | 形式 5 | 形式 6 |
| --- | ---: | ---: |
| ルート一覧の初回ページ | 105 ms | 106 ms |
| フォルダー分析 | 1040 ms | 1058 ms |
| 表示用フォルダー属性 | 186 ms | 149 ms |
| 全件読み込み | 1677 ms | 1469 ms |
| 表示フィルター投影 | 3281 ms | 2754 ms |
| 期間比較 | 2078 ms | 1870 ms |

整数キーにした主な効果は、容量と書き込み量の削減です。照会の時間は、.NET 側で値を読み取る処理が大半を占めるため、改善は 0〜16% にとどまりました。

### .NET 側のメモリ

`--managed-memory true` を指定すると、走査バッファの作成中のヒープの最大値（5 ms 間隔で採取）、作成後に GC してから残る量、保存中のヒープの最大値を、世代ごとに出力します。

2026-10-20 に 200 万件の初回世代で計測しました。走査バッファは 1 観測あたり 506 バイト（約 965 MiB）を保持し、保存中は比較用の配列や書き込み用エンティティで約 370 MiB 上乗せされます。重複検出をレコード範囲のビット列に替え、観測リストを MFT のレコード数（上限 400 万件）で確保した結果、作成中の最大値は 1,279 MiB → 1,226 MiB、保持量と保存時間は変わりませんでした。残りの大半は観測ごとのオブジェクト構造で、削減には走査バッファの表現の変更が必要です。

## 結果を評価する基準

- 処理した件数と保存した内容が一致し、参照の再利用や未解決の状態も保たれていること。
- 初回とウォーム、変更なしと変更あり、通常のフォルダーと巨大なフォルダーを分けて測ること。
- 累積の割り当て量、保持しているメモリ、ピークの working set、DuckDB の上限を混同しないこと。
- 失敗・キャンセル・OOM は、成功した結果から除くだけでなく、失敗した条件として記録すること。
- 保存・照会の高速化と引き換えに、履歴比較や保持整理の正しさを失っていないこと。

性能と保守性のどちらを優先するかの判断は、[履歴ストレージのエンジンの選定](storage.md#エンジンの選定)を参照してください。
