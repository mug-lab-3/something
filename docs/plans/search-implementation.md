# 履歴の絞り込み検索の実装計画

[履歴の絞り込み検索](../search.md)を実装するための計画です。仕様は `search.md` を正とし、この文書には作業の順序、設計上の判断、検証の方法を記録します。作業が進んだら、各段階の状態と計測結果を更新します。

## 前提となる事実

| 事実 | 影響 |
| --- | --- |
| 名前は UTF-16LE のバイト列として BLOB に保存している（[`StorageEncoding.Name`](../../src/Something.Storage/StorageModels.cs)）。DuckDB の VARCHAR は不正な Unicode を保持できないため、意図した形式 | 名前・拡張子・正規表現の照合は SQL では行わず、.NET 側で行う |
| 世代ごとの一覧（名前・親・属性・サイズ）は、ビュー `browser`（[`SharedHistoryViews`](../../src/Something.Storage/SharedHistoryViews.cs)）で引ける。ファイルは `StreamAllocated`/`StreamLogical`、フォルダーは `EntrySubtreeAllocated`/`EntrySubtreeLogical` で、どちらも名前別容量 | 世代をまたぐ数値の集計は、このビューを S の世代に絞って行う |
| MSI は publish の出力をまとめて取り込む（[`Package.wxs`](../../installer/Package.wxs)） | LiveCharts2 の DLL を追加しても、インストーラーの定義は変えなくてよい |
| LiveCharts2 は Windows App SDK の一括パッケージに依存する | 一括パッケージの版の固定と、不要なパッケージの除外が必要（[描画ライブラリ](../search.md#描画ライブラリ)） |

## 設計上の判断

- **評価の分担**：共有一覧は 1 件の変更でフォルダーの全件が複製されるため、範囲の一覧の行は 2 百万件 × 30 世代で 1,590 万行になる。DuckDB で同じ観測状態の行を 1 行にまとめ（407 万行）、識別子ごとに整数だけで集計する（200 万行）。確実に条件を満たさない行は、安全側の SQL の条件で先に除き、名前は残った行の分だけ最後に結合する。名前が変わる識別子とハードリンクは、観測状態ごとの行を名前付きで返し、.NET 側で従来の規則で畳み込む。最終的な判定は常に .NET 側で行う。フォルダーのサイズは、フォルダーの集計から世代ごとに別に読む。名前（BLOB）を集計キーに含めた DuckDB 側の集計は遅く、1 GiB では収まらずディスクに退避したため採らない（下の計測を参照）。
- **一時表とストリーミング**：中間の行は TEMP 表に置く（メモリ上。退避を有効にしたときだけディスクに書く）。`MATERIALIZED` の CTE を `UNION ALL` で結合した照会は、DuckDB 1.5.6 のストリーミングで返ってこなくなったため、2 つの読み取りに分けている。TEMP 表の作成はトランザクションの中だと 2.6 倍遅かったため（0.38 秒が 1.0 秒）、検索はトランザクションを使わない。アプリ内の公開と整理はアーカイブのロックで順序付けられ、範囲のスキャンはリースで保護される。
- **読み取りの値の数**：値を 1 つ読むごとに約 30 ns かかるため、識別子・世代の位置・属性と状態を整数に詰めて、1 行あたりの値を 19 個から 9 個に減らした。
- **スレッドとヒープ**：検索中だけ DuckDB のスレッド数を 8 にする。アプリは Segment Heap を使う（[履歴ストレージ](../storage.md#メモリ予算)）。
- **SQL の書き方**：範囲の全世代を読む集計・時系列・フォルダー階層の読み取りは、[`NativeReads`](../../src/Something.Storage/NativeReads.cs) と同じく型付きの列を直接読む SQL にした（[`HistorySearchReads`](../../src/Something.Storage/HistorySearchReads.cs)）。世代全体の読み取りでは EF の実体化が時間の約半分を占めた既存の計測があり、さらに世代ごとの順序を使う集計（`arg_max_null`、最初の世代の値）とメモリ上の世代番号の対応表は LINQ で表現できないため。範囲の解決などの小さな照会は LINQ のまま。
- **結合条件**：`LEFT JOIN scan_folder_ref` の条件に `e.IsDirectory` を入れると、DuckDB がハッシュ結合を使わなくなり、2 万件 × 6 世代で 5 ms が 1.5 s になった。フォルダーの参照はフォルダーにしかないため、条件から外している。
- **ハードリンクの判定**：名前ごとの集計で、同じ識別子の名前の観測期間が重ならなければ、名前が 1 つのまま変更・移動したものとして 1 項目にまとめる。重なる場合はハードリンクとして名前ごとに分ける。名前を A→B→A と戻した場合も期間が重なるため、別の項目として扱う（推測で対応付けないほうに倒す）。
- **正規表現**：.NET の書式とし、`RegexOptions.NonBacktracking` を使って、入力によって処理時間が爆発しないようにする。大文字と小文字は区別しない。
- **結果の保持**：一致した項目は、メモリ上のコンパクトな配列に保持する。ディスクに一時表は書かない。ツリーと一覧は、この配列から親ごとにページ単位で引く。
- **メモリ**：予算はその PC で使える量から決め、`ScanMemoryBudget` で予約する。検索の開始時に、保存と同じ規則（他の予約と OS 用の余裕を引いた残量の半分、下限 1 GiB）で DuckDB の上限を決め、不足したときは同じ予算から増やす。機械の空きの規則は [`MemoryHeadroom`](../../src/Something.Application/Memory/MemoryHeadroom.cs)、DuckDB の上限の規則は保存層の `DuckMemoryPolicy` にまとめた。全世代の全行を .NET 側へ一度に読み込まず、並べ替えはメモリの上限に応じてレコード番号の範囲に分ける。メモリの少ない PC でも失敗させない。
- **スキーマ**：変更しない。名前の照合がボトルネックだと計測で確認できた場合に限り、検索用の列の追加を改めて検討する。

`--app-paths --count 2000000 --generations 30 --repeats 2` で、2 回目の時間です。結果の件数とチェックサムは 3 回とも同じです。

| --- | ---: | ---: | ---: |

| ファイル・サイズ | 18.6 s | 9.4 s | 177 MiB |

| 名前付きストリーム・サイズ | 19.5 s | 10.7 s | 166 MiB |

初版は、ベンチマークで予算を 1 GiB に固定し、増やす経路も渡していませんでした。名前をキーに含めた DuckDB 側の集計がその上限に収まらず、ディスクへの退避に切り替えて再試行していました。照会単体の計測では、世代ごとの結合（6,000 万行）が 0.75 s、集計が 3.7 s で、全列を返すと 1 GiB でメモリ不足になりました。一覧単位の行を並べ替えて .NET で畳み込む 2 回目の版は、アプリと同じく空きメモリから決めた予算（この PC で 5,251 MiB）で測りました。一覧単位の行は約 210 万行と見込んでいましたが、実際は一覧の複製のため 1,590 万行あり、その読み込みが時間の大半でした。

#### 3 回目の版（整数での集計、2026-10-21）

`--searches-only true --repeats 1` で、予算は空きメモリから決めた 21,584 MiB です（`llama-server` などを止めた状態）。

| 照会 | 2 回目の版 | 3 回目の版 |
| --- | ---: | ---: |
| 条件なし（約 212 万件が結果） | 11.0 s | 6.6 s（初回の JIT を含む） |
| ファイル・サイズ | 9.4 s | 3.9 s |
| 名前（正規表現） | 9.3 s | 3.8 s |
| 増減 | 9.4 s | 3.3 s |
| 単調増加 | 11.0 s | 3.6 s |
| 名前付きストリーム・サイズ | 10.7 s | 4.3 s |
| 1 項目の時系列 | 0.40 s | 0.50 s |

増減の検索の内訳は、フォルダーのサイズ 0.33 s、観測状態ごとの TEMP 表 1.09 s、識別子ごとの TEMP 表 0.35 s、名前が 1 つの識別子の読み取り 0.27 s、名前が変わる識別子の読み取り 0.78 s、パスの照合 0.08 s、ツリー 0.04 s です。

既定のヒープでは、同じプロセスで検索を続けると TEMP 表の作成が 1.27 s から 3.40 s まで遅くなっていきました（7 回）。Segment Heap にしてからは 1.06〜1.10 s で一定です。

空きメモリが少ない状態（`llama-server` が 48.7 GiB を使用中、予算は下限の 1 GiB）では、範囲を 2〜4 に分割し、メモリ不足からの再試行で検索全体をやり直したため、8〜25 s かかりました。結果は同じで、失敗はしていません。再試行を範囲単位にすること、分割の見積もりに TEMP 表の分を含めることが残っています。
