# 初期WinUI画面

スキャン対象はドライブ全体。固定ローカルNTFSドライブを選び、手動で開始する。フォルダ指定スキャンは提供しない。フォルダへの移動は完了した同一スキャン結果の閲覧であり、再スキャンではない。

## 構成

アプリアイコンは承認された赤みのある紫のSモノグラム。`Assets/app-icon.png` が元画像、`Assets/Something.ico` は16／20／24／32／40／48／64／96／128／256pxを含む透過アイコン。exeには `ApplicationIcon` で埋め込み、ウィンドウには [AppWindow.SetIcon](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.appwindow.seticon?view=windows-app-sdk-1.8) で同じICOを指定する。ICOは出力・発行先の `Assets` にコピーする。通常のビルドには追加ツール不要。元画像を変更した場合のみ `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/generate-app-icon.ps1` で再生成する。

- `Something.App`: WinUI 3の画面と表示モデル。Windows App SDK 1.8の保守版を固定する。
- `Something.Application`: 読み取り、集計、DB公開をバックグラウンドで実行する `DriveScanner` と、結果を所有する `ScanSession`。
- 既存のWindows取得、NTFS解析、統計、EF Core保存を再利用する。画面からディスク書き込みAPIを呼ばない。

.NET CLIだけでXAMLを含むビルドが可能。Windows App SDKのネイティブランタイムをNuGetからアプリ出力にコピーする、非パッケージ化構成を使う。Visual Studio、MSIX登録、開発者モード、別途のWindows App Runtimeインストールは前提にしない。.NETランタイムは開発セットアップで用意する。対象はx64 Windows 10 1809以降。

既存のVS Code推奨拡張、CSharpier、セットアップスクリプトを使用する。SDKと依存パッケージは固定し、ロックファイルを含める。採用構成の参考はMicrosoftの [unpackaged WinUI CLI sample](https://github.com/microsoft/winappCli/tree/main/samples/winui-unpackaged-app)。

## 動作と集計

スキャン開始は各ドライブカードの右上のアイコンで操作する。未選択のカードでも、そのドライブを選択してスキャンする。スキャン中は同じアイコンをキャンセルに切り替え、他のドライブの操作は無効にする。カードの選択ボタンとスキャンアイコンは独立したコントロールとして配置する。

ドライブ選択は幅300・高さ140の統一カード形式。選択時も幅を変えず、アクセント色のアウトラインだけで選択状態を示す。枠はボタンのホバー／押下状態とは独立したレイヤーとし、ホバー中も維持する。ドライブ名・ドライブ文字・使用中／合計容量・空き容量を表示し、各カードの最下段にはドライブ全体のスキャン状態とファイル名の数を1行にまとめ、スキャン中は最下段をスピナーと「走査中 42%」「集計中」「保存中」「書き出し中」の文字表示に切り替える。走査の割合はMFT範囲に対する進捗であり、保存まで含めた全処理の完了率ではない。使用量バーはスキャン中もボリューム使用量を表示し、スキャン用の横バーは重ねない。NTFS表記と所要時間はツールチップに置く。使用中／合計容量は単位を共有したコンパクトな表記とし、同じ行に空き容量を表示する。カードの容量表示はWindowsのボリューム容量情報にまとめる。集計サイズと集計方式の説明ラベルはカードには表示しない。フォルダを移動してもカードのファイル名の数はドライブ全体のまま。画面内のアプリタイトルは置かず、タイトルバーに表示する。カードは1行の横スクロールで切り替え、ドライブ数によって縦幅を増やさない。選択したカードは表示範囲に入るようスクロールする。OSのアクセント色とライト／ダークテーマに従う。

UIの「サイズ」とサイズ順はディスク上の割り当て容量に固定し、一覧・ランキングで同じ基準を使用する。基準の切り替えUIは置かず、表示するサイズ列は1つ。保存層では割り当て容量と論理サイズの両方を維持する。下のツリー・一覧には容量サマリーを重ねない。ドライブごとに完了済みの一時DBを保持し、切り替えるとそのドライブの結果を表示する。未スキャンのドライブでは別ドライブの一覧を表示しない。全結果は終了時に破棄する。

起動時はドライブ候補の確認だけを行い、自動スキャンしない。実スキャンでは既存の読み取り専用ボリュームハンドルを使用する。マニフェストは `requireAdministrator`。エクスプローラーから実行ファイルを開くとWindowsのUACで管理者権限を要求する。拒否した場合は起動しない。既に昇格済みの場合は追加の確認は不要。`dotnet run` とVS Codeデバッグは昇格済みのターミナル／VS Codeから実行する。

高DPI対応はマニフェストで `PerMonitorV2` を宣言し、Windowsによるビットマップ拡大を防ぐ。初期ウィンドウサイズはXAMLの表示倍率から物理ピクセルに換算し、モニターの作業領域に収める。表示倍率の異なるモニター間の移動はWinUIのDPI対応を使用する。設定の根拠はMicrosoftの [DPI awareness](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process) と [application manifests](https://learn.microsoft.com/en-us/windows/win32/sbscs/application-manifests)。

読み取り中は取得件数と進捗を更新する。集計・保存中は段階名と不定進捗アニメーションを表示する。キャンセル／失敗時は以前の結果を保持し、未完成のDBを公開しない。ウィンドウ終了でもキャンセルし、所有する一時DBを破棄する。履歴としての保存は次の実装段階。

フォルダ容量はサブフォルダを含む名前別の無名DATA集計。ハードリンクは名前ごとに計上し、DOS別名は表示対象に含めない。ジャンクションやシンボリックリンクの参照先は辿らない。管理領域、名前付きストリーム、共有データの単一計上を含む物理的なドライブ使用量とは別の表示である。

一覧は直下のファイル・フォルダを250件ずつ取得する。フォルダを先に並べ、割り当て／論理容量順をDBクエリで適用してからページ分割する。ツリーも必要になった枝だけ取得し、250件を超える枝は追加読み込みする。SQLをUIへ持ち込まず、EF CoreのLINQを保存層に置く。ランキングは上位20件、全階層またはルートから1～3階層、末端フォルダのみで絞り込める。

大量挿入後、公開トランザクション内でSQLiteの `PRAGMA optimize=0x10002` を実行する。既存DBを開く際にも確認する。SQLite固有の処理は保存層の `SqliteDatabaseBootstrap` に置き、LINQや保存内容は変更しない。これにより親フォルダ索引の選択に必要な統計を公開前・メモリDB書き出し前に準備する。統計の更新も公開の失敗・キャンセル時にはロールバックされる。処理量を制限するSQLite 3.46以降の [推奨方法](https://sqlite.org/lang_analyze.html) を使用する。

2026-10-13の合成データ検証（SQLite 3.53.3、メモリDB、1万ディレクトリ・20万ファイル）では、修正前の実行計画は `observation` のスキャンID範囲から開始し、直下の名前との結合を繰り返していた。修正後は `IX_file_name_ScanId_ParentIndex_ParentSequence` から開始し、対応するレコードだけを主キーで結合することを `EXPLAIN QUERY PLAN` で確認した。2回目の取得ではルートの子フォルダ250件が約7,011msから21ms、20ファイルを含むフォルダ一覧が約637msから1.2msになった。統計作成を単独実行した際の時間は約40ms。全体120万ファイルの場合でも、子フォルダ250件の取得は約40ms、120ファイルの一覧は約3.1msだった。初回はEFクエリ準備などの追加時間がある。これらはDB取得の測定値であり、GUI描画・実ディスク上の時間を保証しない。

ファイル参照のシーケンス番号を親照合と閲覧に使用し、再利用されたレコードを同じフォルダとみなさない。未解決サイズはゼロにせず「不明」と表示する。既知容量に未解決の子が含まれる場合も状態欄に表示する。ライブ観測なので同時点のスナップショットではない。

ツリーのフォルダ、一覧上部の表示パス、右側の一覧・ランキング行には、右クリック／コンテキスト操作でパスのコピーメニューを表示する。ファイル行は「ディレクトリのパスをコピー」（親ディレクトリまで）と「ファイルのパスをコピー」（ファイル名を含む）の2項目。フォルダ行はそのフォルダの「パスをコピー」を表示する。選択中の項目ではなく操作した項目のパスを使用し、「さらに読み込む」や余白には表示しない。省略・エスケープ前のパス全文をテキストとしてクリップボードへコピーする。コピーに伴うDB取得や対象ファイルへのアクセスは行わない。

## 確認方法

`dotnet run --project src/Something.App -- --demo` は合成データだけで同じ集計・保存・閲覧経路を通る。調査対象のファイルやドライブを読み取らない。実スキャンと同じ実行ファイルなので起動には管理者権限が必要。

画面のレンダリング確認には、存在する出力ディレクトリを指定する。

```powershell
dotnet run --project src/Something.App -- --demo --smoke-test "$PWD\artifacts\something-ui.png"
```

初期一覧・ランキングの件数、フォルダ移動、ツリー追加取得、階層／末端フィルターを検証し、画面をPNGへ保存して終了する。失敗時は終了コード1と `.result` に理由を出す。出力はGitに含めない。

保存層のテストは別名、DOS除外、親シーケンス不一致、未解決サイズ、名前付きDATAだけの既知ゼロ、並べ替え後のページングを検証する。セッションのテストはデモ結果の閲覧、並行リクエスト、キャンセルと破棄を検証する。GUIからの実ボリュームスキャンは別途実機で確認する。
