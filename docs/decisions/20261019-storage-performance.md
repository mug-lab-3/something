# 履歴 DB の保存・照会を高速化する

決定日: 2026-10-19。状態: 採用・実施中。

## 背景

スキャン記録の保存、履歴の読み込み、表示への反映で DB 関連の待ち時間が目立ちます。現行コードの調査で、主な原因を次の二つと判断しました。

1. 世代のメンバーシップ（どの観測がどの状態版か）が、全一覧エントリを `DISTINCT` するビュー `observation_ref` で毎回再計算される。公開時の差分・検証、全ファイル読み込み、表示フィルター、親フォルダ解決がすべてこのビューを経由する。
2. 大きな表がランダムな UUID の一覧 ID と挿入順不定で書かれ、zonemap による読み飛ばしが効きにくい。数百万行規模の全表に PK（ART インデックス）があり、投入時間とメモリを消費する。

合成 200 万件の計測では、初回保存 33 秒のうち確定が 12 秒、関係検証が 11 秒でした。また、DuckDB の上限 4 GiB では 2 世代目の差分比較がメモリ不足で失敗しました。一時ディスク退避が無効なので、件数が増えると、空きメモリの少ない PC では保存できなくなります。数十万件規模では、件数・世代数に比例するこれらのコストが見えません。

本アプリは未リリースです。既存 DB との互換性は不要とし、スキーマ変更を通常の選択肢として扱います。既存の DB ファイルを自動で移行・上書き・削除しない規則は維持し、形式識別子とファイル名を上げて新しい DB を作ります。

## 方針

### スキーマを変えない修正

| ID | 内容 |
| --- | --- |
| R1 | 期間比較で同じ世代の集計を二重に読まない。 |
| R2 | フォルダ分析の表示パスをメモ化し、フォルダ数 × 深さの探索をなくす。 |
| R4 | 履歴 DB の接続と開く際の検証を操作ごとに繰り返さない。 |
| R5 | 一覧ページの往復（存在確認・件数・本体）を減らす。 |
| W4 | 主要表の Appender 投入で、値ごとのボックス化とエンティティ生成を避ける。 |
| W5 | `threads=4` 固定を見直す。 |
| W6 | 保持整理を削除世代の参照に限定し、退役世代をまとめて回収する。公開完了の待ちから切り離す。 |

### 新しい共有履歴形式

| ID | 内容 |
| --- | --- |
| S1 | 世代ごとのメンバーシップを実表 `generation_observation(Gen, RecordIndex, Version)` に保存し、事実ビューはこの表と状態表を直接結合する。 |
| S2 | 世代・状態版・一覧の内部キーを整数の連番にする。外部識別子としての `scan.Id`（UUID）は残す。 |
| S3 | `shared_entry` は一覧 ID 順、状態表は（版, RecordIndex）順で投入し、点照会を zonemap で絞る。 |
| S4 | 大きな表の PK・一意インデックスと未使用インデックスを外す。一意性と参照は公開前の論理検証で保証する。小さな表の PK は残す。 |
| S5 | 前世代との差分を、双方向 `EXCEPT` ではなく、キーでの完全外部結合と全列の `IS DISTINCT FROM` で求める。 |
| S6 | 保持整理は、削除する世代が参照した状態のうち他の世代から参照されないものだけを削除する。 |

マイグレーションは未リリースのうちに作り直して 1 本にまとめます。

### メモリに依存しない処理

保存・照会の成否は、実行する PC の空きメモリに依存させません。開発機の RAM に合わせて予算を引き上げ、メモリ不足を回避する方式は採りません。

| ID | 内容 |
| --- | --- |
| M1 | 最低予算 1 GiB で、ボリュームの件数に関係なく保存・照会が完了すること。予算は速度に影響してよいが、成否には影響させない。 |
| M2 | 通常はメモリキャッシュだけで処理し、ファイル書き込みを増やさない（`temp_directory=''`）。メモリ不足時はまず予算を増やして再試行し、増やせない場合に限り DB 隣接の `<DB>.spill` へのディスク退避を有効にして再試行する。退避ディレクトリはエンジンを閉じるときに削除する。 |
| M6 | 確定中のメモリ不足は、DB を読み直して世代が公開されていないことを確認できた場合だけ再試行する。公開済みならその世代を結果とし、二重公開しない。 |
| M3 | 大きな表に、メモリ常駐を前提とするインデックスを置かない（S4）。 |
| M4 | 差分比較・検証・回収は、世代全体の行をハッシュ集合として同時に保持しない形にする（S1・S5・S6）。必要なら RecordIndex の範囲で分割して処理する。 |
| M5 | .NET 側でも、世代全体を辞書や配列に展開する照会（全件読み込み、表示フィルター投影など）のピーク使用量を計測し、件数に比例して増え続ける箇所を段階的に解消する。 |

メモリキャッシュを優先し、ファイル書き込み回数を抑える基本方針は変えません。M2・M6 は、その方針のまま失敗させないためのフォールバックです。ただし、フォールバックでも退避できないメモリ（大きな表の ART インデックス）は残るため、M3・M4 の構造変更と組み合わせて初めて最低予算での完了を保証できます。200 万件・予算 1 GiB の実測では、ディスク退避後の確定直前に ART インデックスが 664 MiB を占め、確定がメモリ不足で失敗しました。

### 保存時のメモリ使用量の実測

200 万件・2 世代の保存で、各段階の開始時点の DuckDB 使用量を `duckdb_memory()` で測りました。本来の使用量を見るための測定なので、予算は 16 GiB にしています。

| 時点 | 初回世代 | 2 世代目（約 1% 変更） |
| --- | ---: | ---: |
| 投入直後（TEMP 表 `incoming_*`） | 1.9 GiB | 1.9 GiB |
| 確定直前（TEMP 表と中間表） | 2.6 GiB | 2.5 GiB |
| 確定直前の ART インデックス | 0.66 GiB | 0.02 GiB |

プロセス全体のピークは 6.7 GiB でした。最大の原因は、変更量に関係なく世代全体を圧縮されない TEMP 表へ複製し、SQL の `EXCEPT` で比較していることです。予算増額やディスク退避では、この構造的な使用量は減りません。再試行するたびに保存全体をやり直すので、かえって遅くなります。

### 保存方式の改訂

最低予算 1 GiB の PC で、再試行も退避もせず、メモリ内だけで保存が完了することを目標にします。予算増額とディスク退避（M2）は、想定外の場合に備えた保険としてだけ残します。

| ID | 内容 |
| --- | --- |
| D1 | TEMP 表への全件複製をやめる。走査バッファはすでに .NET のメモリにあるため、前世代の状態を DB から順不同のまま流し読みし、RecordIndex を添字にした配列でバッファと全列を照合する。保持するのは件数分の小さな配列（版番号・一致フラグ・名前数など、200 万件で数十 MiB）だけにする。 |
| D2 | 一覧の再利用判定も同じ方式にする。前世代の一覧エントリ（一覧キー・RecordIndex・Ordinal・版）を流し読みし、新世代の所属と版が完全に一致する一覧だけを再利用する。版の一致は ID の一致であり、ハッシュは使わない。 |
| D3 | 変更された状態・新しい一覧・世代の所属（S1）だけを、Appender で永続表へ直接書く。大きな表に PK を置かない（S4）ので、DuckDB は大量追加をトランザクションのメモリに溜めず、行グループ単位で DB ファイルへ書き出せる。 |
| D4 | 照合と同時に、一意性・参照の検証を .NET 側で済ませる。確定前の SQL 検証は件数の照合など、全件をハッシュ集合にしない軽い検査に限る。 |

DuckDB の作業用メモリは流し読みのバッファと Appender の行グループに限られ、件数に比例しなくなる見込みです。.NET 側では走査バッファそのもの（M5）が残るため、これは別に計測して削減します。

### SSD への書き込み量

ディスクへ書く場合も、SSD の寿命を縮める書き方はしません。

- 1 世代で書き込むのは、変更された状態と所属・参照の行だけにする。所属表（S1）は整数 3 列で、世代内で値が一定または連続するため、強く圧縮される。増加量を計測して記録する。
- 世代全体の一時複製、中間表の作り直し、退避ディレクトリへの書き出しを、通常の保存経路に入れない。
- DB 全体を書き直す最適化（`VACUUM` 相当や詰め直し）は、明示操作のときだけ実行し、自動では実行しない。
- 書き込み量はプロセスの書き込みバイト数（`ProcessIo`）で計測し、変更前後を比較する。

現行方式の 200 万件での書き込み量は、初回 705 MiB、変更なしの世代 39 MiB、約 1% 変更の世代 193 MiB でした。変更量に対して書き込みが大きいため、改訂後の目標比較値とします。

## 維持する要件

[保存エンジンの選定](20261014-duckdb-storage.md)の要件は変えません。

- 原観測・名前・DOS 別名・ストリーム・未解決状態を省かない。
- 差分はハッシュ一致だけで同一と判定せず、保存対象の全列を比較する。
- 世代の公開を原子的にし、参照を検証してから公開する。物理 FK・カスケードには依存しない。
- EF Core・LINQ・型付きエンティティを基本とし、手書き SQL・Appender は計測したボトルネックに限る。

## 進め方と計測

1. 変更前の基準値を `tools/Something.StorageCompare` の `--app-paths` で記録する。標準条件は 200 万件・30 世代・DuckDB 予算 1 GiB（アプリの最低予算）とし、失敗する場合はその世代と原因を記録する。
2. R1・R2 を実施する。
3. M2 を入れる（実施済み）。S1・S2・S4 をまとめて新形式とし、保存を D1〜D4 の方式に書き換える（S5 は D1 に置き換わる）。S6 の回収 SQL も書き直す。予算 1 GiB で、200 万件・30 世代の保存が再試行・退避なしで完了することを確認する。
   - 2026-10-19 実施：形式 5 として S1・S4・D1〜D4・S6 を実装し、上記の完了を確認した（[性能計測](../benchmarks.md)）。S2（整数キー）は未実施で、一覧 ID だけを公開ごとに昇順の UUID とした。
   - 2026-10-20 実施：形式 6 として S2 を実装した。形式 5 の 30 世代 DB（840 MiB）では、版・一覧の UUID 列が格納ブロックの約半分を占めていた（所属表の版の列だけで約 210 MiB）。世代・版・一覧を整数にし、`scan.Id` は外部識別子として残した。確定前の追記をメモリに溜めないため、共有履歴は `preserve_insertion_order=true` に変更した。
4. S3 を加え、一覧の点照会を計測する。
   - 2026-10-20 に読み込み経路を先に改善した。全件読み込み・表示用フォルダ属性・フォルダ集計は、DuckDB では EF を使わず型付きの列を直接読む（`NativeReads.cs`）。根拠は、200 万件の全件読み込み 3.1 秒のうち EF のエンティティ変換が約 1.6 秒だった計測。SQLite は EF のまま。フォルダ一覧は参照する集計状態の版だけを読む。結果は[性能計測](../benchmarks.md)に記録した。
5. 残ったボトルネックに応じて R4・R5・W4・W5・W6 を実施する。

各段階で、保存時間・DB サイズ・照会時間・プロセスのピーク使用量・書き込みバイト数を同条件で前後比較し、[性能計測](../benchmarks.md)に記録します。保存事実・一覧・照会結果の一致検証が通らない高速化は採用しません。容量が増える変更（S1 など）は、増加量を計測して記録します。
