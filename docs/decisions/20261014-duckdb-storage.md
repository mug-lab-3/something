# 保存エンジンにDuckDBのファイル方式を採用する

決定日: 2026-10-14。状態: 採用・アプリと診断CLIの切り替え実装済み。

## 結論

Somethingの保存エンジンは、比較した「最適化DuckDB・ファイル」方式を採用する。
ユーザーはルート一覧の約10msを許容し、保存時間、DB容量、容量・変動ランキングの性能を重視すると判断した。
オンメモリDBを最後に書き出す方式は標準にしない。

この決定はエンジンと保存方式の選択であり、手書きSQL中心の実装への変更や保守性の優先順位を下げる合意ではない。
型付きモデルとLINQ・EF Coreを優先する方針を維持する。DuckDB向けEF Coreプロバイダーの互換性は、本番置き換え時に実際のモデルと照会で検証する。

## 比較結果と判断理由

合成120万件＋ルートを2世代、設定予算1 GiB、独立プロセスで各方式3回。
一覧用の派生テーブルをSQLiteにも追加し、構造改善の効果を含む対照で比較した。
値は3回の中央値。照会は各回15回のウォーム計測の中央値。

| 項目 | 現行SQLite | 一覧用構造ありSQLite | 最適化DuckDB・ファイル |
|---|---:|---:|---:|
| 2世代の保存完了まで | 35.34秒 | 47.70秒 | 28.78秒 |
| ルート一覧の初回ページ | 495.52 ms | 0.81 ms | 9.71 ms |
| ルートの件数取得 | 392.06 ms | 4.32 ms | 0.55 ms |
| 小さいフォルダの一覧 | 0.030 ms | 0.030 ms | 1.17 ms |
| 容量上位20件 | 32.83 ms | 34.63 ms | 3.35 ms |
| 増加量上位20件 | 182.24 ms | 179.51 ms | 11.28 ms |
| 最終DBサイズ | 2097.8 MiB | 2665.8 MiB | 699.3 MiB |

一覧用構造ありSQLiteに比べ、DuckDB案は保存時間が約40%短く、DB容量が約74%小さく、増加量上位20件が約16倍速い。
SQLite案の一覧は約12倍速いが、DuckDB案の絶対時間を許容できるため、この差を採用上の障害としない。
全9回で全保存列と可視一覧全行のSHA-256、および7種類の照会結果が一致した。
原観測、シーケンス番号、ハードリンク名、DOS名、名前付きストリーム、未解決状態の削減による高速化ではない。

初回比較ではDuckDB案の一覧が現行SQLiteより速かったが、一覧構造をそろえた対照ではSQLite案の方が速かった。
この経緯も含め、DuckDBを「どの照会でも速い」とは評価しない。
また、容量型・差分計算・参照検査も異なるため、差をエンジンだけの効果とは主張しない。
UI描画、実データの深い階層、多世代履歴の性能を保証する測定ではない。

オンメモリ方式の初回比較は、2 GiB予算でも2世代の保存・書き出しが53.34秒だった。
同じ初回比較のファイル方式34.36秒より遅く、ピークメモリも大きかったため、ファイル方式を選ぶ。
後の追試の28.78秒とは別の反復なので、直接の改善率計算には使わない。

詳細な条件・全結果・再現コマンドは [storage-comparison.md](../storage-comparison.md) に記載する。
候補ソースの退避先とハッシュも同文書に記録した。生成DBや退避ZIPはGitへ含めない。

## 本番化で維持する要件

- 全ドライブ・全世代を1つの共有ファイルに保存し、スキャンごとの別DBには戻さない。
- 完了した観測、一覧用データ、履歴メタデータ、対象ボリュームの最新ポインターを同一トランザクションで公開する。
- 観測と名前・ストリームを保持し、未解決をゼロ容量や削除済みへ変換しない。
- GUIDはUUID、集計容量はUHUGEINT、名前は任意のUTF-16コード単位を保持できるBLOBとする。UInt128全域と増加・減少双方の差分を検証する。
- 一覧用の派生データを持ち、ツリー、無限スクロール、件数、深さ・末端フィルター、パスコピーの既存動作を保つ。
- 過去24時間の全記録と、それ以前の日次最終記録を保持する。24時間・7日・365日の変動照会、閲覧中の世代の保護も保つ。
- 別ドライブの取得・解析は並行可能とし、共有DBへの公開・整理は調停する。DuckDBの共有メモリ予算とスキャン中の予約を二重計上しない。
- 保存先はアプリ専用領域とし、ボリューム取得は引き続き読み取り専用。実ファイルやMFTを変更しない。

## 切り替えの実施順序

1. EF Coreプロバイダーで実モデル、UUID・UHUGEINT・UTF-16、LINQ照会、トランザクション、スキーマ構築を検証する。プロバイダーの説明だけで動作を保証しない。
2. 保存層に本番用DuckDB接続・型変換・一括保存・一覧構造を実装する。比較CLIをそのままアプリへ組み込まず、合成データや固定の世代時刻を除く。
3. 一覧・ランキング・期間比較・履歴整理を置き換える。比較CLIの全ポインター削除など、単一ボリューム前提の処理は本番で使わない。
4. 失敗・キャンセル、並行保存と閲覧、保持整理、再起動、参照再利用、最大値、減少・未知値を含む回帰テストと性能比較を行う。
5. アプリと診断CLIを切り替え、VS Code/.NET CLIのセットアップ・固定依存・実行時前提条件を更新する。

DuckDB向けEF CoreプロバイダーはLINQやマイグレーションなどの対応を案内しているが、現行アプリでの検証は未実施。
依存バージョンやAPIの採用は次段階で決定する。[プロバイダーの一次資料](https://github.com/skuirrels/DuckDB.EFCoreProvider)

未リリースのためSQLite履歴の自動移行は実装しない。既存の `catalog.sqlite3` をDuckDBとして開いたり、自動削除・上書きしたりしない。
新形式は別ファイル名 `catalog.duckdb` とし、旧ファイルを保持したまま新しいスキャンで履歴を開始する。
現在のアプリはDuckDBを使用する。SQLiteの実装は比較・回帰テスト用として保持する。

## 切り替え実装の記録

2026-10-14、アプリ・診断CLIをDuckDBへ切り替えた。EF Coreプロバイダー1.27.0とSkuirrels.DuckDB.NET.Data.Full 1.5.6を固定。UHUGEINTはプロバイダーに直接のEFスカラー対応がないため、保存層にUInt128/BigIntegerの型アダプターを追加した。UInt128全域と任意UTF-16名の保持をテストした。

観測保存はEFモデル由来のAppender、一覧は型付きbrowserモデルのLINQ、履歴の公開・保持整理・閲覧はEF Coreを維持する。物理外部キーは作らず、公開前の集合検査と同一トランザクション内の明示的な依存行削除を使用する。DB識別・初期スキーマはチェックイン済みのDuckDB専用マイグレーションで管理する。

723テスト成功・公開コーパス7件未実行。Releaseビルド、合成100万件の容量一致、空の.toolsからのセットアップも確認した。Visual C++ランタイムは既に導入済みの環境で確認しており、未導入PCでのインストールは実機未検証。実ボリュームの再スキャン、多世代での長期性能、複数アプリプロセスでの同時DB利用は検証対象に含めていない。
