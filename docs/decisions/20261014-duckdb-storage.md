# DuckDB のファイル方式を採用する

決定日: 2026-10-14。状態: 採用。

## 判断

履歴の通常保存には DuckDB のファイル方式を使います。大規模なスキャンの保存容量・保存時間・集計と履歴比較の性能を優先し、一覧の点照会の絶対時間も評価した選択です。全ドライブ・全世代を一つの共有 DB へ保存します。

型付きモデル、EF Core、LINQ を基本とし、測定したボトルネックに限って保存層内の Appender・集合 SQL を使用します。エンジン選定を、全処理を手書き SQL にする理由にはしません。

## 比較の根拠

同じ一覧用構造を持つ SQLite を対照に、合成 120 万件・二世代を比較しました。採用時の中央値は DuckDB が保存 28.78 秒・699.3 MiB、SQLite 対照が 47.70 秒・2665.8 MiB でした。増加量上位の照会も DuckDB が有利でした。

ルート一覧は SQLite 対照が 0.81 ms、DuckDB が 9.71 ms で、SQLite の方が速い結果です。DuckDB をすべての照会で最速と評価せず、一覧の絶対時間と他の処理の改善を合わせて採用しました。比較条件と表は[性能計測](../benchmarks.md)に記載しています。

オンメモリ方式は保存後の書き出しとピークメモリの負担があり、同日の別反復でファイル方式より遅かったため標準にしません。比較ツールの候補構造と現在の共有状態モデルは同一ではなく、採用時の数値を現在の性能保証には使いません。

## 維持する要件

- 原観測・名前・DOS 別名・ストリーム・未解決状態を省かない。
- UInt128 全域、任意 UTF-16 名、符号付き増減を保持する。
- 世代の公開を原子的にし、参照を検証してから公開する。
- 物理 FK・カスケードに依存せず、依存行と共有状態を明示的に回収する。
- 一覧構造を持ち、連続スクロール・件数・ソート・過去世代の照会を維持する。
- ドライブごとの並行取得と共有 DB の予算・保存調停を分離する。
- 未対応の旧 DB を自動移行・上書き・削除しない。

実装の正本は[履歴ストレージ](../storage.md)、保持規則と管理操作は[履歴](../history.md)です。SQLite は比較・回帰テスト用に残します。
