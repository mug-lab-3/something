# DuckDBのメモリ予算と不足時の対策

## 原因と実装済みの修正

E:の保存で `63.8 MiB/64.0 MiB used` が発生した。SQLite用のページキャッシュ予算をDuckDBの `memory_limit` に流用していた。小さいドライブの推定DBサイズが共有履歴全体の処理用メモリ上限を64 MiBまで下げてしまう設定だった。エラー画面だけでは、実際に失敗した演算子や索引は特定できない。

DuckDB用の選択を分離する。バッファ完成後の物理・commit・virtualの空き量から他スキャンの予約を引き、安全余裕（物理RAMの20%、1〜4 GiB）を除く。その残量の1/4を1〜2 GiBへ制限し、16 KiB単位へ切り下げる。新しいドライブの推定DBサイズでは上限を切らない。空き量を取得できない場合も1 GiBとする。予約管理には選択した上限の2倍とスキャンバッファを計上する。SQLite比較用の64 MiB〜2 GiBキャッシュ計算は変更しない。

ストレージ側にも1 GiBの最低上限を設け、従来の小さいキャッシュ予算を渡した呼出しで共有エンジンが64 MiBに落ちることを防ぐ。読み込み接続は既存エンジンの上限を再設定しない。設定は接続ごとの専用予算ではなく同じDBを使うエンジン全体に適用される。

これは使用可能な上限であり、1 GiBを事前確保する操作ではない。一方、低メモリ環境でも完了を保証するものではなく、プロセス全体をこの値以下に制限するものでもない。

## 一覧生成のOOMと自動回復

その後、ステップ12/14の一覧生成でも `1023.9 MiB/1.0 GiB used` が発生した。1 GiBの最低値だけでは、共有履歴の索引と結合・並べ替えの処理用メモリに足りない場合がある。個々の演算子の内訳は画面からは判定できない。

アプリの保存でDuckDBのOOMを検出した場合、失敗したトランザクションを破棄し、既存の公開履歴が保持された状態から増額・再試行する。物理・commit・virtual空き量を再取得し、他スキャンの予約とOS安全余裕を除いた残量に増額分の2倍が収まる場合だけ予約を更新する。上限は倍増、最大8 GiB、再試行は最大3回。初期上限1〜2 GiBの選択は維持する。RAM情報がない場合や余裕不足では増額しない。完成済み観測バッファを再利用するため、ライブボリュームを再スキャンしない。

同じファイルの接続が共有するエンジンの上限を追跡し、小さい別ドライブの保存や読込が上限を下げないようにする。保存開始時には既存エンジンの実際の上限もスキャン予約へ反映し、後続スキャンが余裕を使い回さないようにする。最後の接続を閉じたら記憶した上限を解放し、次のエンジンはその時の予算で開始する。再試行中は進捗へ回数と上限を表示し、ステップ番号・保存件数は保存のやり直しに合わせて戻る。

再試行対象は保存確定前のDuckDB OOMだけ。キャンセル、制約違反、一般の.NET OutOfMemoryExceptionは再試行しない。コミット開始後は結果が不確実になり得るため、自動再試行しない。ストレージAPIだけを呼ぶ診断ツールでは、予約更新コールバックを渡した場合にのみ再試行する。

テストは小さい独立メモリDBに実際のDuckDB OOMを発生させ、その例外を保存途中に注入して、増額前のロールバック、成功時の単一世代公開、増額拒否、回数上限、キャンセル、共有上限の維持と接続終了時の解放を確認する。実ドライブの履歴量・PC空きRAMによってはなお失敗し得る。索引削減や全件結合の分割は、測定後の追加対策として残す。

## 残る対策案：一時書き込みよりRAMを優先

ユーザー指定により、追加のSSD書き込みを抑えるため以下の順序を採用する。増額と限定再試行は上記のとおり実装済み。詳細メモリ診断・負荷削減・退避順序の厳密な制御は残る作業。

1. 失敗した処理段階、DuckDBの上限・使用量、索引と一時データの内訳、OS空き量、他スキャンの予約を記録する。ファイル名などの私的なスキャン情報は診断ログに含めない。
2. RAMに余裕があれば、共有エンジンの予約を原子的に更新して上限を増やす。失敗した保存トランザクションをロールバックし、完成済みバッファから回数を限定して再試行する。増額は最大8 GiBまで。RAMを使い切る無制限の増額は行わない。
3. 他の保存処理を待機させ、処理スレッド数を減らす。索引の実際の利用を測定し、不要な索引や全件の中間結果を減らす。整合性を守る制約は根拠なく削除しない。
4. 増額・負荷削減で足りない場合に限り、アプリ所有の一時領域へ退避する。容量上限・空き容量・終了時の安全な削除を管理する。DuckDBの自動退避は現状の既定設定でも動作するため、この順序を厳密に保証するには退避設定の制御と再試行テストが必要。
5. 退避できない処理やストレージ不足では、保存完了と扱わず以前の公開世代を維持する。容量をゼロとして保存しない。

DuckDBは通常の処理用データをディスクへ退避できるが、すべての処理が対象ではない。特にART索引のメモリはbuffer managerへ登録されるものの、現状では通常のページのようには追い出されない。このため「キャッシュが足りなければページを捨てれば必ず完了する」とは保証できない。
