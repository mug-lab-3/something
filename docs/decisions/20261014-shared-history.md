# 未変更の履歴データを共有する保存形式

2026-10-14。ユーザーの「本体で試す」という指示により、フォルダ一覧共有をアプリの履歴保存・閲覧へ組み込む。

## 保存構造

本体は `%LOCALAPPDATA%\Something\History\catalog-v4.duckdb` を使用する。形式識別子は4。旧 `catalog-v2.duckdb` は移行・上書き・削除しない。最初は履歴が空で、新たに完了したスキャンから記録する。

- `state_observation` / `state_file_name` / `state_stream`: 不変の観測状態、全名前（DOS別名含む）、全DATAストリーム。キーのScanIdは**状態グループの識別子**であり、元スキャンの存続に依存しない。MFT番号とシーケンスを保存する。
- `state_folder_sample`: 不変のフォルダ集計。名前別の容量と重複排除した容量を両方保存する。
- `scan_folder_ref`: 世代ごとのフォルダ識別子、観測状態、集計状態。未観測のフォルダには観測参照を作らない。
- `shared_entry` / `scan_listing_ref`: 不変の直下の表示一覧と世代ごとの参照。4096件を超える一覧だけ、MFT番号の1024レコード範囲で分割する。表示順とは独立した分割で、変更箇所のブロックのみ新規作成する。
- `auxiliary_ref`: 一覧・フォルダ参照から復元できない管理・拡張・未解決・所属不明の観測。通常一覧にないという理由で観測を省かない。
- `scan` / `volume_sample` / `history_snapshot` / 時間計測: 世代ごとのメタデータ、不確実性、管理・所属不明容量、処理時間。

世代から共有状態へ直接参照するため、前回から差分を何世代もたどらない。全ファイルの対応行を毎回作る代わりに、一覧の参照からその世代のファイル集合を復元する。空フォルダはscan_folder_refに残る。世代の参照行は増えるため、未変更スキャンでもDBの増加がゼロになるとは保証しない。

## 変更検出と公開

長期間のC#比較キャッシュをプロセスに保持しない。本体では完成したスキャンバッファをDuckDBのTEMPテーブルへ一括投入し、同じボリューム・シリアル・取得範囲・集計ポリシーの前の公開世代と、保存対象の全列を集合比較する。文字列はUTF-16のバイト列を比較する。ハッシュ一致だけで共有を決めず、サイズ・名前・属性・名前Ordinal・親参照/シーケンス・ADS・ヘッダーリンク数・取得/解決状態の違いを保持する。

変更なしはファイル内容のバイト一致を意味しない。今回取得できなかったファイルや未解決の容量を前回の値で補わない。以前にあった別状態への再変更は前回と違うため新しく保存する。本体では当初の試作のような全過去状態の再検索は行わない。

新しい状態、一覧、参照、容量集計、履歴と公開ポインターを同一トランザクションで確定する。参照先の存在と観測参照の一意性を検証する。キャンセル・制約違反・保存確定前のOOMではロールバックし、前の公開結果を維持する。既存のメモリ予約・上限増額・限定再試行を継承する。TEMPの自動ディスク退避を無効にし、RAM増額を先に試す。RAMを確保できない場合に保存完了と扱うことはない。WALは維持する。

実ドライブの保存で「Failed to append: Current transaction is aborted」が表示された。複数Appenderの後始末が最初の例外を上書きする問題を、独立したDuckDBで制約違反とメモリ不足を発生させて再現した。最初の追加・flush・保存本体の例外をトランザクション内で保持し、後続Appenderの後始末のエラーで置き換えない。これにより元のOOMが増額処理へ届く。保持した例外はトランザクション終了時に解放し、次の保存へ持ち越さない。実ドライブでの最初の原因はこの表示だけでは特定できない。

再実行で `Failed to append: failed to allocate data of size ... (1.0 GiB/1.0 GiB used)` が確認された。OOMの接頭辞がないAppenderエラーもメモリ不足として判定するよう修正した。またユーザー指定により固定の2GiB/8GiBの天井を撤廃し、現在の空きメモリと競合予約に基づいて予算を決める。[現在のメモリ方針](20261014-duckdb-memory.md)を参照。

EF Coreの型付きモデルとLINQを維持する。共有状態の型は元の型と同じ変換・列型・キー・値制約を使用し、スキーマはSharedHistoryDbContextの初期マイグレーションで管理する。Appenderは列名だけでなくネイティブ列型も照合する。元の世代単位のモデルは読み出しビューへ接続する。一括の差分検出・参照公開・回収に限ったSQLはSharedHistoryPublicationに隔離する。

## 一覧と保持整理

通常の一覧APIは最初に指定世代・親フォルダの一覧IDだけを取得し、その共有一覧をLINQで絞り込む。フォルダの配下容量は指定世代の集計状態を結合するため、深いファイルの変更で祖先の表示一覧すべてを複製しない。件数、サイズ順、ページ取得、連続スクロール、過去世代の表示を維持する。

既存の24時間＋日別最終記録の保持規則と閲覧リースを維持する。リースのない退役世代の参照を除いた後、残る世代から参照されない一覧・観測・名前・ストリーム・集計だけを同じトランザクションで回収する。元スキャンを削除しただけで、他のスキャンが使う状態を消さない。DuckDBファイルは削除直後に小さくなるとは限らず、解放領域を次の保存で再利用する。

## 確認

本体の保存経路を使用した10万件・3世代（初回、未変更、約1%変更）の合成比較で、現行全件保存・各試作と全保存事実・一覧・測定照会・先頭世代削除後の残存履歴が一致した。共有形式の最終本体63.5MiB、全件形式123.0MiB。初回保存2.222秒、未変更0.686秒に対し、全件形式は2.178秒、2.128秒。保存時間には変更比較を含む。これは一回の予備測定で、入力生成・集計を除いた保存のみ。

比較CLIの `--history-dedup --mode production` で本体の共有形式を測れる。`--mode all` は全件方式・3試作・本体形式を比較する。例:

```powershell
dotnet run --project tools/Something.StorageCompare -c Release -- --history-dedup --count 100000 --generations 3 --output artifacts/history-dedup-production-100k.json
```

既存の期間比較・履歴テストに加え、全接続を閉じた後の未変更共有、名前/属性/ADS/ヘッダー数/シーケンス変更、未取得・未解決、ボリュームの分離、保持整理と共有状態の回収、リース、公開キャンセルと再試行、OOM時の増額前のロールバック、5000件フォルダの単一ブロック更新と一覧APIをテストする。実ディスクでの容量・一覧応答・保存速度はこれから確認する。初期のC#キャッシュを使う試作の速度を本体の速度として扱わない。
