# 履歴の比較と管理

## 識別と保持

履歴には、ボリュームの識別情報、シリアル、取得範囲、スキャン ID、完了日時（UTC）、記録時のローカル日付と UTC オフセットを保存します。ファイルとフォルダーは MFT 番号とシーケンス番号の組で照合し、番号だけで同じものとは判断しません。シーケンス番号が一周するほどの長期にわたる同一性は保証しません。

[`HistoryRetention`](../src/Something.Application/History/ScanHistoryEntry.cs) の保持規則は次のとおりです。

1. 現在から 7 日未満のスキャンは、すべて残す。
2. それより前は、ボリュームと記録時のローカル日付ごとに、最後のスキャンを残す。
3. 同じ時刻のスキャンは、スキャン ID で一意に選ぶ。ちょうど 7 日前のものは、すべて残す対象に含めない。

整理は、新しいスキャンの保存に成功したあとに行います。起動時、バックグラウンドの監視、定期的なタイマーでは整理しません。日付は保存済みのローカル日付を使い、タイムゾーンを変えても過去の分類はやり直しません。保持する日数の上限は設けていませんが、最初のスキャンより前の履歴は当然ありません。

## 比較対象の選択

表示するスキャンを終点として、24 時間、7 / 30 / 365 日間、今日、今週、今月、今年、または任意の 2 回のスキャンを比較できます。週は月曜始まりです。期間の区切りは、指定したタイムゾーンで決めます。

[`ComparisonSelection`](../src/Something.Application/Comparison/ComparisonSelection.cs) は、終点より後のスキャンを使いません。期間の開始時点以前で最新のスキャンを比較元とし、それがなければ期間内で最も古い別のスキャンを使います。この場合は「履歴がある範囲のみ」の比較として、指定した期間と実際に比較した両端を区別して表示します。

スキャンが 1 回分しかない場合は、それを比較元に残し、比較先を「なし」とします。同じスキャンを両端に使って増減 0 と表示することはしません。任意比較では画面上の矢印に沿って、比較先のサイズから比較元のサイズを引きます。

増減は期間の両端のサイズの差で、期間内のすべての変化の累積や、一時的なピークではありません。同じ識別子のまま名前の変更や移動があった場合は、両端のパスをそれぞれ保持します。片側にしかない観測、未解決の容量、階層の不確かさは、追加・削除や確定した増減とは区別します。比較の両端には同じ表示設定を適用します。

## 手動で履歴を削除する

履歴タブは共通のドライブ選択を使い、スキャン日時とレコード数を一覧表示します。ヘッダーのチェックから全選択・解除できます。

日時の範囲や期間のボタンは、範囲の入力を変えるだけです。「この範囲で選択」を押すと、行のチェックに反映されます。開始と終了の初期値は、履歴の日時から決めます。選択した履歴を削除する前に、件数と日時の範囲を確認ダイアログに表示します。

削除の対象は履歴のデータだけで、実際のファイルは削除しません。完了後は関係する表示を読み直し、通知します。表示中で参照が残っている共有状態は、その参照が解放されたあとに回収します。

## データベースのサイズと最適化

履歴タブと設定画面のデータベースのサイズは、現行 DB 本体と WAL のファイル長の合計です。全ドライブ共通の値で、スキャンごとのサイズではありません。状態を共有しているため、レコード数から容量を単純に換算することはできません。旧形式、作業用のコピー、バックアップはこの値に含めません。値は変更を伴う操作のあとと画面の読み込み時に更新し、常に監視することはしません。

通常の削除のあとは `CHECKPOINT` を行います。DB ファイルが削除した件数に比例して小さくなるとは限らず、空いた領域はあとの保存で再利用されます。ファイル全体を詰め直す場合は、履歴タブの「データベースを最適化」か、削除の確認ダイアログにある最適化のオプションを使います。時間と空きディスクが必要なので、明示的な操作と確認を求めます。

[`HistoryCompaction`](../src/Something.Storage/HistoryCompaction.cs) の手順は次のとおりです。

1. 閲覧セッションを解放し、DB ゲートを取得する。残る管理対象接続があれば拒否する。
2. 退役世代を回収してチェックポイントする。日次保持規則での追加の間引きは行わない。
3. 元 DB の 1.25 倍 + 64 MiB の空きディスクを事前確認し、専用作業ディレクトリにファイル DB をコピーする。
4. 全永続テーブルを双方向の `EXCEPT ALL` で照合し、形式・共有関係も再検証してフラッシュする。
5. コピー先が小さい場合だけ、バックアップを伴う `File.Replace` で置き換える。再接続の検証後にバックアップを削除する。

切り替える前まではキャンセルできます。置き換えと再検証の短い区間はキャンセルしません。置き換えが完了していないことを示す `.compaction-backup` があれば、次の操作で元の DB を復元します。WAL などが併存する不明な状態のファイルを、強引に消すことはしません。異常終了したときは、`.compaction-*` の作業用コピーが残ることがあります。

コピーと照合には、メモリと一時的なディスクへの書き込みが必要です。成功しても、必ず小さくなるとは限りません。削除後の最適化だけが失敗した場合は、削除が完了したことと最適化に失敗したことを分けて通知します。

## 保存先の変更とデータベース全体の削除

設定ページの「履歴データベース」で、保存先フォルダーの変更、フォルダーを開く操作、データベース全体の削除ができます。設定は `%LOCALAPPDATA%\Something\database-settings.json` に保存します。表示設定とは別のファイルで、デモは通常の設定を読み書きしません。

保存先を変更すると、全ドライブの履歴を移動します。DB の参照を解放し、WAL をチェックポイントしたあと、移動先へコピーして形式を検証します。設定を原子的に更新してから、元の DB を削除します。移動先にすでに DB・WAL・復旧用のファイルがある場合は、上書きしません。設定を確定する前に失敗した場合は元の保存先のまま使い、元の DB の削除だけに失敗した場合は、新しい保存先を使ったうえで警告します。

データベース全体の削除では、確認のあとに現行形式の DB だけを削除し、表示中のスキャンをクリアします。空の表示のためにすぐ DB を作り直すことはせず、次のスキャンのときに作成します。隣にあるほかのファイル、旧 SQLite、旧形式の DB、単独で残った不明な WAL は削除しません。

スキャン・読み込み・履歴の処理中は、移動・全体の削除・最適化を始められません。

> [!WARNING]
> 履歴を手作業でバックアップする場合は、アプリを終了してから、DB と（あれば）WAL を一組としてコピーしてください。使用中の DB 本体だけをコピーしないでください。
