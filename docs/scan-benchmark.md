# 読み取り専用全件走査の基準測定

## 実装と目的

`LiveMftScanner` はファイルの観測結果を `IAsyncEnumerable<MftScanEntry>` として逐次返す。
全件をメモリへ蓄積せず、baseレコードだけから完全に結合できたファイルのDATA容量を報告する。
拡張レコードは別のファイルとして容量を加算しない。フォルダへの帰属・種別分類・履歴保存はまだ行わない。

Windows取得層は `FSCTL_GET_NTFS_FILE_RECORD` を降順に使用する。
要求した番号以下の最初の使用中レコードが返るため、次の要求を「返された番号 - 1」にすることで
観測時の空きスロットを1個ずつ取得せずに進める。
これは [MicrosoftのAPI仕様](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_get_ntfs_file_record)
に沿った列挙であり、MFT全体をまとめてraw取得する高速経路はまだ実装していない。
まず、既存の取得・再検証経路の時間を測る基準実装とする。

列挙した番号とシーケンス番号をファイル再取得時にも照合する。
途中の削除・変更・参照再利用・不正構造・未対応・取得上限超過は、容量不明として区別する。
結果は既存の `LiveMftFileReader` の上限付き結合・再検証を経て返す。
列挙が飛ばしたスロットは「今回返されなかった」だけで、過去のファイルの削除を証明しない。
開始時のMFT長で範囲を固定するので、範囲外に増えたスロットは今回の対象に含まれない。
時点スナップショットではなく、未訪問スロットに対する変更やABAは検出できない。

## コマンド

管理者PowerShellをリポジトリ直下で開き、まず少数スロットで確認する。
Releaseビルドを事前に行い、ビルド時間を測定に含めない。

```powershell
dotnet build Something.slnx -c Release
# スロット0〜9999だけを測定。ファイル10000件という意味ではない
dotnet run --project tools/Something.LiveInspect -c Release --no-build -- C: --scan 10000
# 開始時に観測した全スロットを走査
dotnet run --project tools/Something.LiveInspect -c Release --no-build -- C: --scan
```

範囲は0から指定上限まで。指定上限は開始時のスロット数以下でなければならない。
Ctrl+Cでキャンセルする。実行中の同期ネイティブI/Oを即時中断する保証はない。
ボリュームアクセスはGENERIC_READだけで、ロック・マウント解除・修復・書き込みは行わない。
結果・名前・パス・rawデータをディスクに保存しない。

## 出力と測定の読み方

ドライブのプロパティの「使用領域」と比較するときは、`Resolved-DATA-only`の
`allocated-bytes`を使う。これはフォルダ帰属やSQLiteを通さず、取得できた全baseファイルの
全DATAストリームを一度ずつ足した値で、ハードリンク名・拡張レコードでは重複加算しない。
ディレクトリ自身のDATAと、取得できたNTFS管理ファイルのDATAも含む。
`Resolved-regular-files-DATA`はディレクトリを除いたファイル件数・論理容量・割り当て容量を別表示する。

`Volume-at-open.used-bytes`は開始時のNTFSボリューム応答の使用中クラスタ数×クラスタサイズ。
`DATA-allocated-bytes`と差分も最後に表示する。ボリューム使用量にはDATA以外の管理領域なども含まれ、
取得不能のファイルや開始後の変更もあるため、差分を即座に集計誤りや管理領域のサイズと断定しない。
キャンセル時・`completed=False`の差分は途中集計との比較であり、全件比較には使わない。

レコード単位の出力は行わない。標準エラーへ開始時に1行、その後5秒に1行だけ途中経過を表示する。
心拍表示は取得を行うワーカーとは別タスクで動くので、ネイティブI/O待ちの間も経過時間を表示できる。
`last-completed-record` は最後に処理が完了した番号。値や件数が増えない場合は新しい結果が出ていない。
心拍表示が出ること自体は、ディスク取得が正常に進んでいる証明ではない。

最後に標準出力へまとめて表示する。未解決理由は状態ごとに最初の3件までに絞る。
キャンセル・I/O失敗時も `completed=False` として、それまでの件数を表示する。

| 項目 | 意味 |
|---|---|
| observed-slots | 開始時に決めた走査範囲のスロット数 |
| traversed-slots | 結果が完了した位置までのスロット数。正常終了時は全範囲 |
| candidates | 列挙され、処理が完了した候補レコード数 |
| slots-not-returned | 走査済み範囲で候補として返されなかった数。削除件数ではない |
| resolved-files / resolved-directories | 再検証・完全結合に成功したbaseファイル／ディレクトリ数 |
| extension-records | 再検証した拡張レコード数。別ファイルとして計上しない |
| unresolved | 容量を確定できなかった候補数 |
| Elapsed / candidates-per-second | 逐次走査・解析・結合・再検証・集計にかかった実時間と候補処理速度 |
| native-read-time | FILEレコード／リストクラスタの取得バックエンド呼び出し時間の合計 |
| record-requests / raw-reads | 再検証・失敗を含むFILEレコード要求数／リストクラスタ読み取り回数 |
| Resolved-DATA-only | 解決済みbaseの全DATAストリームの論理／割り当てバイト数の参考合計 |

最終出力は計時停止後に行う。5秒ごとの出力は測定中だが、件数に比例して増やさない。
ドライブを開く時間、初期ジオメトリ取得、ビルドは測定対象外。
`native-read-time` はロック待ち・解析・コンソール出力を含めず、raw読み取りの初回整列情報照会は含む。
実時間との差は解析だけの時間ではなく、割り当て・タスク実行・集計等も含む。
OSキャッシュや別プロセスの負荷により測定値は変わる。キャッシュを強制消去する操作は行わない。

DATA参考合計には名前付きストリームと管理ファイルの解決済みDATAも含む。
baseを一度だけ加算するため、同じファイルの複数ハードリンク名は二重加算しない。
未解決ファイル、MFTレコード自身やディレクトリ索引などの管理領域は総占有量として補完しない。
resident DATAの追加割り当て0もファイル全体の占有量0ではない。
この値はドライブ使用量や完全なフォルダ集計とは扱わない。
合計はUInt128で保持し、容量演算のオーバーフローを防ぐ。

終了コードは0が走査完了かつ未解決なし、1が走査完了かつ未解決あり、2が入力・権限・I/O失敗、
130がキャンセル。`$BadClus` の専用集計はまだ未対応なので、これが含まれる走査では未解決になりうる。

## 検証範囲

未解決理由は走査終了後に状態ごとに最大3例を表示する。最初の例に加え、残る取得上限等の
理由を同じ走査で確認できる。超過例は省略件数だけ表示し、5秒間隔の途中表示は増やさない。
保持するのは番号・理由のみで、ファイル名・パス・rawレコード・ファイルモデルを保存しない。
理由は最大1024文字、状態数と例数も有限に制限する。全未解決の履歴やdumpは作らない。
例は原因の代表性を保証する抽出ではなく、列挙順に最初の3件である。

合成テストで順序・重複・範囲の検証、空き範囲の飛び越し、所有するレコードバッファ、
baseと拡張の区別、変更・削除・参照再利用、不正レコードの再取得、結合失敗、部分消費時の列挙解放、
キャンセル・I/O例外の伝達を確認した。
少数レコードと非residentリストの実機確認は [windows-acquisition.md](windows-acquisition.md) を参照。

2026-10-12、ユーザーの実機でRelease版を実行し、1万スロットの範囲走査と全件走査が完了した。
この条件での基準値は次のとおり。デバイスの詳細、OSキャッシュ状態、他プロセスの負荷は未測定。

| 測定 | 実時間 | 候補処理速度 | ネイティブ取得時間 | レコード要求回数 |
|---|---:|---:|---:|---:|
| 1万スロット | 0.572秒 | 17,473.6件/秒 | 0.420秒 | 50,487 |
| 開始時の全スロット | 36.710秒 | 39,150.8件/秒 | 32.608秒 | 7,294,666 |

全件走査では未解決1,270件（InvalidRecord 1,212、InvalidAssembly 51、Unsupported 1、LimitExceeded 6）を報告した。
最初のInvalidRecord理由は復元済み入力でのUSA保存値とセクタ末尾の不一致、
最初のInvalidAssembly理由はDATA extentの不連続・重複・flags不一致のいずれかだった。
この測定はWindows取得をFixupsRestoredとしていた変更前の値。
その後、入力契約をWindowsDecodedとして分離し、結合エラー理由も個別表示へ変更した。
これは変更前の測定記録。修正後の全件走査と上限128／256の比較結果は
[windows-acquisition.md](windows-acquisition.md) の検証状況に記録している。
Unsupportedの1件は `$BadClus` 専用集計の未対応。LimitExceededは既定のファイル取得レコード上限超過。
これらをディスク破損や容量0とは扱わない。未解決ファイルの容量を含む完全な集計はまだできない。
5秒間隔の進捗表示も動作したが、今回の測定で例外・キャンセル・I/O長時間待機を実機検証したわけではない。

取得時間が実時間の約89%を占めるため、取得APIの呼び出し回数を削減することが次の速度改善候補になる。
ただし、まず未解決の入力形式・結合条件を切り分け、正常なファイルを取りこぼさないことを確認する。

### 圧縮設定の継続省略対応後の全件確認

2026-10-12、ユーザーの実機でRelease版を最大取得レコード数256として再実行した。
開始時の2,050,304スロットを走査し、候補1,441,654件、解決済みファイル1,179,946件、
ディレクトリ210,135件、拡張レコード51,570件、未解決3件だった。
未解決の内訳は `$BadClus` の専用集計未対応1件と、取得上限超過2件（必要317件・289件）。
今回の走査ではextent設定差によるUnsupported、InvalidRecord、InvalidAssemblyの報告はなかった。
全形式への対応や他ボリュームでの結果を保証するものではない。

実時間16.360秒、候補処理速度88,120.3件/秒、ネイティブ取得時間12.869秒、
レコード要求7,320,988回、raw読み取り9,018回だった。
解決済みDATAの参考合計は論理1,449,719,217,864バイト、割り当て1,395,000,381,440バイト。
未解決ファイルと管理領域を含むディスク使用量ではない。
累積managed割り当ては43,777,826,848バイト、プロセス開始後のピークworking setは68,022,272バイト。
前者は保持メモリやピーク値ではなく、走査中に繰り返し確保された合計。
走査時点や候補数・キャッシュ状態が異なるので、前回との差を容量増減や処理改善の効果と断定しない。

### フォルダ帰属を通さない総量の確認

2026-10-13のユーザー実機で全件走査を行い、解決済みDATA割り当て量は
1,440,562,024,448バイト、開始時のボリューム使用量は1,441,348,419,584バイトだった。
差は786,395,136バイト（使用量の約0.055%）。未解決は`$BadClus`1件だった。
総量が近いことは全ファイルの個別容量の正しさや差分の内訳の証明ではない。
旧フォルダ集計の大幅な不足は、総量とは分けて調査した。
DOS短縮名を持つ通常ファイルを所属不明に誤分類する取得アダプターの問題を
公開コーパス7ケースで再現・修正した。詳細は[statistics-design.md](statistics-design.md)を参照。
修正後の実機ランキングではフォルダ容量の大幅な不足は改善したが、
エクスプローラーとの残差の調査は継続中。

### バッファ方式の追試と名前数の残差

2026-10-13の実機追試は50.894秒。走査・バッファ18.251秒、メモリ集計1.405秒、
永続化・公開28.963秒、ランキング2.165秒だった。
バッファ後managedメモリ667,017,088バイト、ピークworking set1,107,709,952バイト。
性能改善はこの状態で保留し、容量差の調査を優先する。

容量保存則は一致した。所属不明16,735件はすべて`NameCountMismatch`で、
論理8,044,595,672バイト、割り当て8,064,389,120バイトだった。
最大の2サンプルはいずれもヘッダー名前数3に対して結合後FILE_NAMEが1だった。
これはフォルダ合計から除外された理由を示すが、取得漏れ・ヘッダーの意味・
実メタデータの状態のどれが原因かはまだ確定していない。
所属不明容量が特定のフォルダに属するとも断定しない。

2026-10-13、`adc5656`の変更後の全件ランキングは53.052秒。
走査・バッファ19.431秒、メモリ集計1.508秒、永続化・公開29.763秒、ランキング2.207秒。
