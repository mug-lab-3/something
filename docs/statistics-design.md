# フォルダ容量・肥大化の集計設計

設計日: 2026-10-13。統計層の基礎を実装。保存・UI・ライブ接続・分類・履歴比較は未実装。
この文書は実装済み部分と次の実装の判断基準とする。
保存の基盤は [storage-design.md](storage-design.md)、取得の制限は
[ntfs-format-audit.md](ntfs-format-audit.md) を参照。

## 採用する指標

主指標は解決済みDATAの割り当て容量。論理サイズも別に保存・表示する。
同一ボリュームの同一ファイル参照（シーケンス番号込み）のDATAは一度だけ計上する。
圧縮・Sparseは解析済みの物理割り当てを使い、名前付きDATAも含める。
常駐DATAの専用クラスタ割り当て0は正常な値だが、そのファイルの管理コストが0という意味ではない。
名前・FILE_NAMEのキャッシュ容量、extentごとの容量欄は容量の正本にしない。

これはDATA割り当ての分析であり、ドライブの全占有量の完全な配分ではない。
ディレクトリ索引、MFT、その他の管理属性、WOF・重複排除等による共有実体の扱いは別問題。
それらをDATA合計から推測してフォルダへ配分しない。

| 指標 | 意味 |
|---|---|
| DirectData | 直下の通常ファイルに一意に帰属したDATA容量 |
| SharedData | このフォルダを共通祖先とする共有ファイルのDATA容量 |
| DirectoryData | フォルダ自身のDATA容量。索引などDATA以外の属性は含めない |
| SubtreeData | DirectData + SharedData + DirectoryData + 子フォルダのSubtreeData |
| ReferencedSharedData | 配下に名前がある共有ファイルの参考容量。使用量合計に加えない |

上記の加算可能な指標は論理・割り当ての両方に用意する。主表示は割り当て。
量はバイト単位の整数で持ち、丸めは表示時だけ行う。
帰属ファイル件数も容量と同じ帰属先で一度だけ計上する。表示する名前数・共有参照件数・
ディレクトリ件数は別の指標にし、ファイル数へ混ぜない。

## ハードリンクの帰属

ユーザーと合意した方針は、共有DATAを各リンクの最も近い共通祖先へ一度だけ帰属させる方式。
元ファイルとリンクを推定して選ばず、決定的な代表名を元ファイルと呼ぶこともしない。
Microsoftの説明ではハードリンクは同じボリュームの同じファイルへの複数のパス。
現在取得するMFT情報には元の名前を示す識別情報がない。
[Hard links and junctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)

1. 一つのファイルの有効な名前から、異なる親フォルダ参照の集合を作る。
2. 親が一つだけなら、その親のDirectDataへ一度だけ計上する。同じ親の複数名でも二重計上しない。
3. 親が複数なら、全親の最も近い共通祖先のSharedDataへ一度だけ計上する。
4. 各リンクは名前・親・共有ファイル参照を記録する。参考の共有容量とリンク数を表示できる。
5. 複数リンクの表示行に、独立したリンクファイルの割り当てサイズを捏造しない。
   帰属容量0と、共有実体の容量・不明な管理コストを別のフィールドにする。
   LinkMetadataBytesは初期版では不明。FILE_NAMEの属性長等をリンクの物理占有量と同一視しない。

例: `Root/A/a.bin` と `Root/B/b.bin` が同じ100 MiBのDATAを参照する場合、
AとBの帰属容量は各0 MiB、RootのSharedDataは100 MiB、RootのSubtreeDataは100 MiB。
AとBにはそれぞれ共有ファイルへの参照100 MiBを参考表示する。
共有容量は親画面の独立した項目として必ず見せる。子の容量の和との差を隠さない。

DOSエイリアスは保存するが独立したリンクとして追加しない。Win32AndDosは一つの名前。
POSIX名と大文字小文字を保持し、OSやSQLiteの大文字小文字無視比較で名前を潰さない。
DOS名だけが残る、拡張レコードを取得できないなど、リンク集合を確認できない場合は
LinkSetIncompleteとする。所属を確認できない共有DATAはUnattributedDataへ一度だけ計上し、
分かっている名前だけから共通祖先を推定しない。

初期版はボリューム全体を取得してからフォルダを絞り込む。部分スキャンから全リンクを推定しない。
同一ファイルが管理領域と一般領域の双方へリンクされている場合は、推定で一方へ寄せず分類競合を記録する。

## 管理領域と分類不能

| 区分 | 扱い |
|---|---|
| OrdinaryData | 一般ファイルとフォルダ自身のDATA。隠し・System属性だけで除外しない |
| NtfsMetadata | NTFS内部ファイルの解決済みDATA。通常の肥大化ランキングから分離 |
| UnattributedData | DATA容量は解決済みだが、親・リンク集合・階層などの所属が不明 |
| UnresolvedCapacity | 容量を取得できない対象。既知の部分容量をファイル全体の容量にしない |

NTFS 3.xで予約された先頭16レコードのうち、ルート（5）はフォルダ集計の起点とする。
その他の予約レコードは内部管理対象として分類する。未使用スロットや拡張レコードを
独立した管理ファイルの容量として数えない。
`$Extend` 配下は検証済みの参照関係で判定する。予約名前・親関係が不整合なら問題を残す。
単に名前が `$` で始まる一般ファイルを管理領域へ隠さない。
[Microsoft: Master File Table](https://learn.microsoft.com/en-us/windows/win32/devnotes/master-file-table)

`$BadClus` は既存の参照・名前・ストリームを検査する分類器の判定を引き継ぐ。
専用集計が未実装でも「NTFS管理領域・容量不明」として記録し、通常のフォルダ未解決と分ける。
一般DATAの規則を緩めて通したり、0バイトに置き換えたりしない。
これで一般フォルダの解析を進められるが、管理領域の完全集計を達成したとは扱わない。

ボリュームの概要ではOrdinaryData・NtfsMetadata・UnattributedDataの既知合計と、
各区分の未解決件数を別々に表示する。ドライブ使用量はWindowsの独立した取得結果を別指標として持つ。
異なる取得時刻や共有実体もあり得るので、両者の差を確定的な管理領域容量と呼ばない。
ドライブ使用量の取得に失敗したら、取得不能を表示しDATA合計へ置き換えない。

## フォルダ階層と観測品質

フォルダのキーはボリューム・観測区間・シーケンス番号込みの参照。パスは表示用。
親の存在・種別・シーケンスを検査し、ルートの自己参照だけを終端として許可する。
それ以外の自己参照・循環・複数の矛盾する親・欠落・再利用は階層不明とする。
再帰呼び出しに頼らず、深い階層でもスタックを消費し続けない探索にする。

シンボリックリンク・ジャンクションのリンク先を辿らず、別ボリュームを混ぜない。
その参照自身にDATAがあれば一度だけ計上し、reparse属性などの管理コストをDATAに混ぜない。
MFTから独立に取得した実在の親子関係は検証する。reparse点という理由で、確認できた実在レコードを消さない。

フォルダにはKnownBytes・解決済み件数・容量不明件数・所属不明の影響を保存する。
親まで所属が確認できる欠測は、その祖先へ品質問題を伝播する。
所属すら不明な通常ファイルがある場合、ボリューム全体にUnknownAttributionを付け、
影響がないと確認できないフォルダの履歴比較を信頼できる比較として出さない。
管理領域だけの容量不明は一般フォルダの品質と分けるが、ドライブ全体の集計品質には残す。

Completedは走査処理の完了。集計品質とOptimisticLiveは別の情報。
容量不明を0にせず、既知合計はライブ観測の部分合計として表示する。
表示上の全項目が解決済みでも時点スナップショットや全リンクの同時存在を保証しない。
欠測対象の前回値を現在値に混ぜない。中断・失敗時は前の公開世代を維持する。

## データ種別

共有ファイルも含め、ファイル単位で一つの主分類を決め、全DATAストリームへ適用する。
全正規名の拡張子が同じ分類なら採用し、異なる分類を示すリンク名は「その他・不明」にする。
名前付きDATAは所属ファイルの分類へ算入し、独立した拡張子で二重分類しない。
動画・音声・画像・文書・アーカイブ・アプリ／開発・ディスクイメージ・その他を初期分類とする。
ログ／キャッシュ等の用途は別軸のタグにし、データ種別の円グラフへ混ぜて二重加算しない。
用途タグが複数なら、その割合図も互いに排他的な優先規則を定義してから追加する。
内容は読まない。管理領域は一般データ種別の割合から分ける。

容量割合の分母は選択フォルダの既知SubtreeData。SharedDataは共通祖先での分類へ一度だけ含める。
参考のReferencedSharedDataは分母・分子に加えない。不明分類は分母に含め、容量不明は件数として示す。
分母0なら割合は未定義。欠測があれば「既知容量に対する割合」と表示する。
分類・容量算入・リンク帰属のルールをそれぞれバージョン管理する。

## 肥大化の比較

同じボリューム・観測区間・対象範囲・帰属規則・容量算入規則で、品質が比較可能な世代を使う。
フォルダの参照再利用、連続性不明、欠測、ルール変更は比較不能の理由を返す。
初期の全件スキャンだけでは削除や観測間の連続性を証明できないので、差は「観測容量差」と呼ぶ。
OptimisticLiveの比較を確定的な内容増加と表示しない。

| 保存・算出する値 | 用途 |
|---|---|
| Direct / Shared / Directory / Subtreeの各差 | 直下・共有の帰属・配下の変化を分ける |
| 正のバイト差 | 初期の増加ランキングの主順位 |
| バイト差 / 実際の経過日数 | 計測間隔が違う場合の増加速度 |
| バイト差 / 基準容量 | 増加率。基準0の場合は未定義 |
| 過去の親・名前、今回の親・名前 | フォルダ移動・改名の表示 |

7日・30日の基準は目標日時以前で最も近い比較可能な計測を使う。最大許容ずれは設定とし、
範囲内の基準がなければ欠測。実際の両日時・比較期間・基準のずれを必ず表示する。
複数期間で正の観測容量差が続くフォルダを優先して見せるが、因果を断定しない。
最低容量差・期間数等のランキング条件は設定として保持する。

共有リンクの追加・削除・移動だけでも共通祖先への帰属が変わる。SharedDataの変化を
「共有容量の変化（帰属変更を含む）」と表示し、ファイル内容が増えたと断定しない。
最新ファイル詳細とフォルダ履歴だけでは、全ファイルの過去の移動・増加原因を分解できない。
初期版はこの制約を明示する。完全な原因分解にはリンク帰属の変更履歴等を別途設計する。
親子のランキングは掘り下げ用で、親子の増加量を足し合わせない。

## 実装境界と処理手順

`Something.Statistics` はWindows API・SQLite・UIへ依存しない純粋な集計ライブラリにする。
取得結果から作る入力は完全な参照、親と名前、取得状態、管理分類、リンク数の観測、
解決済みストリーム容量、reparseの観測、走査範囲と品質。rawバッファ・全runは集計層に保持しない。
既存NtfsFileはリンク数を持たず、未解決MftScanEntryは親・管理分類を持たないため、
取得のアダプターに必要な型付き観測を追加する。Error文字列や番号だけからBadClus判定を復元しない。
不完全なレコードから得た名前も完全なリンク集合・確定した所属として採用しない。

| 責務 | 初期のクラス／入力・出力 |
|---|---|
| 容量算入の規則 | CapacityPolicy / 管理区分・ストリーム → 容量と品質 |
| 名前の保持とリンク正規化 | FileLinkNormalizer / 名前・リンク数の観測 → 親集合と完全性 |
| 階層検証と共通祖先検索 | FolderGraph / フォルダ観測 → 有効な階層・問題・共通祖先 |
| 一つの帰属先の決定 | FileAttributionPolicy / ファイル・親集合 → 直下・共有・所属不明 |
| 集計 | FolderAggregator / 帰属観測 → フォルダ・種別・ボリュームの集計と品質 |
| 履歴比較 | FolderHistoryComparer / 二世代の集計と条件 → 観測差または比較不能理由 |

これらの純粋な入力・出力を先に固定する。取得の非同期列挙とステージ保存の制御は
上位の処理担当に置き、集計クラスの中でボリュームを開いたりDBへ書いたりしない。

1. メタデータをコンパクトな観測へ変換し、同一世代のステージ領域へバッチ保存する。
2. フォルダ参照グラフを作り、所属・循環・欠測を検査する。
3. ステージ領域からファイルを逐次読み、リンクを正規化、管理分類、共通祖先を決定する。
4. ファイルの容量・分類・件数を一つの帰属先へ加え、フォルダを子から親へ一度ずつ合算する。
5. 品質・カテゴリ合計・ボリューム一意合計を照合し、完了世代だけを公開する。

保存層は統計層のための列挙とステージングを提供し、統計層にSQLを埋め込まない。
フォルダのグラフ・集計だけを主にメモリへ保持し、全ファイルのモデルや祖先ごとのファイル集合を蓄えない。
共通祖先の判定は前処理したグラフで行い、毎ファイルから全階層を辿る実装の速度を測定する。
必要なら祖先検索索引を追加する。メモリ不足は明示的な失敗とし、部分結果を完全として公開しない。
バッチ・グラフ探索・リンク処理の境界でキャンセルを確認し、進捗は時間間隔で絞る。

集計はchecked UInt128、容量差は符号付きで表現範囲を検査する（例: BigInteger）。
SQLiteでは集計容量を固定長16バイトbig-endian BLOBとして往復し、SQLのSUMに依存しない。
ストリームのlong容量とは別の保存形式にする。不明値はNULLと状態で表し、0とは区別する。

## 実装順と検証条件

最初は型・ポリシー・階層検証と、小さな合成観測の集計を作る。次に保存層のステージングと接続し、
実機ではパスを通常ログへ出さない要約CLIで測定する。最後に分類・履歴比較・UIへ進む。
スキャン対象は読み取り専用。永続化はアプリ専用DBだけで行い、フォーマット・修復・属性変更はしない。

以下をxUnit v3 / MTPで検証する。非同期処理にはテストのキャンセルトークンを渡す。

- 同じ親の複数名、兄弟間の共有、祖先と子の共有、DOS・POSIX名、分類が衝突するリンク名。
- 100 MiBの共有例で親は100 MiB、子の帰属は0、参考値は重複しても主合計へ入らない。
- 入力順を変えても結果不変。帰属合計とボリューム一意DATA合計が一致し、カテゴリ和も一致する。
- 常駐0、圧縮・Sparse、名前付きDATA、ディレクトリ自身のDATA、管理ファイルの分離。
- 欠損親、シーケンス違い、循環、深い階層、リンク集合不足、所属不明、正常0と容量不明の区別。
- 共有先の変更、移動・改名・参照再利用、欠測、分類変更、基準0、異なる期間の比較。
- オーバーフロー・キャンセル・バッチ失敗時に前の公開世代を維持する。
- 決定的な乱数によるグラフ入力と、大規模観測の時間・メモリ測定。合成成功を実機対応の証明にしない。

## 現在の実装と次の作業

`Something.Statistics` にFolderGraph・FileAttributionPolicy・FolderAggregatorを追加した。
NTFSの参照・名前モデルを再利用するが、Windows・DB・UIへの依存はない。
入力は一つのボリューム・世代に限定したコンパクトな観測。ボリュームを混ぜない責任は上位に置く。
管理区分とLinkSetCompleteは取得アダプターが裏付けて渡す値であり、統計層が名前の先頭文字や
手元の名前数だけで推定したものではない。
MftObservationAdapterは再検証済みのファイル参照・種別を型付きの取得証拠と照合する。
通常ファイルは取得・結合が成功し、可視名があり、名前・親参照・namespaceの重複や
対応するWin32名のないDOS名がない場合に、列挙したリンク集合を集計へ採用する。
ヘッダーの名前数との不一致だけでは所属不明へ分類しない。
これは完全な属性列挙を前提とする楽観的観測であり、同一時点の完全性保証ではない。
ATTRIBUTE_LISTの参照先欠落・再利用・未掲載属性・不正な属性構造は従来どおり結合失敗となる。
ディレクトリの所属はFolderGraphで親参照を検証する。
管理ファイルは予約レコードと検証済みの管理ディレクトリの祖先で分類し、`$`で始まる名前だけでは判定しない。
MFTヘッダーの名前数は独立したDOS短縮名も含み、Windows APIが返す可視ハードリンク数とは区別する。
この形式上の事実は[Linux NTFS3のDOS名計数修正](https://github.com/torvalds/linux/commit/110b24eb1a749bea3440f3ca2ff890a26179050a)と、
公開NISTコーパス7ケースのDOS名を持つ通常ファイルで照合した。
Microsoftの公開FILE_RECORD_SEGMENT_HEADERでは当該フィールドは予約扱いであり、公開APIの保証とは区別する。
OSSコードのコピーや翻訳は行っていない。

DOS名を除いた数をヘッダーと比較していた旧アダプターは、通常ファイルを所属不明へ誤分類した。
容量自体はUnattributed.KnownDataへ残っていたが、フォルダランキングから欠落していた。
修正後はDOS名の対応関係を検査し、帰属時だけエイリアスを除外する。
保存層は入力の既知DATA総量がルートのSubtreeData＋Metadata.KnownData＋Unattributed.KnownDataに
一致することを公開前に検証し、不一致なら例外にする。ランキングCLIも全区分の既知量を最終表示する。

2026-10-13の実機診断では、所属不明だった2件でヘッダー3・FILE_NAME1・Windowsリンク数1を観測し、
論理容量と割り当て容量はNTFSとWindowsで一致した。
これを受け、ヘッダーの計数を完全性の判定条件から外した。
参考にした[Linux ntfs3の実装](https://github.com/torvalds/linux/blob/master/fs/ntfs3/inode.c)は、
全FILE_NAMEとDOS専用名を除くリンクを別々に数え、ヘッダー不一致時には列挙数へ補正する。
Somethingはこの列挙優先方針だけを採用し、ディスク上の補正は一切行わない。
取得したヘッダー値・全名前・LinkSetCompleteは従来どおりDBへ保存するので、
保存した観測から不一致を再計算できる。追加のWindows照会は不要。
ランキングCLIは最後にヘッダー不一致件数と、そのうち名前集合を採用した件数を表示する。
変更後の実機全件集計では名前数不一致27,814件を採用し、所属不明容量・件数は0となった。

容量不明はnullableの容量と未解決件数で表す。管理区分の未解決は一般フォルダの未解決と分離。
所属不明はUnattributedへ一度だけ残し、HasUnknownAttributionを返す。
フォルダ観測だけでは、そのフォルダ自身のDATA容量まで取得済みとは限らないため、
DirectoryCapacityObservedとSubtreeUnobservedDirectoryCountも返す。

通常ファイルの帰属件数で、ディレクトリや容量不明件数とは分ける。
この結果だけで履歴を比較可能と断定せず、上位で列挙範囲・観測方式・各品質を合わせて判定する。
