# Something

複数起動を防ぎ、2回目以降は既存のウィンドウを表示します。最小化されている場合は復元します。[起動管理の仕様](docs/single-instance.md)を参照してください。

ファイル・容量分析の一覧右端から、確認後に実ファイル・フォルダをゴミ箱へ移動できます。移動済み項目は取り消し線で表示し、履歴DBの観測値は維持します。[ファイル操作の仕様](docs/file-actions.md)を参照してください。

保存済み履歴は「ファイル／DB管理」タブで切り替えて一覧し、チェックした記録を削除できます。対象ドライブは共通で、日時範囲を編集したり半年前・1年前などの期間ボタンで設定した後、「✓（この範囲で選択）」を押すとチェックに反映します。[履歴管理の仕様](docs/history-management.md)を参照してください。

容量履歴の保存には、性能比較を経てDuckDBのファイル方式を採用しました。[比較結果と採用理由](docs/decisions/20261014-duckdb-storage.md) を記録しています。アプリと診断CLIはDuckDBで動作し、通常の照会はEF Core・LINQ・型付きモデルを使います。保存モデル・欠測の扱い・履歴比較の方針は [docs/storage-design.md](docs/storage-design.md) を参照してください。保存基盤・履歴保存と、過去24時間・7日・365日のフォルダ変動照会APIを実装しています。旧SQLite履歴の自動移行は行わず、新たなスキャンからDuckDBに記録します。
フォルダ容量・共有ファイル・管理領域・肥大化比較の設計は [docs/statistics-design.md](docs/statistics-design.md) を参照してください。フォルダ表示は無名DATAを可視ファイル名ごとに数え、ハードリンクも名前ごとに計上します。ディスク全体の確認用には共有DATAを共通祖先へ一度だけ帰属した値も維持します。ライブ取得・統計・保存基盤とCLIランキング、WinUI画面とサイズ差分モードを実装しました。種別分類は未実装です。

画面上部で「表示する記録」と「比較」を選択します。「比較：なし」ではサイズだけを表示し、期間や任意の比較元を選ぶと、同じ一覧に増減列を追加します。サイズ列は常に表示し、比較前のサイズはツールチップで確認できます。ツリーは展開矢印と名前の間に、増加はオレンジの上矢印、減少は緑の下矢印、比較不能はグレーの疑問符を表示し、変化なしには印を付けません。ランキングはサイズ順に加えて、比較中は増加順・減少順・増減の大きさ順を選べます。24時間・7日間・30日間・365日間、今日・今週（月曜始まり）・今月・今年、任意の比較元に対応します。期間は表示中のスキャン完了日時を基準にします。開始境界以前の記録がなければ期間内で履歴がある範囲を比較し、実際の比較日時と合わせて明示します。履歴不足や未解決容量は0扱いせず区別します。[比較の仕様と制限](docs/comparison-mode.md)を参照してください。

Everythingをもじった、Windows向けのディスク使用量・フォルダ肥大化分析アプリです。

各スキャンのステップ別処理時間と合計時間もDBへ記録し、ドライブカードに `スキャン済み (53.4秒)` と表示します。保存先は `%LOCALAPPDATA%\Something\History\catalog-v4.duckdb`。未変更の観測・名前・ストリーム・フォルダ一覧・集計を共有し、各スキャンは保存済みの状態を直接参照します。未リリースのため旧DBとの互換性・移行処理は持たず、旧ファイルを保持して新しいスキャンから記録します。

現在の大容量フォルダだけでなく、徐々に容量が増えているフォルダを見つけることを重視します。

## 技術方針

- C# + WinUI 3 / Windows App SDK。
- 初期の高速スキャン対象はローカルNTFSボリューム。
- MFTのメタデータをまとめて読み取り、ファイル・フォルダの階層と容量を集計。
- スキャン・解析・集計をUIから独立させ、バックグラウンドで実行。
- SSD / NVMe向けの最適化は、読み取り・解析・集計の時間を分けて計測して判断。
- 低レベルのボリューム読み取りには管理者権限が必要。実行ファイルを開くとWindowsのUACで昇格を求める。

## アプリの起動

普段の開発では `dotnet build Something.slnx` またはVS Codeの `build` タスクを使い、`src\Something.App\bin\Debug\net10.0-windows10.0.26100.0\win-x64\Something.App.exe` を起動します。DLLや画面リソースが並ぶ通常の出力で、自己展開は行いません。Releaseビルドも同じ方式です。通常のビルド・起動は配布用exeを生成しません。

配布用の単一exeが必要なときだけ、以下でpublishします。VS Codeのタスク `publish app` からも実行できます。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/publish-app.ps1
```

出力は `artifacts\publish\win-x64\Something.App.exe` です。このexeだけを配布してください。.NET 10・WinUI・DuckDB・画面リソース・依存ライセンス通知を同梱するため、配布先で.NETやWindows App SDKを事前にインストールする必要はありません。PDBやXML APIドキュメントは含めません。開発用の `bin\Release` は配布対象ではありません。

初回起動時、依存ファイルを通常 `%TEMP%\.net\Something.App\<bundle-id>` に展開します。同じexeの次回起動では展開済みファイルを再利用します。これは通常のインストーラーや静的リンクとは異なり、実行時には展開先のファイルを使用します。新しい版では別の展開先になるため、旧版のキャッシュが残る場合があります。履歴DBの保存先は引き続き `%LOCALAPPDATA%\Something\History` です。

Windows App SDKの総合パッケージではなく、WinUI・DWriteのコンポーネントパッケージを使用します。元の総合パッケージと同じコンポーネント版を固定し、AI・ML・ウィジェットの未使用依存を取り込みません。WinUI/Foundationの共通ランタイム、Windowsメタデータ、多言語リソースは維持します。[配布構成の確認結果](docs/deployment.md)を参照してください。

再発行は完成した新しいフォルダで出力を置き換えるため、前回の残りファイルを混ぜません。`artifacts\publish\win-x64` は生成物専用で、手作業のファイルを置かないでください。そのフォルダから起動中の場合はアプリを閉じてから再発行します。開発用のアプリとビルド出力は別の場所なので、開発用アプリを閉じずに発行できます。

セットアップ後、実行ファイル `src\Something.App\bin\Debug\net10.0-windows10.0.26100.0\win-x64\Something.App.exe` を開くとUAC確認が表示されます。Releaseビルドの場合は `Debug` を `Release` に読み替えてください。

CLIからの `dotnet run` は管理者PowerShellで実行してください。通常のPowerShellからは昇格が必要な実行ファイルを直接起動できないことがあります。実データを使わず画面を確認する場合も、同じ実行ファイルのため昇格が必要です。

```powershell
dotnet run --project src/Something.App -- --demo
```

実際のドライブを調べる場合は、管理者として開いたPowerShellで起動します。

```powershell
dotnet run --project src/Something.App
```

ドライブを選んで「スキャン開始」を押すと、読み取り専用でドライブ全体を調べます。進捗表示・キャンセル、フォルダツリー、ファイル一覧、サイズ順の並べ替え、階層／末端フォルダで絞り込む容量ランキングを利用できます。フォルダ指定のスキャンは行いません。完了したスキャンは履歴として保存し、再起動後も日時を選んで閲覧できます。直近7日間の全記録と、それ以前の各日の最終記録を保持します。保存先は `%LOCALAPPDATA%\Something\History`。詳細は [履歴設計](docs/history-design.md) を参照してください。画面の設計・制限は [docs/ui-design.md](docs/ui-design.md) を参照してください。

VS Codeの「タスクの実行」で `run app` / `run app demo`、デバッグ構成で `Something app` / `Something app (demo)` を選べます。
アプリ起動・デバッグ時はVS Codeも管理者として起動してください。セットアップ・ビルド・単体テストには管理者権限は不要です。

## 計画している機能

SQLiteとDuckDBの合成データによる性能比較CLIは [docs/storage-comparison.md](docs/storage-comparison.md) を参照してください。最適化DuckDBのファイル方式へ切り替え済みです。

履歴の重複保存を減らす比較結果は [docs/history-deduplication-comparison.md](docs/history-deduplication-comparison.md)、本体に組み込んだ共有方式は [docs/decisions/20261014-shared-history.md](docs/decisions/20261014-shared-history.md) を参照してください。

- フォルダ別の容量一覧、容量バー、階層移動。
- 論理サイズとディスク上の割り当て容量の表示。
- ローカルに保存した計測履歴による増加量・増加率の比較。
- 前回、7日前、30日前からの増加ランキングと容量・ファイル数の推移。
- 増加に寄与した子フォルダへの掘り下げ。
- データ種別ごとの容量割合と期間内の増加量。
- 拡張子を基本とした分類、およびキャッシュ・ログなどのパス／名前による分類ルール。

分類例: 動画、音声、画像、文書、アーカイブ、アプリ・開発関連、ディスクイメージ・仮想ディスク、その他・不明。
初期版では分類のためにファイル内容を読みません。

## 最初の実装範囲

1. NTFSボリュームの手動スキャンとフォルダ容量一覧。
2. 起動時・手動の計測、1日1回の履歴保存。
3. 7日・30日の増加ランキングとフォルダ別の推移グラフ。
4. ドライブ全体／選択フォルダのデータ種別別容量表示。

初回計測が履歴の基準になります。計測前の容量推移は復元しません。
USNジャーナルによる差分更新は、その後の拡張として検討します。

## 集計で考慮すること

- ハードリンクの二重計上と、複数フォルダへの容量帰属。
- 圧縮、スパースファイル、代替データストリーム、常駐データ。
- ジャンクション／シンボリックリンクの扱い。
- 移動・名前変更と実際のデータ増加の区別。ボリューム識別子・ファイルID・再利用を考慮。
- 親と子をランキングで表示する際の増加量の重複。
- 欠測日を考慮した期間比較と、ライブスキャン中のファイル変更への対応。
- フォルダの集計合計と、NTFS管理領域などを含むドライブ使用済み容量の違い。

## 開発状況

WindowsでGitとVS Code（`code`コマンド）を用意し、リポジトリを取得したら以下の一コマンドで開発環境を準備できます。Visual Studioや事前の.NETインストールは不要です。SDK・Visual C++ランタイムが未導入の場合はWindowsの管理者確認が必要です。初回はインターネット接続が必要です。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/setup.ps1 -Open
```

SDKの取得・ハッシュ確認、推奨拡張のインストール、ワークスペース生成、依存・フォーマッタ復元、整形検査、ビルド、単体テストまで行います。公開テストデータも取得する場合は`-WithPublicCorpus`を追加してください。

UIから独立したMFT解析ライブラリ、オフライン検査CLI、xUnit.net v3 / Microsoft.Testing.Platformによるテストを追加しています。.NET 10 / C# 14を使用します。

VS Code / CLIでの開発手順は [docs/development.md](docs/development.md)、解析の境界・ライブ変更への対応設計・制限は [docs/ntfs-design.md](docs/ntfs-design.md) を参照してください。

読み取り専用Windows取得層と検証CLIを追加しています。実機の通常ファイル1件でMFTとWindows APIの論理サイズ一致を確認しました。範囲と手順は [docs/windows-acquisition.md](docs/windows-acquisition.md) を参照してください。全件走査の基準測定用CLIも追加しました。途中経過は5秒ごとに絞り、最後にまとめて表示します。手順と制限は [docs/scan-benchmark.md](docs/scan-benchmark.md) を参照してください。USN追跡、統計履歴は今後の実装です。

NISTの公開NTFSイメージ7件を使った追加検証を用意しています。利用条件、取得元、検査結果、再実行方法は [docs/public-corpus.md](docs/public-corpus.md) を参照してください。ダンプはGitへ含めません。
